# J Harness 협업 개발

사용자 목표와 기존 프로젝트 상태를 먼저 확인한다. 중요한 누락만 질문하고, 나머지는 되돌릴 수 있는 권장안을 제시한다. 기술 선택을 전부 사용자에게 돌리지 않는다. 기존 스택·데이터·인증·배포 범위를 보존한다.

1. 글로벌 연결 블록의 JH 명령으로 `begin "요청"`을 실행한다. 분석·권장 방향·계획을 한국어로 짧게 설명하고, 제공된 정책 경로 중 지금 필요한 것만 `policy read <ID>`로 읽는다.
2. `skills search "작업 목적"`으로 내장·설치·승인 등록 Skills를 찾는다. 유용한 것만 `skills read <id>`로 읽는다. 이 명령의 출력과 hash가 조회 증거이며, 읽기만 한 것을 실행 성공으로 표시하지 않는다.
3. 적합한 계획과 수용 기준을 정하고 `advance plan`, `advance implement`를 기록하며 개발한다. 외부 설치·비밀정보·삭제·비용·배포 등 중요한 경계에서만 필요한 승인을 받는다. 일상 수정마다 승인받지 않는다.
4. `verify -- <프로젝트 테스트 명령과 인수>`로 실제 테스트를 실행한다. 실패하면 원인·최소 수정·재실행 결과를 남긴다. 테스트를 약화하거나 PASS JSON만 작성해 완료하지 않는다.
5. 실제 적용한 Skill의 결과는 `skills record <id> --result APPLIED --note "..."`로 남긴다. 이는 Agent 보고이며 독립 검증은 실제 명령 기록을 근거로 한다.
6. `advance handoff`, `finish` 전 실행·설치·사용 방법, 성공 범위, 미해결 문제를 설명한다. 브라우저/실사용/배포 미실행은 NOT_RUN이다. 현재 코드 hash가 바뀌면 이전 검증을 무효화한다.

사용자에게 단계별 `[J Harness · 분석/계획/구현/검증/인도]` 진행 상황을 보여 준다. 실제 쓰지 않은 정책/Skill은 적용했다고 말하지 않는다. 소규모 변경은 절차를 간소화하되 검증 근거는 남긴다. ON/OFF는 새 Codex 세션 기준이며 OS 수준의 통제 장치가 아니다.
