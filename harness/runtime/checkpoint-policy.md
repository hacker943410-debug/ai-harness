# Safe checkpoint
Before H2/H3 transition choose a stoppable feature boundary. Record changed files, Git status/branch/base commit, current goal/phase/acceptance, completed and incomplete work, current test evidence and known failures, DB/schema/migration status, environment changes as names only, decisions, risks and next task. Create a recoverable commit or verified snapshot without discarding dirty work.
A checkpoint is safe when another agent/session can restore the exact work and explain the next step; all features need not pass. Verify snapshot bytes and restoration method. Record recovery reference in transition manifest. Binding snapshots from plan/apply protect Harness-managed files; they do not constitute a backup of databases or all product work.
Do not checkpoint during production deployment, destructive migration or data transformation for an unrelated upgrade. Defer at a named milestone; if root cause of failures or merge conflict is unknown, resolve/reconcile first. A HARNESS_BLOCKER records description, affected phase, inability to continue, minimal fix, impact, rollback and verification.
Evidence: Git/snapshot references, file hashes, recorded contract and test results. UNKNOWN recovery blocks H3. Preserve secrets outside checkpoint artifacts.
