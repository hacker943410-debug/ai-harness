# Token and context policy
Budgets: TINY, SMALL, MEDIUM, LARGE, CRITICAL; configure per phase using project size/runtime telemetry. Do not invent exact token limits as universal defaults. Discovery/architecture/implementation/review/release commonly MEDIUM, docs/requirements SMALL, complex debugging LARGE.
SOFT_LIMIT: summarize, release completed-phase text, stop repeated discovery, reuse fresh maps/commands/decisions, compact and split next unit. HARD_LIMIT approach: avoid new broad exploration, save goal/acceptance/decisions/evidence/risks/next tasks and stop at recoverable checkpoint; handoff rather than skip checks.
Measure input/output/cached/provider tokens when available; otherwise label context byte/character estimator explicitly ESTIMATE with formula and UNKNOWN exact billing. Record wall time, calls, retries, repeated reads, escalations and human interventions. Never represent an estimator as actual tokens or claim model cost savings from byte reduction alone.
Profiles: GREENFIELD_CONTEXT allows enough architecture context; MAINTENANCE_DELTA uses summary→scope→dependency map→affected files; HOTFIX_CRITICAL uses critical path with evidence retained; MIGRATION_COMPATIBILITY uses old/local/target comparisons; active migration prioritizes transition manifest→goal/phase→decisions/acceptance→affected files→baseline.
JIT reads only current relevant policy/Skill/protocol, normally 2–5 policies without hard cap. Updates read source manifest/version, transition, thin router, relevant protocol, current summary/custom rules then required runtime docs. Save raw logs as artifacts, use targeted searches/ranges, and invalidate cached facts on drift. Token savings never waive acceptance, verification, review or critical backfill.
