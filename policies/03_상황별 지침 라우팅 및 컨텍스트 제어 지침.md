# Instruction Router v1

## 상황별 AI 지침 선택 및 컨텍스트 제어 정책

Version: 1.0

---

# 0. 목적

이 문서는 프로젝트에 존재하는 여러 AI 개발 지침을 매 작업마다 전부 Context에 넣지 않고,

> 현재 작업에 필요한 지침만 선택적으로 활성화하고 필요하지 않은 지침은 로드하지 않도록 하는 최상위 Instruction Router

를 정의한다.

이 Router의 목적은 다음과 같다.

```text
Context 최소화
+
Token 사용량 최소화
+
규칙 충돌 최소화
+
현재 작업에 필요한 규칙 집중
+
장기 프로젝트의 지침 확장성 확보
```

새로운 Policy가 추가되어도 Core Prompt를 계속 비대하게 만들지 않는다.

---

# 1. 최상위 원칙

AI는 프로젝트에 존재하는 모든 지침서를 무조건 읽어서는 안 된다.

반드시:

```text
USER REQUEST
      ↓
TASK CLASSIFICATION
      ↓
RISK CLASSIFICATION
      ↓
CURRENT PHASE
      ↓
REQUIRED POLICIES
      ↓
MINIMAL POLICY LOAD
```

순서로 필요한 지침만 선택한다.

---

# 2. 핵심 규칙

> 필요한 지침만 읽는다.

> 이미 현재 Context에 충분히 반영된 지침을 중복 로드하지 않는다.

> 현재 작업과 관계없는 Policy는 읽지 않는다.

> 한 단계가 끝났다고 해서 이전 단계의 전체 Policy 내용을 계속 Working Context에 유지하지 않는다.

> 새로운 Policy가 추가되어도 Router의 분류 체계에 등록하는 것만으로 사용할 수 있어야 한다.

---

# 3. Router 자체는 얇게 유지한다

`Instruction Router`는 다른 지침 내용을 복제하지 않는다.

예:

금지:

```text
Router 안에
Codebase OS 전체 내용 삽입

Multi-Agent Harness 전체 내용 삽입

Verification 전체 내용 삽입
```

권장:

```text
조건
→ 어떤 Policy를 활성화할 것인지
→ 왜 필요한지
→ 언제 비활성화할지
```

만 정의한다.

---

# 4. 권장 Policy 구조

프로젝트에 다음과 같은 Policy Pack을 둘 수 있다.

```text

│

```

경로는 프로젝트 환경에 맞게 변경할 수 있다.

# 5. Policy 유형

Policy는 다음 세 종류로 구분한다.

## ALWAYS

항상 필요한 최소 규칙.

예:

```text
CORE
ROUTER
```

---

## CONDITIONAL

특정 조건일 때만 활성화.

예:

```text
Multi-Agent Harness

Security

Dependency

Migration

Checkpoint
```

---

## PHASE

특정 작업 단계에서만 활성화.

예:

```text
Bootstrap

Change Control

Verification

Handoff
```

---

# 6. 항상 활성화되는 것은 최소화한다

Always-On Context에는 가능한 한 다음만 둔다.

```text
CORE

+

ROUTER
```

CORE에는 매우 짧은 원칙만 둔다.

예:

```text
사용자 요청을 우선한다.

실제 코드를 Source of Truth로 사용한다.

필요한 지침만 Router를 통해 로드한다.

불필요한 Scope 확장을 하지 않는다.

검증하지 않은 내용을 완료로 보고하지 않는다.
```

상세 행동 규칙은 각 Policy가 담당한다.

# 7. 작업 시작 분류

사용자 요청을 받으면 먼저 작업 유형을 판단한다.

기본 Task Type:

```text
QUESTION

DISCOVERY

BUG_FIX

SMALL_CHANGE

FEATURE

REFACTOR

ARCHITECTURE

DEPENDENCY_CHANGE

DATABASE_CHANGE

INFRA_CHANGE

SECURITY_CHANGE

DOCUMENTATION

REVIEW

VERIFICATION

HANDOFF
```

복수 유형일 수 있다.

예:

```text
"로그인 기능을 리팩터링하면서
JWT 라이브러리도 교체해줘"
```

는:

```text
REFACTOR
+
DEPENDENCY_CHANGE
+
SECURITY_CHANGE
```

다.

---

# 8. 작업 단계 분류

현재 Phase를 확인한다.

```text
PROJECT_BOOTSTRAP

TASK_DISCOVERY

PLANNING

PRE_MODIFICATION

IMPLEMENTATION

MID_TASK

VERIFICATION

COMPLETION

HANDOFF
```

Router는 Task Type과 Phase를 함께 사용한다.

---

# 9. 위험도 분류

작업 Risk를 평가한다.

기본:

```text
LOW

MEDIUM

HIGH

CRITICAL
```

---

# 10. LOW Risk

예:

```text
텍스트 수정

단일 UI 표시 변경

지역적 CSS 변경

명확한 단일 Component 변경
```

필요 Policy를 최소화한다.

---

# 11. MEDIUM Risk

예:

```text
일반 Feature

일반 API 로직

공용 Hook

공용 Service

일반 Bug Fix
```

Codebase 및 Change Control을 활성화한다.

---

# 12. HIGH Risk

예:

```text
API Contract 변경

DB Schema 변경

Global State

공용 Library

Major Refactor

Infrastructure 변경
```

추가 Policy를 활성화한다.

---

# 13. CRITICAL Risk

예:

```text
Authentication

Authorization

IAM

Permission

Secret

Production Data Migration

Payment

Destructive Operation

Critical Infrastructure
```

비용 절감보다 Reliability를 우선한다.

```text
Dependency Policy
```


추가.

# 24. Security 변경

# 25. 외부 API 사용

다음이 감지되면 Dependency Policy를 활성화한다.

```text
새 SDK

외부 REST API

외부 GraphQL

새 Framework API

버전별 동작이 중요한 Library

Cloud Provider API

Third-party Service
```

모델 기억만으로 API를 추측하지 않도록 한다.

---

# 26. Multi-Agent Harness 활성화 조건

다음 중 하나 이상이면 Harness 활성화를 고려한다.

```text
관련 파일이 많음

서로 독립적인 조사 항목이 여러 개

Frontend/Backend/DB를 동시에 조사해야 함

Repository가 큼

병렬 탐색의 이점이 있음

전문 영역이 여러 개

고비용 Primary Model이 단순 작업을 많이 수행하게 됨
```

---

# 27. Multi-Agent Harness를 활성화하지 않는 경우

다음에는 일반적으로 활성화하지 않는다.

```text
1개 파일

명확한 위치

매우 단순한 수정

Delegation 설명 비용이 실제 작업보다 큼

Subagent 결과를 다시 해석하는 비용이 더 큼
```

---

# 28. Change Control 활성화 시점

실제 소스 변경 직전에 활성화한다.

즉:

```text
탐색 단계
```

에서는 반드시 필요하지 않다.

하지만:

```text
"이제 실제 파일을 수정한다."
```

가 되는 순간 로드한다.

---

# 29. Verification Policy 활성화 시점

다음 시점에 활성화한다.

```text
코드 수정 완료

또는

작업 완료 주장 직전
```

초기 탐색 단계부터 전체 Verification Policy를 Context에 유지할 필요는 없다.

---

# 30. Checkpoint 활성화 조건

다음 중 하나 이상이면 Checkpoint Policy를 활성화한다.

```text
작업 시간이 길어짐

많은 파일을 읽음

여러 Subagent 결과가 누적됨

Context가 커짐

여러 단계의 결정을 수행함

다음 작업 단계로 넘어감

모델/Agent 교체 가능성이 있음

중간 상태를 보존해야 함
```

---

# 31. Checkpoint 이후 Context 정리

Checkpoint를 생성하면 다음 정보는 압축하거나 제거할 수 있다.

```text
이미 해결된 탐색 과정

중복 Tool Output

실패한 후보 경로

오래된 가설

반복된 설명
```

유지:

```text
Goal

Success Criteria

Confirmed Facts

Decisions

Target Files

Changes

Verification State

Open Issues

Next Step
```

---

# 32. Handoff Policy 활성화 조건

다음 상황에서 활성화한다.

```text
다른 Agent가 이어받음

다음 Session으로 넘김

현재 작업을 중단하고 추후 재개

작업 완료 후 유지보수 정보를 남김
```

---

# 33. 작업 완료 후 Policy 해제

Policy는 한 번 읽었다고 영구적으로 활성화하지 않는다.

예:

```text
Migration 작업 종료
↓
Migration Policy 상세 Context 제거
```

남길 것은:

```text
실제 결정

Migration 결과

Verification 결과

Rollback 상태
```

정도다.

---

# 34. 최소 활성화 원칙

현재 작업이 다음으로 충분하다면:

```text
Codebase OS
+
Change Control
```

굳이:

```text
Security
Dependency
Migration
Harness
Architecture
```

까지 로드하지 않는다.

---

# 35. Policy Count 최소화

동시에 너무 많은 Policy가 선택되면 Router는 다시 평가한다.

질문:

```text
이 Policy가 현재 단계의 결정을 실제로 바꾸는가?
```

NO:

```text
로드하지 않는다.
```

---

# 36. Policy Conflict Resolution

여러 Policy가 서로 다른 지시를 줄 수 있다.

우선순위:

```text
1. 사용자 명시 요구

2. 안전 / 보안 제약

3. 현재 작업에 더 구체적인 Policy

4. 더 좁은 Scope의 Policy

5. CORE

6. 일반 권장사항
```

---

# 37. Specific Beats General

예:

CORE:

```text
가능하면 최소 변경
```

Migration Policy:

```text
Schema 변경에 필요한 Migration 파일을 반드시 추가
```

이면 Migration Policy를 따른다.

이는 필요한 Scope 확장이므로 최소 변경 원칙과 충돌하지 않는다.

---

# 38. Directory-Scoped Instruction

지원되는 환경에서는 디렉터리별 지침을 활용한다.

예:

```text
/

AGENTS.md
→ Core / Router


/src/

AGENTS.md
→ Frontend rules


/server/

AGENTS.md
→ Backend rules


/prisma/

AGENTS.md
→ DB / Migration rules


/tests/

AGENTS.md
→ Test rules
```

현재 수정 대상과 무관한 디렉터리 지침은 로드하지 않는다.

---

# 39. File Scope Awareness

Target File이:

```text
src/features/dashboard/...
```

에만 있다면 DB Policy를 자동 로드하지 않는다.

Target File이:

```text
prisma/schema.prisma
```

에 들어가면 Migration Policy를 활성화한다.

---

# 40. Event-Based Activation

Policy는 사용자 요청뿐 아니라 작업 중 발견된 사실에 의해 동적으로 활성화될 수 있다.

예:

초기:

```text
일반 Feature
```

진행 중:

```text
DB Schema 변경 필요 발견
```

그러면:

```text
Migration Policy
```

를 즉시 활성화한다.

---

# 41. Dynamic Deactivation

반대로 초기에는 필요할 것으로 생각했지만 실제로 필요하지 않은 Policy는 해제한다.

예:

```text
API 변경 예상

↓

탐색 결과 UI만 수정하면 됨

↓

Dependency/API 관련 Policy 해제
```

---

# 42. Risk Reclassification

작업 중 Risk가 변할 수 있다.

예:

초기:

```text
LOW
```

진행 중:

```text
Shared Auth Utility 수정 필요
```

발견.

즉시:

```text
CRITICAL 또는 HIGH
```

로 재분류하고 Security Policy를 활성화한다.

---

# 43. Router는 구현 내용을 결정하지 않는다

Router가 결정하는 것:

```text
어떤 Policy를 읽을 것인가?
```

Router가 결정하지 않는 것:

```text
실제 코드 구현 방식

Architecture 세부 설계

테스트 구현

모델 선택
```

해당 내용은 각 전문 Policy가 담당한다.

---

# 44. Router와 Multi-Agent Harness 차이

Instruction Router:

```text
어떤 지침이 필요한가?
```

Multi-Agent Harness:

```text
어떤 Agent 역할에게 어떤 작업을 맡길 것인가?
```

둘을 혼동하지 않는다.

---

# 45. Router와 Codebase OS 차이

Instruction Router:

```text
Codebase OS를 지금 읽어야 하는가?
```

Codebase OS:

```text
어떤 Feature와 코드를 찾아야 하는가?
```

---

# 46. Router와 Change Control 차이

Instruction Router:

```text
Change Control이 필요한 단계인가?
```

Change Control:

```text
실제로 어디까지 변경해도 되는가?
```

---

# 47. Router와 Verification 차이

Instruction Router:

```text
지금 완료 검증 단계인가?
```

Verification:

```text
무엇을 검증해야 완료인가?
```

---

# 48. Router 결과 형식

Router는 내부적으로 다음과 같이 결정하면 된다.

```text
TASK

Type:
FEATURE

Phase:
PRE_MODIFICATION

Risk:
MEDIUM


ACTIVE POLICIES

- Codebase OS
- Change Control


DEFERRED POLICIES

- Verification


NOT REQUIRED

- Migration
- Security
- Dependency
```

반드시 사용자에게 매번 이 전체 내용을 출력할 필요는 없다.

---

# 49. Router Output은 간결해야 한다

Router 자체가 Token 낭비 원인이 되어서는 안 된다.

내부 상태 예:

```json
{
  "type": ["FEATURE"],
  "phase": "PRE_MODIFICATION",
  "risk": "MEDIUM",
  "load": [
    "codebase-os",
    "change-control"
  ],
  "defer": [
    "verification"
  ]
}
```

# 50. Policy Registry

Policy가 많아지면 별도 Registry를 둔다.

예:

```json
{
  "codebase-os": {
    "path": ".ai/policies/codebase-os.md",
    "triggers": [
      "feature",
      "bug_fix",
      "refactor",
      "discovery"
    ]
  },

  "migration": {
    "path": ".ai/policies/migration-policy.md",
    "triggers": [
      "database_change",
      "infra_change"
    ]
  }
}
```

새 Policy 추가 시 Router 본문을 대규모 수정하지 않고 Registry 등록을 우선한다.

# 52. Router의 미래 확장성

목표:

```text
Policies = 5
```

에서:

```text
Policies = 50
```

으로 늘어나도 한 작업에서 실제 활성화되는 Policy는:

```text
2~5개
```

정도로 유지할 수 있어야 한다.

고정 숫자는 아니지만 최소화가 원칙이다.

# 54. Bootstrap 감지

다음 조건이라면 Bootstrap Policy를 활성화한다.

```text
새 Repository

AI 지침 체계 없음

Code Map 없음

Architecture 문서 없음

사용자가 Harness 구축을 요청
```

# 55. 기존 프로젝트에서는 Bootstrap 반복 금지

Codebase OS가 이미 구축된 프로젝트에서 새 작업마다 Bootstrap을 다시 실행하지 않는다.

# 56. 기존 Map 활용

Codebase Map이 최신이면:

```text
재구축 X
```

```text
기존 Map 활용 O
```

필요한 경우 Incremental Update만 수행한다.

---

# 57. Policy Loading Budget

Policy에도 Context Budget을 적용한다.

우선순위:

```text
현재 단계에 직접 필요한 Policy

>

다음 단계에서 곧 필요한 Policy

>

참고용 Policy
```

참고용 Policy는 가능하면 로드하지 않는다.

---

# 58. Just-In-Time Instruction Loading

Policy를 미리 전부 읽지 않는다.

예:

```text
탐색 단계

Codebase OS만
```

↓

```text
수정 직전

Change Control 추가
```

↓

```text
완료 직전

Verification 추가
```

이 방식을 기본으로 한다.

---

# 59. Just-In-Time Unloading

각 단계가 끝나면 상세 규칙을 Working Context에서 제거하거나 Checkpoint로 압축한다.

---

# 60. Context Pollution 방지

다음은 Context Pollution으로 간주한다.

```text
현재 작업과 관계없는 Security 규칙

이미 끝난 Bootstrap 절차

사용하지 않는 Framework 규칙

다른 디렉터리 전용 지침

동일 내용의 중복 Policy

과거 작업의 Raw Tool Output
```

---

# 61. Policy Summary Cache

이미 Policy를 읽고 현재 Session에서 해당 핵심 규칙이 충분히 유지되고 있다면 매번 전체 문서를 다시 읽지 않아도 된다.

단:

```text
작업 유형이 크게 바뀜

Risk가 상승

Policy Version이 변경

중요 규칙이 불확실
```

하면 원문을 다시 확인한다.

# 62. Policy Version

# 64. 단계 변경 감지


# 75. Mandatory Router Questions

비단순 작업에서 최소 다음을 판단한다.

# 76. 최종 압축 규칙

상시 Context에 전체 문서를 넣기 어렵다면 아래만 유지할 수 있다.

```text
INSTRUCTION ROUTER CORE

For every task:

1. Classify task type.
2. Identify current phase.
3. Assess risk.
4. Load only the policies that materially affect the current phase.
5. Do not preload policies for future phases.
6. Activate new policies dynamically when new risks or change types are discovered.
7. Deactivate policies that are no longer relevant.
8. Prefer just-in-time instruction loading.
9. Avoid duplicate or unrelated instructions in working context.
10. More specific and safety-critical policies override general policies.
11. Keep CORE and ROUTER thin; detailed behavior belongs in separate policy files.
12. At phase transitions, checkpoint essential state and discard obsolete instruction/context detail.
```

# 77. 최종 설계 원칙

이 Router의 성공은:

```text
지침이 몇 개 존재하는가
```

로 평가하지 않는다.

다음으로 평가한다.

```text
현재 작업에 필요한 지침만 활성화되는가?

중복 Context가 줄었는가?

지침 충돌이 줄었는가?

새 Policy 추가가 Core Prompt 비대화로 이어지지 않는가?

작업 단계가 바뀔 때 Policy도 자연스럽게 교체되는가?
```

---

# 78. Final Principle

> 모든 규칙을 항상 기억하게 만드는 것보다, 필요한 순간에 올바른 규칙을 불러오는 것이 더 중요하다.

따라서 이 프로젝트의 Instruction Architecture는:

```text
SMALL CORE

+

INSTRUCTION ROUTER

+

MODULAR POLICIES

+

JUST-IN-TIME LOADING

+

CHECKPOINT / COMPACTION
```

구조를 기본으로 한다.

새로운 지침은 가능한 한 CORE에 추가하지 않는다.

새 Policy Module로 추가하고 Router의 Trigger Registry에 등록한다.
