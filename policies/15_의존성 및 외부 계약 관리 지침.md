# ⑬ 의존성 및 외부 계약 관리 지침 v1

## Dependency & External Contract Policy

### 라이브러리·SDK·외부 API·서비스 계약·버전·호환성 변경 통제 지침

Version: 1.0

---

# 0. 목적

이 지침은 AI Agent가 기능 개발 과정에서 외부 라이브러리, SDK, API, 서비스, 프로토콜 또는 Package를 임의로 추가·변경하거나 존재하지 않는 기능을 추측하여 사용하는 것을 방지한다.

대표적인 실패:

```text
현재 설치 버전을 확인하지 않고
모델이 기억하는 최신 API 사용

존재하지 않는 함수 호출

기능 하나를 만들기 위해 불필요한 Package 추가

Package 업데이트 후 Breaking Change 발생

Lock File까지 광범위하게 변경

외부 API Response 구조를 추측

Deprecated API를 새 코드에 사용

API Rate Limit을 고려하지 않음

External Consumer 확인 없이 Contract 변경

Cloud SDK 버전과 공식 문서 버전 불일치

"최신 버전이 더 좋다"는 이유로 Upgrade
```

이를 방지하기 위해 기본 흐름을 다음으로 고정한다.

```text
NEED EXTERNAL CAPABILITY?

↓

EXISTING SOLUTION?

↓

CURRENT INSTALLED VERSION

↓

CURRENT PROJECT USAGE

↓

AUTHORITATIVE CONTRACT

↓

COMPATIBILITY

↓

CHANGE REALLY REQUIRED?

↓

MINIMUM CHANGE

↓

VERIFY

↓

LOCK / RECORD
```

# 1. 최상위 원칙

> 외부 Dependency의 기능은 기억으로 구현하지 않는다.

다음은 금지한다.

```text
"아마 이 함수가 있을 것이다."

"최신 버전이면 지원할 것이다."

"보통 이 Library는 이렇게 쓴다."

"예전에 사용해 봤으니 동일할 것이다."
```

현재 프로젝트에서 실제 사용하는 버전과 Contract를 확인한다.

---


# 4. 기본 변경값

Dependency 관련 기본값:

```text
DEPENDENCY_CHANGE = NO

DEPENDENCY_ADD = NO

DEPENDENCY_UPGRADE = NO

EXTERNAL_CONTRACT_CHANGE = NO
```

필요하다는 근거가 확인된 경우에만 YES로 전환한다.

# 5. Convenience Dependency 금지

다음 이유만으로 새 Package를 설치하지 않는다.

```text
코드가 조금 짧아짐

구현이 편함

```

# 6. Existing Capability First

새 Dependency 전에 확인한다.

```text
1. Standard Library로 가능한가?

2. 현재 프로젝트 Utility가 있는가?

3. 이미 설치된 Dependency가 지원하는가?

4. 기존 Pattern으로 충분한가?
```

---

# 7. 예

요구:

```text
날짜를 YYYY-MM-DD로 표시
```

현재 프로젝트에:

```text
dateUtils.formatDate()
```

가 있다면 새 날짜 Library를 설치하지 않는다.

---

# 8. Dependency Addition Gate

새 Dependency 추가 전에 최소 다음을 확인한다.

```text
왜 필요한가?

현재 방법으로 해결 불가능한가?

실제 유지보수 가치가 있는가?

기존 Package와 중복되는가?

Runtime/Build 영향은?

Lockfile 영향은?

License/Security 문제는?

현재 Requirement에 필요한가?
```

# 12. Runtime Compatibility

Library가 지원하는 Runtime과 현재 환경을 비교한다.

```text

Current:

```

---

# 13. Project Existing Usage

새 API 사용 전에 Repository에서 기존 사용 방식을 확인한다.

예:

```text
현재 프로젝트는
axios.create() 기반 apiClient를 사용
```

그런데 새 코드만:

```text
fetch()
```

를 직접 사용하지 않는다.

특별한 이유가 없다면 Convention을 따른다.

---

# 14. Existing Usage는 매우 강한 Evidence다

공식 문서의 여러 사용 방법 중 무엇을 선택해야 할지 모른다면 현재 프로젝트 Pattern을 우선한다.

---

# 15. 단 Existing Usage가 Deprecated일 수 있음

기존 코드가 존재한다고 자동으로 최선의 방법이라고 판단하지 않는다.

다음이 확인되면 별도 검토한다.

```text
Deprecated warning

Security issue

Unsupported API

Runtime incompatibility
```

# 16. Authoritative Source

AI Memory는 마지막 보조수단이다.

# 250. 압축 Core 지침

```text
의존성 및 외부 계약 관리 CORE

1. 외부 Library, SDK, API의 기능을 모델 기억만으로 사용하지 않는다.
2. 새로운 Dependency 추가·업데이트·삭제와 외부 Contract 변경의 기본값은 NO다.
3. 새 Dependency 전에 Standard Library, 기존 Utility, 이미 설치된 Package로 해결 가능한지 확인한다.
4. 실제 설치 Version과 Runtime Version을 먼저 확인한다.
5. 현재 프로젝트에서 동일 Dependency를 사용하는 기존 Pattern을 확인한다.
6. 공식 Documentation과 API Contract가 현재 설치 Version에 해당하는지 확인한다.
7. 확인되지 않은 함수, 옵션, Endpoint, Response Field 또는 CLI Flag를 만들어내지 않는다.
8. Dependency 변경에는 명확한 현재 Requirement 또는 검증된 기술적 필요성이 있어야 한다.
9. Consumer를 확인하지 않은 채 Public/API Contract를 변경하지 않는다.
10. Repository 내부 Consumer 확인과 외부 Consumer 부재 확인을 동일하게 취급하지 않는다.
11. Breaking Change, Semantic Change, Nullability, Error Contract, Authentication 및 Version을 명시적으로 검토한다.
12. Lockfile 변경을 실제 의도한 Dependency 변경과 비교하고 unrelated noise를 제거한다.
13. Dependency 변경으로 Runtime, Build Tool, Peer Dependency 또는 다른 Package까지 연쇄 변경되면 Scope와 Risk를 재평가한다.
14. 외부 API는 Request, Response, Error, Authentication, Rate Limit, Timeout, Retry 및 Side Effect 중 관련 항목을 실제 Contract에 따라 확인한다.
15. Mock 테스트 통과만으로 실제 External Contract가 검증되었다고 주장하지 않는다.
16. Dependency/API 변경에 따라 Build, Typecheck, Tests, Integration 및 Consumer Compatibility 검증 범위를 조정한다.
17. 예상하지 못한 Dependency 또는 외부 Contract 변경이 필요해지면 Drift Sentinel과 Replanning을 실행한다.
18. Authentication, Secret, Permission, Payment, destructive API 등 고위험 경계를 발견하면 해당 전문 Policy를 추가 활성화한다.
19. 중요한 External Fact는 freshness와 확인 범위를 보존하고, 검증하지 못한 부분은 UNVERIFIED로 남긴다.
20. 목표는 최신 Dependency를 사용하는 것이 아니라 현재 요구를 만족하는 가장 작고 검증된 Dependency/Contract 변경을 수행하는 것이다.
```

# 251. Final Principle

Dependency는 편리한 도구이지만 동시에 새로운 외부 신뢰 경계다.

따라서:

```text
NEED

↓

CHECK WHAT ALREADY EXISTS

↓

VERIFY VERSION

↓

VERIFY CONTRACT

↓

CHECK CONSUMERS

↓

CHANGE ONLY IF REQUIRED

↓

CHANGE MINIMALLY

↓

VERIFY COMPATIBILITY

↓

CLAIM ONLY VERIFIED BEHAVIOR
```

를 따른다.

가장 위험한 방식은:

```text
기억상 API가 있을 것 같다

↓

코드 작성

↓

Type Error

↓

Package Upgrade

↓

다른 Package도 Upgrade

↓

Build System 수정

↓

원래 Task보다 Upgrade 작업이 더 커짐
```

이다.

이 지침의 핵심은:

> **외부 기술을 많이 아는 AI가 아니라, 현재 프로젝트가 실제로 어떤 Version과 Contract를 사용하고 있는지 확인한 뒤 변경하는 AI를 만드는 것**

이다.

최종적으로:

> **Dependency는 필요해서 선택하고, Contract는 확인해서 사용하며, Version은 근거 없이 바꾸지 않는다.**

# 252. MCP와 Agent Skill도 Dependency다

MCP Server, Agent Skill, MCP 실행용 CLI, 원격 MCP Endpoint는 이 정책의 Dependency 또는 External Contract 범위에 포함한다.

현재 Agent에 Capability가 없다는 이유만으로 즉시 설치하지 않는다. 먼저 내장 도구, 프로젝트의 기존 Script/CLI/Package, `.ai/capability-lock.json`의 기존 설치를 확인한다.

# 253. Capability Acquisition

`TOOL_CAPABILITY_GAP`, `MCP_DISCOVERY`, `SKILL_DISCOVERY`, `PROJECT_TOOL_INSTALL`이 발생하면 `<HARNESS_ROOT>/workflows/CAPABILITY_ACQUISITION.md`를 JIT로 읽는다.

후보 검색은 다음 Catalog를 사용한다.

```text
catalogs/mcp-catalog.json
catalogs/skill-catalog.json
```

Catalog 전문을 일반 작업 Context에 preload하지 않는다.

# 254. Verified와 Discovery-only

- `verified`: Publisher와 설치 근거가 확인된 후보. 설치 시점에도 현재 공식 문서를 확인한다.
- `discovery_only`: Capability 검색용 후보. 이름만으로 설치할 수 없으며 공식 Registry·제작사 문서·Skills.sh에서 최신 Source를 재검증한다.

확인되지 않은 npm/Python Package명, URL, 실행 명령을 모델 기억으로 만들어내지 않는다.

# 255. Project-local Default

MCP/Skill 설치 Scope의 기본값은 현재 Project다. 전역 설치는 사용자가 명시했거나 Project-local 방식이 기술적으로 불가능하고 그 영향이 승인된 경우에만 별도 판단한다.

Project Lock에는 Source, 정확한 Version 또는 Content Hash, Reason, Status, Config Path만 기록하고 Secret 값은 기록하지 않는다.

# 256. Install과 Verify 분리

설치 명령 성공은 `installed` 또는 `configured`다. MCP handshake/Skill discovery와 안전한 Smoke Test가 확인돼야 `verified`다. Client 재시작이 필요하면 현재 Session에서 활성화됐다고 주장하지 않는다.
