# Plan Deviation & Replanning Policy v1

## 계획 이탈 판정·재계획·범위·위험 재평가 지침

Version: 1.0

---

# 0. 목적

이 Policy는 AI Agent가 개발 중 기존 계획과 다른 사실을 발견했을 때 다음과 같은 문제를 방지한다.

```text
계획이 틀렸는데도 그대로 밀어붙임

실제 행동만 바꾸고 Plan은 갱신하지 않음

새로운 API/DB 변경이 몰래 추가됨

계획 변경과 Scope Drift를 구분하지 못함

사용자가 왜 계획이 바뀌었는지 알 수 없음

Risk가 증가했지만 기존 Verification 수준 유지

Subagent가 각자 다른 새로운 계획으로 움직임

오래된 Plan이 Context에 남아 후속 Agent를 혼란시킴

계획 수정이 반복되며 목표 자체까지 흔들림
```

이를 방지하기 위해:

```text
ACTIVE PLAN

↓

NEW EVIDENCE

↓

PLAN STILL VALID?

├─ YES
│   ↓
│ CONTINUE
│
└─ NO
    ↓
DEVIATION CLASSIFICATION
    ↓
REPLAN NECESSARY?
    ↓
IMPACT ANALYSIS
    ↓
SPEC / SCOPE / RISK CHECK
    ↓
NEW PLAN
    ↓
PLAN LOCK
    ↓
CONTINUE EXECUTION
```

구조를 사용한다.

최종 목표:

> 계획에 집착하는 Agent도 아니고, 계획을 무시하는 Agent도 아닌, 새로운 사실에 따라 통제된 방식으로 계획을 수정하는 Agent를 만든다.

---

# 1. 최상위 원칙

> 계획은 증거보다 높은 권한을 가지지 않는다.

계획:

```text
Frontend만 수정하면 됨
```

실제 코드 확인:

```text
필요한 데이터가 Backend에서 제공되지 않음
```

이라면 기존 계획을 고집하지 않는다.

---

# 2. 그러나 Evidence 없는 Plan Change도 금지

다음은 계획 변경 근거가 아니다.

```text
이 방식이 더 좋아 보여서

새 Architecture가 더 세련돼서

코드를 보다 보니 바꾸고 싶어서

최신 기술을 사용하고 싶어서

리팩터링하면 깔끔할 것 같아서
```

---

# 3. Plan Deviation의 정의

현재 실제 상황이 기존 Active Plan의:

```text
Assumption

Step

Scope

Dependency

Risk

Implementation Path

Verification Plan
```

중 하나 이상과 의미 있게 달라진 상태.

---

# 4. Deviation과 Drift 차이

## PLAN DEVIATION

```text
새로운 사실 때문에
기존 계획이 더 이상 적절하지 않음
```

## EXECUTION DRIFT

```text
기존 계획은 여전히 유효하지만
Agent가 다른 작업을 하고 있음
```

---

# 5. 예

기존 Plan:

```text
UI Component만 수정
```

실제 발견:

```text
Root Cause가 Shared Hook에 있음
```

→ `PLAN DEVIATION`

반면:

```text
Shared Hook 구조가 마음에 안 들어
전체 Refactor
```

→ `DRIFT`

# 6. Replanning Trigger

다음 상황에서 이 Policy를 활성화한다.

```text
PLAN_ASSUMPTION_FALSE

NEW_REQUIRED_DEPENDENCY

ROOT_CAUSE_CHANGED

SCOPE_EXPANSION_REQUIRED

BOUNDARY_CROSSING_REQUIRED

API_CHANGE_REQUIRED

DB_CHANGE_REQUIRED

SECURITY_RISK_DISCOVERED

ARCHITECTURE_CONSTRAINT_DISCOVERED

EXPECTED_SCOPE_EXCEEDED

VERIFICATION_REVEALS_DESIGN_ERROR

BLOCKER_INVALIDATES_PLAN

USER_REQUIREMENT_CHANGED
```

---

# 7. 모든 작은 차이를 Replan하지 않는다

예:

```text
예상 Test file 이름이 다름

Helper 위치가 예상과 다름

Implementation 내부 순서 변경
```

처럼 결과·Scope·Risk에 영향을 주지 않는 차이는 Local Adjustment로 처리할 수 있다.

---

# 8. Deviation Classification

다음으로 분류한다.

```text
D0 — LOCAL ADJUSTMENT

D1 — EXECUTION ADJUSTMENT

D2 — SCOPE DEVIATION

D3 — ARCHITECTURAL DEVIATION

D4 — CRITICAL DEVIATION
```

---

# 9. D0 — Local Adjustment

사용자 결과, Scope, Risk에 영향 없음.

예:

```text
Helper 이름 변경

Test fixture 위치 변경

함수 내부 구현 순서 변경
```

Formal Replan 불필요.

---

# 10. D1 — Execution Adjustment

계획 단계 순서나 세부 방법이 변경되지만 Scope와 결과는 동일.

예:

원래:

```text
UI 수정
→ Test
```

실제:

```text
기존 Test를 먼저 수정하지 않고
현재 실패 재현부터 수행
→ UI 수정
→ Test
```

Plan을 간단히 갱신한다.

---

# 11. D2 — Scope Deviation

예상 변경 범위가 의미 있게 확대 또는 축소.

예:

```text
1 Component

↓

Component + Shared Hook + 3 Consumer Tests
```

Change Contract와 Verification 범위를 재평가한다.

---

# 12. D3 — Architectural Deviation

Layer나 구조가 바뀐다.

예:

```text
Frontend only
→ Backend 필요
```

```text
Local storage
→ DB persistence 필요
```

```text
Existing service
→ New service required
```

강한 Replan 대상.

---

# 13. D4 — Critical Deviation

다음 영역:

```text
Security

Permissions

Production destructive operation

Data loss risk

Billing

External contract breaking change

Irreversible migration
```

이 새롭게 등장.

즉시 현재 구현을 중단하고 관련 Risk Policy를 활성화한다.

---

# 14. Replan Decision Tree

```text
NEW FINDING

↓

Does it invalidate a material plan assumption?

NO
→ Continue

YES
↓

Can current goal still be achieved inside locked scope?

YES
→ Adjust plan

NO
↓

Does goal remain valid but scope must expand?

YES
→ Scope Replan

NO
↓

Does requirement itself need change?

YES
→ Spec / User Authority flow
```

---

# 15. Goal과 Plan을 구분한다

매우 중요하다.

Goal:

```text
야간 근무자가 없으면 "공석" 표시
```

Plan:

```text
Frontend에서 처리
```

Plan이 틀릴 수 있어도 Goal은 유지될 수 있다.

---

# 16. Replan은 Goal 변경 수단이 아니다

기술 문제가 있다고 사용자의 Goal을 쉽게 바꾸지 않는다.

먼저 경로를 변경할 수 있는지 본다.

---

# 17. Goal Change

Goal 자체가 변경되어야 한다면:

```text
Canonical Spec

+

User Authority
```

정책을 사용한다.

AI가 Replanning 이름으로 Goal을 바꾸지 않는다.

---

# 18. Plan Assumption Review

Replan 전에 기존 Plan이 어떤 가정 위에 있었는지 확인한다.

예:

```text
A-001:
API already exposes nightWorker state
```

검증:

```text
FALSE
```

이것이 Replan의 직접 원인이다.

---

# 19. Evidence Required

Material Replan에는 반드시 근거가 있어야 한다.

근거:

```text
Current source code

Test result

Runtime behavior

Actual API contract

DB schema

Security constraint

Locked new user requirement
```

---

# 20. "느낌"은 Evidence가 아니다

---

# 21. Root Cause Re-evaluation

Bug Fix 중 Root Cause가 바뀌면 Plan도 바뀔 수 있다.

예:

초기 추정:

```text
UI rendering bug
```

실제:

```text
Timezone conversion bug
```

기존 UI Patch Plan을 폐기한다.

---

# 22. Symptom Patch 방지

기존 Plan에 이미 시간을 썼다는 이유로 잘못된 방향을 유지하지 않는다.

---

# 23. Sunk Cost 금지

다음 사고를 피한다.

```text
이미 여기까지 구현했으니까
이 방법으로 끝내자.
```

Evidence가 Plan을 부정하면 되돌릴 수도 있어야 한다.

---

# 24. Replan 전에 현재 작업 정지

Material Deviation이 감지되면:

```text
PAUSE NEW EDITS
```

한다.

계획과 Scope를 재정렬한 뒤 계속한다.

---

# 25. 기존 변경을 즉시 전부 되돌릴 필요는 없다

먼저 어떤 변경이 새 Plan에서도 유효한지 평가한다.

---

# 26. Change Reuse Classification

기존 변경을:

```text
KEEP

ADAPT

REVERT

UNKNOWN
```

으로 분류할 수 있다.

---

# 27. KEEP

새 Plan에서도 필요.

---

# 28. ADAPT

일부 수정 후 재사용 가능.

---

# 29. REVERT

잘못된 Plan에만 필요했던 변경.

제거한다.

---

# 30. UNKNOWN

판단 전 추가 확인 필요.

---

# 35. Replan Status

```text
PROPOSED

APPROVED

NEEDS_USER_DECISION

BLOCKED

SUPERSEDED
```

---

# 36. PROPOSED

Agent가 새로운 Plan을 구성했지만 아직 필요한 Gate가 끝나지 않음.

---

# 37. APPROVED

현재 Authority 범위 내에서 확정.

---

# 38. NEEDS_USER_DECISION

Material User-owned 결정이 필요.

예:

```text
DB 변경 금지 Constraint를 풀어야 함
```

---

# 39. BLOCKED

새 Plan조차 수행할 조건이 없음.

---

# 40. SUPERSEDED

더 최신 Replan으로 대체됨.

---

# 41. Authority Check

Replanning은 다음 질문을 포함한다.

```text
이 변경을 AI가 스스로 결정해도 되는가?
```

---

# 42. AI가 자율 Replan 가능한 예

```text
Target helper 위치 변경

같은 Layer 내부에서 Root Cause 위치 변경

관련 Test 추가

내부 구현 순서 변경
```

---

# 43. 사용자 결정이 필요한 예

```text
새 Business Rule

API Contract breaking change

DB 저장 구조 변경

비용 증가

기존 금지사항 해제

Major Design Direction 변경

Scope 대폭 확대
```

---

# 44. User Authority Policy 연동

필요한 경우:

```text
Replan
↓
User Decision
↓
Spec Lock Update
↓
New Plan
```

순서를 따른다.

---

# 45. Spec Impact

Plan이 바뀌어도 Locked Spec이 그대로 유지될 수 있다.

예:

```text
Goal:
공석 표시

Scope:
Dashboard

```

구현 Path만:

```text
Frontend
→ API + Frontend
```

로 바뀔 수 있다.

---

# 46. 그러나 Locked Constraint와 충돌할 수 있다

Spec:

```text
API CHANGE = NO
```

새 Plan:

```text
API CHANGE required
```

Conflict.

AI가 몰래 Spec을 수정하지 않는다.

---

# 47. Spec Change Gate

```text
New Plan conflicts with locked spec?

YES
→ Spec Change / User Authority

NO
→ Continue Replan
```

---

# 48. Change Contract Update

Scope 변경 후 기존 Change Contract를 그대로 사용하지 않는다.

예:

Before:

```text
Primary:
TodayShiftCard

API:
NO
```

After:

```text
Primary:
TodayShiftCard
ShiftController
ShiftService

API:
YES
```

---

# 49. Risk Reclassification

Material Replan은 Risk를 다시 평가한다.

---

# 50. 예

Before:

```text
Frontend local
Risk: LOW
```

After:

```text
Shared API
6 Consumers
Risk: HIGH
```

Verification 수준도 달라져야 한다.

---

# 51. Verification Plan Update

Risk/Scope가 변했는데 기존 Test 계획을 그대로 사용하지 않는다.

---

# 52. Example

Before:

```text
Component test only
```

After API change:

```text
Component test

API contract test

Consumer regression

Build

Integration
```

필요 가능.

---

# 53. Policy Activation Update

Replan으로 새로운 영역이 생기면 Router가 추가 Policy를 활성화한다.

예:

```text
DB change discovered
→ Migration & Rollback Policy
```

```text
Permission change
→ Security Policy
```

---

# 54. Future Policy를 무조건 다 로드하지 않는다

현재 새 Scope에 필요한 것만 JIT activation.

---

# 55. Roadmap Impact

현재 Replan이 Milestone 순서까지 바꾸는지 확인한다.

---

# 56. Local Replan

현재 Task만 변경:

```text
Roadmap 영향 없음
```

---

# 57. Milestone Replan

선행관계 변경:

```text
Holiday Handling
→ Calendar Generation보다 먼저 필요
```

Roadmap 수정.

---

# 58. Phase-level Replan

예:

```text
기존:
Frontend 먼저

새 사실:
Core API foundation이 선행 필요
```

Phase/Milestone 순서 재설계 가능.

---

# 59. Project Goal 변경은 별개

Roadmap Replan을 이유로 North Star를 임의 변경하지 않는다.

---

# 60. Progress Ledger Update

Replan 발생 시 실제 상태도 갱신한다.

예:

```text
Original task:
IMPLEMENTING

↓

REPLAN

↓

Current:
PLANNING
```

으로 돌아갈 수 있다.

---

# 61. State Regression은 실패가 아니다

정확한 상태를 반영하는 것이 중요하다.

예:

```text
VERIFYING
→ IMPLEMENTING
```

Regression failure 발견 때문에 되돌아갈 수 있다.

---

# 62. State Machine은 단방향이 아니다

필요하면 이전 단계로 돌아간다.

---

# 63. Replan Loop

```text
PLAN

↓

IMPLEMENT

↓

NEW EVIDENCE

↓

REPLAN

↓

IMPLEMENT

↓

VERIFY
```

정상적인 개발 흐름일 수 있다.

---

# 64. 그러나 반복 Replan은 신호다

계획이 계속 틀린다면 원인을 분석한다.

---

# 65. Excessive Replanning

예:

```text
Plan v1
v2
v3
v4
v5
```

다음 가능성:

```text

```

# 66. Replanning Frequency는 Harness Evaluation 지표가 될 수 있다

# 67. Pre-implementation Discovery 강화

```

를 강화한다.

```

# 250. 압축 Core 지침

```text
PLAN DEVIATION / REPLANNING CORE

1. Treat the active plan as a working route, not an authority above verified evidence.
2. Do not change a material plan without new evidence, a new user requirement, or a verified risk/constraint.
3. Distinguish execution drift from valid replanning: drift is unnecessary departure; replanning is evidence-driven correction of an invalid or insufficient plan.
4. Preserve the user goal whenever possible even when the implementation path must change.
5. If a new plan conflicts with a locked requirement or user-owned constraint, do not silently modify the spec; invoke the appropriate authority/spec-change process.
6. Classify deviations by impact and avoid formal replanning for trivial internal adjustments.
7. For material replans, explicitly record the old plan, new evidence, why the old plan is invalid, the new plan, scope delta, risk delta, and concrete next step.
8. Pause additional material edits while a scope/architecture/risk replan is unresolved.
9. Re-evaluate change scope, risk, router policies, dependencies, and verification whenever a replan crosses a meaningful boundary.
10. Decide what existing work should be kept, adapted, or reverted rather than blindly discarding or preserving it.
11. Retire superseded plans so multiple contradictory active plans do not pollute context.
12. Subagents may suggest plan changes, but the orchestrator owns the canonical active plan.
13. Use delta replanning for small changes and full replanning only when most of the existing plan is invalid.
14. Do not let sunk cost force continuation of a plan disproven by evidence.
15. Avoid plan thrashing by defining explicit decision criteria and resolving conflicting evidence before switching strategies.
16. Replanning may expand, reduce, reorder, or replace scope; the objective is the smallest correct plan, not merely the smallest plan.
17. Update project state and checkpoint after material replanning so future agents resume from the new baseline.
18. Treat repeated planning errors, late replans, and false assumptions as Harness learning signals.
```

# 251. Final Principle

좋은 개발 시스템은:

```text
처음 만든 계획을 끝까지 지키는 시스템
```

이 아니다.

실제 개발에서는 새로운 사실이 계속 나온다.

따라서 좋은 시스템은:

```text
PLAN

↓

ACT

↓

OBSERVE REALITY

↓

PLAN STILL CORRECT?

├─ YES
│   ↓
│ CONTINUE
│
└─ NO
    ↓
UNDERSTAND WHY

↓

REPLAN

↓

RESET BASELINE

↓

CONTINUE
```

할 수 있어야 한다.

그러나 동시에:

```text
"계획은 바뀔 수 있으니까"
```

라는 이유로 아무 방향으로나 움직여서도 안 된다.

따라서 가장 중요한 구분은:

> **계획을 벗어난 것인가, 아니면 현실이 기존 계획을 무효화한 것인가?**

이다.

전자는 `Drift Sentinel`이 막고,

후자는 `Replanning Policy`가 통제한다.

최종적으로:

> **Goal은 가능한 한 안정적으로 유지하고, Route는 실제 Evidence에 따라 유연하게 바꾼다.**

```text
STABLE INTENT

+

ADAPTIVE PLAN

+

EXPLICIT REASON

+

UPDATED SCOPE

+

UPDATED VERIFICATION
```

이 조합이 장기 AI 개발에서 계획을 유연하게 유지하면서도 길을 잃지 않게 만드는 핵심이다.
