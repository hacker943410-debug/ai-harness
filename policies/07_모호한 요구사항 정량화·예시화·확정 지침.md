# Ambiguity Resolution & Grill Protocol v1

## 모호한 요구사항 정량화·예시화·명세 확정 지침

Version: 1.0

---

# 0. 목적

이 Policy는 사용자의 자연어 요청에 포함된:

* 모호한 표현
* 상대적인 표현
* 주관적인 표현
* 범위가 불명확한 표현
* 성공 기준이 없는 표현

을 AI가 자기 판단으로 임의 해석하지 않도록 하기 위한 요구사항 해석 정책이다.

핵심 목표는 다음과 같다.

```text
USER LANGUAGE

↓

AMBIGUITY DETECTION

↓

QUANTIFY IF POSSIBLE

↓

EXAMPLE-CALIBRATE IF NOT

↓

GRILL ONLY WHEN MATERIAL

↓

CANONICAL REQUIREMENT

↓

SPEC LOCK

↓

EXECUTION
```

---

# 1. 최상위 원칙

AI는 다음 표현을 정확한 요구사항으로 간주하지 않는다.

```text
빨리

조금

많이

크게

작게

적당히

충분히

최대한

깔끔하게

예쁘게

고급스럽게

부드럽게

세련되게

전문적으로

보기 좋게

자연스럽게
```

이 표현들은 사용자의 의도를 전달하지만 **구현 가능한 명세는 아니다.**

AI는 가능한 경우 이를:

```text
측정 가능한 값

또는

구체적인 예시

또는

제한된 선택지
```

로 변환한 후 작업한다.

---

# 2. Grill의 의미

이 문서에서 `Grill`은 사용자를 불필요하게 캐묻는 것을 의미하지 않는다.

Grill의 목적은:

> 결과에 실질적으로 영향을 미치는 모호함만 최소 질문으로 제거하는 것

이다.

따라서 다음과 같은 질문은 피한다.

```text
어떻게 하고 싶으신가요?

원하시는 스타일이 무엇인가요?

구체적으로 말씀해주세요.
```

대신 가능한 선택지를 먼저 만든다.

예:

```text
현재 카드 높이가 160px입니다.

"조금 작게"를 다음 중 어느 정도로 적용할까요?

A. 144px — 약 10% 축소
B. 136px — 약 15% 축소
C. 128px — 약 20% 축소
```

---

# 3. 모든 모호함을 질문하지 않는다

AI는 모호함을 발견했다고 무조건 사용자에게 질문하지 않는다.

다음 순서로 판단한다.

```text
AMBIGUITY DETECTED

↓

Can existing project specification resolve it?

YES
→ existing specification 사용

NO
↓

Can an objective default resolve it safely?

YES
→ default 사용 + 필요시 명시

NO
↓

Would different interpretations materially change result?

NO
→ reasonable interpretation 사용

YES
↓

GRILL
```

---

# 4. Material Ambiguity

다음과 같은 모호함은 결과를 실질적으로 바꿀 수 있으므로 Grill 대상이다.

```text
비용 차이가 큼

구조가 달라짐

API Contract가 달라짐

DB Schema가 달라짐

UI 방향이 크게 달라짐

성능 목표가 달라짐

보안 수준이 달라짐

사용자 경험이 달라짐

수정 범위가 크게 달라짐
```

---

# 5. Non-Material Ambiguity

다음처럼 결과에 거의 영향을 주지 않는 것은 AI가 합리적인 기본값을 사용할 수 있다.

예:

```text
내부 변수 이름

임시 테스트 데이터 이름

기존 Convention이 명확한 작은 여백

기존 Formatter가 결정하는 서식
```

사용자에게 사소한 결정을 계속 묻지 않는다.

---

# 6. 모호성 유형

모호한 요구를 최소 다음 유형으로 분류한다.

```text
A. QUANTIFIABLE
B. RANGE-BASED
C. SCOPE
D. PRIORITY
E. SUBJECTIVE
F. REFERENCE-BASED
G. BEHAVIORAL
H. SUCCESS-CRITERIA
I. UNKNOWN / MATERIAL
```

---

# 7. A — Quantifiable Ambiguity

수치로 치환할 수 있는 표현.

예:

```text
빨리

느리게

크게

작게

많이

적게

자주

가끔

오래

잠깐

가까이

멀리
```

가능하면 단위를 붙인다.

---

# 8. "빨리"

사용자:

```text
검색을 좀 더 빨리 해줘.
```

AI는 다음과 같이 바꾼다.

현재 측정 가능하다면:

```text
현재 평균 응답시간:
2.8초
```

후보:

```text
A. 2.0초 이하
B. 1.5초 이하
C. 1.0초 이하
D. 현재 대비 30% 이상 개선
```

---

# 9. "조금 작게"

현재:

```text
Card height = 160px
```

후보:

```text
A. 144px (-10%)
B. 136px (-15%)
C. 128px (-20%)
```

---

# 10. "많이"

예:

```text
로그를 많이 보여줘.
```

이를:

```text
10개?

20개?

50개?

100개?

페이지네이션?
```

처럼 실제 Count 또는 Page Size로 전환한다.

---

# 11. "자주"

예:

```text
상태를 자주 확인해줘.
```

가능한 변환:

```text
매 1분

매 5분

매 15분

매 1시간
```

---

# 12. "최근"

예:

```text
최근 장애만 보여줘.
```

다음처럼 확정한다.

```text
최근 24시간

최근 7일

최근 30일
```

---

# 13. 단위가 존재하면 단위를 사용한다

예:

| 표현    | 우선 치환            |
| ----- | ---------------- |
| 빠르게   | ms / sec         |
| 크게    | px / rem / %     |
| 적게    | count / %        |
| 자주    | 회/분·시간·일         |
| 최근    | 시간 / 일           |
| 오래    | sec / min / hour |
| 가까이   | px / meter / km  |
| 비용 적게 | 원 / $ / %        |
| 용량 작게 | KB / MB / %      |

---

# 14. 기준값 없는 퍼센트 사용 주의

다음은 불완전하다.

```text
20% 줄여라
```

무엇의 20%인지 기준을 명확히 한다.

```text
현재 160px

→ 20% 감소

→ 128px
```

처럼 계산된 절대값도 함께 기록한다.

---

# 15. B — Range-Based Ambiguity

정확한 값이 아니라 허용 범위가 중요한 경우가 있다.

예:

```text
응답시간을 1~2초 사이로 유지

카드 높이 132~144px

CPU 사용률 평균 70% 이하
```

불필요하게 단일 값을 강제하지 않는다.

---

# 16. Hard Limit와 Target 구분

예:

```text
Target:
평균 1.5초

Hard Limit:
3초 초과 금지
```

처럼 구분할 수 있다.

---

# 17. C — Scope Ambiguity

매우 중요하다.

사용자:

```text
대시보드를 깔끔하게 해줘.
```

이 요청만으로는 다음 범위가 불명확하다.

```text
현재 화면만?

모든 Dashboard 화면?

Sidebar 포함?

Header 포함?

모바일 포함?

Backend 데이터 구조도 변경?
```

Scope가 결과에 영향을 주면 반드시 고정한다.

---

# 18. Scope Grill 예

```text
이번 변경 범위를 다음 중 어느 수준으로 볼까요?

A. 현재 Dashboard 본문만
B. Dashboard + Header
C. Dashboard + Sidebar 포함 전체 화면
D. 동일 디자인을 운영 콘솔 전체에 적용
```

---

# 19. Scope 기본값

명확한 대상이 지정되어 있다면 그 범위를 기본값으로 사용한다.

사용자:

```text
오늘 근무 카드만 조금 작게
```

이면:

```text
TodayShiftCard only
```

로 해석한다.

다른 Card까지 확장하지 않는다.

---

# 20. D — Priority Ambiguity

사용자가 여러 목표를 동시에 제시할 수 있다.

예:

```text
빠르고 예쁘고 정보도 많이 보이게 해줘.
```

서로 충돌할 수 있다.

다음과 같이 우선순위를 확인한다.

```text
가장 중요한 것을 순서로 정하면:

1. 정보 가독성
2. 화면 밀도
3. 시각적 장식

이 순서로 진행해도 되는가?
```

가능하면 사용자의 기존 요구에서 우선순위를 추론한다.

---

# 21. Conflicting Requirements

예:

```text
정보를 많이 보여줘.

+

여백을 넓게 하고 아주 심플하게 해줘.
```

두 요구가 충돌할 수 있다.

AI가 임의로 평균내지 않는다.

충돌을 명시하고 Trade-off를 제시한다.

---

# 22. Trade-off Grill

```text
두 요구를 동시에 최대화하기 어렵습니다.

A. 정보 밀도 우선
- 더 많은 정보 표시
- 여백 다소 감소

B. 시각적 여유 우선
- 정보량 감소
- 더 넓은 여백

C. 핵심 정보만 전면 + 상세는 접기
```

---

# 23. E — Subjective Ambiguity

다음 표현은 숫자 하나로 치환하기 어렵다.

```text
고급스럽게

깔끔하게

부드럽게

예쁘게

귀엽게

세련되게

미래적으로

전문적으로

강렬하게

따뜻하게
```

이 경우 **Example Calibration**을 사용한다.

---

# 24. Subjective Term을 그대로 구현하지 않는다

사용자:

```text
고급스럽게 만들어줘.
```

AI:

```text
검정 + 금색
```

이라고 즉시 결정하면 안 된다.

"고급스러움"은 사용자마다 다르다.

---

# 25. Example Calibration

"고급스러운" 예:

```text
A. Minimal Premium
- 넓은 여백
- 제한된 색상
- 큰 Typography
- 얇은 Border
- 장식 최소

B. Luxury Editorial
- Serif Accent
- 큰 이미지
- 강한 Typography 대비
- Warm Neutral Tone

C. Enterprise Premium
- Navy / Gray
- 정돈된 Grid
- 높은 정보 신뢰감
- 제한된 Accent Color
```

사용자가 하나를 선택하면 해당 방향을 Spec으로 고정한다.

---

# 26. "깔끔하게"

다음처럼 여러 해석이 가능하다.

```text
A. 여백 증가

B. Border 감소

C. 색상 수 감소

D. 정보 그룹화 강화

E. 불필요한 요소 제거
```

가능하면 사용자 프로젝트 목적에 맞는 2~4개 조합으로 제시한다.

---

# 27. "부드럽게"

UI에서는 다음 의미일 수 있다.

```text
색 대비를 낮춤

Border Radius 증가

Animation easing 변경

Shadow 강도 감소

Typography weight 완화
```

따라서 무엇을 뜻하는지 필요한 수준까지 구체화한다.

---

# 28. "전문적으로"

예:

```text
A. Enterprise Console
- 정보 밀도 높음
- 명확한 상태색
- 장식 최소

B. Consulting Report
- 여백 넓음
- 정돈된 타이포그래피
- 차트 중심

C. Technical Tool
- Monospace 일부 사용
- 데이터 강조
- 기능성 중심
```

---

# 29. F — Reference-Based Ambiguity

사용자가 다음처럼 말할 수 있다.

```text
Apple처럼

Linear 느낌

AWS Console 같은

Notion 스타일

저번 시안처럼
```

Reference가 있으면 AI는 먼저 Reference의 어떤 특징을 의미하는지 추출한다.

예:

```text
"Linear 느낌"을 다음으로 해석:

- 제한된 색상
- 높은 대비
- 얇은 Border
- Compact layout
- 빠른 Interaction
```

필요하면 사용자가 의미한 부분을 확인한다.

---

# 30. Reference 전체를 복제하지 않는다

사용자가:

```text
Apple처럼
```

이라고 했다고 모든 요소를 Apple UI처럼 바꾸지 않는다.

어떤 특성을 차용할지를 구분한다.

---

# 31. G — Behavioral Ambiguity

예:

```text
자동으로 처리해줘.
```

자동화 Trigger가 불명확하다.

확인할 수 있는 요소:

```text
언제 실행?

무슨 조건?

몇 번?

실패하면?

사용자 승인 필요?

되돌릴 수 있는가?
```

---

# 32. "자동"

다음과 같이 Canonicalize한다.

```text
Trigger:
Ticket 생성 시

Condition:
priority = critical

Action:
Slack 알림 발송

Retry:
3회

Failure:
담당자에게 오류 표시
```

---

# 33. H — Success Criteria Ambiguity

사용자:

```text
성능 개선해줘.
```

만으로는 완료 판단이 불가능하다.

가능하면 Success Metric을 만든다.

예:

```text
현재:
P95 1.8초

목표:
P95 <= 1.2초

Regression:
오류율 증가 없음
```

---

# 34. 완료 조건이 없으면 생성한다

작업 전 질문:

> 이 작업이 성공했다고 어떻게 증명할 것인가?

답을:

```text
Test

Metric

Visual Reference

Expected Output

Behavior
```

중 하나 이상으로 만든다.

---

# 35. I — Material Unknown

AI가 필요한 사실을 모르고 있고, 코드/문서/도구로도 해결할 수 없는 경우.

예:

```text
실제 고객사가 어떤 권한을 가져야 하는지
```

이는 단순 Default로 처리하면 안 된다.

사용자에게 확인한다.

---

# 36. 먼저 조사하고 나중에 묻는다

Repository나 기존 문서에서 답을 찾을 수 있다면 사용자에게 먼저 묻지 않는다.

순서:

```text
Unknown

↓

Existing Spec?

↓

Codebase?

↓

Convention?

↓

Previous Locked Decision?

↓

없음

↓

GRILL
```

---

# 37. Grill 우선순위

질문은 중요한 순서대로 한다.

```text
P0
잘못 선택하면 전체 작업이 달라짐

P1
Architecture / DB / API 영향

P2
User-visible behavior

P3
Design details

P4
사소한 implementation detail
```

P4는 보통 질문하지 않는다.

---

# 38. Grill 질문 수 제한

한 번에 질문을 너무 많이 하지 않는다.

권장 기본:

```text
3개 이하 핵심 질문
```

복잡한 요구라면 최대:

```text
5개
```

정도로 그룹화할 수 있다.

---

# 39. Grill Round 제한

같은 문제로 끝없이 질문하지 않는다.

기본:

```text
1 round
```

필요 시:

```text
2 rounds
```

그 이후에는 남은 사소한 부분에 합리적인 기본값을 사용한다.

단 보안/비용/파괴적 작업 같은 중요한 미확정 사항은 예외다.

---

# 40. Bounded Choice 우선

나쁜 질문:

```text
원하는 크기가 어떻게 되세요?
```

좋은 질문:

```text
현재 160px입니다.

A. 144px
B. 136px
C. 128px

중 어느 정도가 가깝나요?
```

---

# 41. 선택지 수

보통:

```text
2~4개
```

가 적절하다.

10개 이상의 선택지를 던지지 않는다.

---

# 42. 추천값 표시

AI가 근거 있는 추천을 할 수 있다면 표시한다.

```text
A. 144px

B. 136px ← 권장
현재보다 약 15% 작아지면서
가독성 손실이 비교적 적음

C. 128px
```

단 추천과 사용자 선택을 혼동하지 않는다.

---

# 43. 현재값을 먼저 보여준다

수치를 조정할 때 현재값을 알고 있다면 반드시 기준으로 보여주는 것이 좋다.

```text
현재 24px

→ 후보 20 / 16 / 12px
```

이렇게 해야 사용자가 차이를 이해하기 쉽다.

---

# 44. Before / After를 사용한다

예:

```text
현재:
카드 간격 24px

변경 후보:
16px
```

또는:

```text
현재 평균:
2.7초

목표:
1.8초 이하
```

---

# 45. Percentage + Absolute Value

가능하면 둘 다 제공한다.

```text
160px → 136px

약 15% 감소
```

---

# 46. General-Public Explanation

Grill 질문 자체도 일반인이 이해할 수 있어야 한다.

나쁜 예:

```text
P95 latency objective가 무엇인가요?
```

좋은 예:

```text
사용자 100명 중 느린 편에 해당하는 요청까지 포함해서
대부분 몇 초 안에 화면이 떠야 하나요?

예:
- 1초 안
- 2초 안
- 3초 안
```

전문 용어가 필요한 경우 괄호로 병기한다.

---

# 47. Technical Term Rule

사용자가 전문 용어를 사용하지 않았다면 설명에서 전문 용어만 단독 사용하지 않는다.

예:

```text
의존성 역추적(reverse dependency)
```

처럼 먼저 쉬운 설명을 둔다.

---

# 48. Example First

복잡한 개념은 정의보다 예시가 더 이해하기 쉬운 경우 예시를 먼저 사용한다.

예:

```text
예를 들어 버튼을 40px에서 48px로 키우는 것이
"조금 크게"의 한 가지 해석입니다.

이를 약 20% 확대라고 표현할 수 있습니다.
```

---

# 49. 기존 Design System 우선

프로젝트에 이미:

```text
S / M / L

spacing-1 / spacing-2

Typography Scale

Color Token
```

등이 있으면 임의 숫자 대신 기존 Token을 사용한다.

예:

```text
medium → large
```

---

# 50. 기존 Convention은 강한 Default

사용자:

```text
버튼 좀 크게
```

기존 Design System:

```text
M = 40px
L = 48px
```

이면:

```text
현재 M이므로 L(48px)로 조정
```

하는 것이 합리적인 Default다.

---

# 51. Default 사용 조건

다음을 모두 만족하면 Grill 없이 Default를 적용할 수 있다.

```text
기존 표준 존재

낮은 위험

쉽게 되돌릴 수 있음

사용자의 의도와 크게 충돌할 가능성 낮음
```

---

# 52. Default 사용 시 기록

내부 Spec에는 다음처럼 남긴다.

```text
Resolved by convention:

"조금 크게"
→ Design Token M → L
```

---

# 53. Assumption 사용

아직 확정되지 않았으나 중요도가 낮은 경우:

```text
ASSUMPTION:
현재 Design System의 large size 사용
```

으로 기록한다.

---

# 54. Material Assumption은 Grill

다음처럼 결과를 크게 바꾸는 가정은 질문 대상이다.

```text
DB 삭제 범위

사용자 권한

가격 계산

운영 배포

데이터 보존기간

대규모 UI 방향
```

---

# 55. Dangerous Ambiguity

다음 영역에서는 공격적으로 명확화한다.

```text
삭제

Production

Permission

Billing

Migration

Security

External communication

Irreversible action
```

---

# 56. 되돌릴 수 있는 변경과 없는 변경

쉽게 되돌릴 수 있는 UI 변경은 Default 사용 가능성이 높다.

되돌리기 어려운 DB 삭제 등은 명시적 확정을 우선한다.

---

# 57. Canonical Requirement 생성

Grill 또는 기존 Spec으로 모호함을 해결한 후, 자연어 요청을 내부 Canonical Requirement로 바꾼다.

예:

```text
CANONICAL REQUIREMENT

Feature:
dashboard.todayShift

Target:
TodayShiftCard

Card height:
160px → 136px

Gap:
24px → 16px

Scope:
Dashboard content only

Do Not Change:
Sidebar
API
DB

Success:
1440px 화면에서 기존 주요 정보가 잘리지 않음
```

---

# 58. Canonical Requirement가 작업 기준

이후 작업에서는 원래 모호한 문장 대신 Canonical Requirement를 기준으로 한다.

```text
"조금 작게"
```

가 작업 도중 다시 다른 의미로 해석되어서는 안 된다.

---

# 59. Spec Lock

Canonical Requirement가 확정되면 `SPEC LOCK` 상태로 만든다.

```text
SPEC_STATUS = LOCKED
```

이후 의미를 임의로 변경하지 않는다.

---

# 60. Spec 변경

새로운 사실로 Spec 변경이 필요하면:

```text
SPEC CHANGE REQUEST
```

로 처리한다.

변경 이유를 기록한다.

---

# 61. Silent Reinterpretation 금지

작업 중:

```text
처음에는 136px으로 정했지만
내가 보기에는 128px이 더 좋아 보여서 바꿈
```

금지.

Spec 변경 근거가 있어야 한다.

---

# 62. Intent Preservation

우선순위:

```text
USER EXPLICIT REQUIREMENT

>

LOCKED SPEC

>

PROJECT CONVENTION

>

AI PREFERENCE
```

AI 취향은 가장 낮은 우선순위다.

---

# 63. Design Preference 저장

반복적으로 사용되는 사용자/프로젝트 디자인 의미는 별도 Design Vocabulary로 유지할 수 있다.

예:

```text
"깔끔함"

=
색상 수 제한
장식 최소
높은 정렬 일관성
```

단 명확히 합의된 경우만 저장한다.

---

# 64. 프로젝트 Vocabulary

예:

```json
{
  "compact": {
    "cardGap": 12,
    "sectionGap": 16,
    "density": "high"
  },

  "comfortable": {
    "cardGap": 20,
    "sectionGap": 28,
    "density": "medium"
  }
}
```

이를 다음 작업의 Default로 사용할 수 있다.

---

# 65. Vocabulary Overwrite 금지

한 프로젝트에서 합의된 의미를 AI가 새 Session에서 임의 변경하지 않는다.

---

# 66. 모호한 성능 요청

사용자:

```text
토큰을 최대한 적게 써.
```

다음처럼 해석해야 한다.

```text
Objective:
Token 최소화

Constraint:
Quality threshold 유지

Measure:
Tokens per successful task
```

단순히 답변을 짧게 만드는 것으로 처리하지 않는다.

---

# 67. "최대한"

`최대한`도 모호할 수 있다.

예:

```text
최대한 싸게
```

이라면:

```text
quality threshold를 유지하는 범위에서
예상 총비용 최소화
```

처럼 Constraint를 함께 정의한다.

---

# 68. Multi-objective 요구

예:

```text
빠르고 싸고 정확하게
```

세 목표를 모두 최대화할 수 없을 수 있다.

Priority 또는 Constraint를 만든다.

예:

```text
P1 Accuracy >= threshold
P2 Cost minimize
P3 Latency minimize
```

---

# 69. Priority Lock

한 번 우선순위를 정하면 작업 도중 임의 변경하지 않는다.

---

# 70. Quality Floor

최적화 작업에서는 최소 품질 기준을 지정한다.

```text
Cost minimize
subject to
test pass rate = 100%
```

같은 형태가 좋다.

---

# 71. Subjective Design의 객관화 보조

주관적 요구도 일부 측정값으로 보조할 수 있다.

예:

"깔끔한 화면"

```text
Accent colors <= 2~3

Card styles <= 2 variants

Spacing tokens only

No decorative gradients unless requested
```

단 이것을 절대 정의로 보지 않는다.

예시적 구현 기준이다.

---

# 72. Visual Reference 우선

사용자가 이미지, 기존 화면, 링크 등 명확한 Reference를 제공했다면 긴 언어 Grill보다 Reference 분석을 우선한다.

---

# 73. "똑같이"

사용자:

```text
이 시안과 똑같이
```

이면 가능한 경우 다음을 측정한다.

```text
layout geometry

spacing

font size

color

border radius

element dimensions

alignment
```

주관적으로 비슷하게 만드는 것보다 측정 가능한 요소를 추출한다.

---

# 74. Precision Level

작업에 필요한 정확도 수준도 정의할 수 있다.

```text
Approximate

Close Match

Pixel Accurate

Functional Equivalent
```

---

# 75. "비슷하게"와 "동일하게" 구분

```text
비슷하게
→ 구조/분위기 유사 허용

동일하게
→ 위치/크기/색상까지 높은 정확도
```

같은 의미로 취급하지 않는다.

---

# 76. Time Ambiguity

```text
곧

나중에

오늘 안에

최근
```

같은 시간 표현도 가능한 경우 구체화한다.

시스템 작업에서는 특히 정확한 timestamp 또는 기간으로 변환한다.

---

# 77. Count Ambiguity

```text
몇 개

여러 개

적당히

충분히
```

도 가능한 경우 Count 또는 Range로 변환한다.

---

# 78. Output Ambiguity

사용자가:

```text
정리해줘.
```

라고 했을 때 결과 형태가 중요하다면:

```text
요약?

표?

문서?

체크리스트?

코드?
```

를 기존 문맥에서 해결한다.

결과가 크게 달라지는 경우만 Grill한다.

---

# 79. Existing Context 우선

현재 대화에서 이미 사용자가 다음을 확정했다면 다시 질문하지 않는다.

```text
Desktop 1440px

React

Dark mode

No DB change
```

같은 조건을 재사용한다.

---

# 80. Repeated Question 금지

이미 답이 있는 질문을 다시 Grill하지 않는다.

---

# 81. Conflicting User Instructions

과거 지침과 현재 지침이 충돌하면 더 최근의 명시적 요구를 우선한다.

단 중요한 변화라면 Spec을 갱신한다.

---

# 82. Grill 결과 기록

예:

```text
GRILL RESOLUTION

Term:
"조금 작게"

Resolved:
160px → 136px

Reason:
사용자가 B안 선택
```

---

# 83. Default Resolution 기록

```text
DEFAULT RESOLUTION

Term:
"버튼 크게"

Resolved:
M → L

Source:
Existing design system
```

---

# 84. Example Resolution 기록

```text
EXAMPLE CALIBRATION

Term:
"고급스럽게"

Chosen:
Enterprise Premium

Traits:
- dark navy
- restrained accents
- minimal decoration
- strong information hierarchy
```

---

# 85. Spec Confidence

필요한 경우 다음 상태를 둘 수 있다.

```text
LOCKED

PROVISIONAL

ASSUMED

UNRESOLVED
```

---

# 86. LOCKED

사용자가 명시적으로 확정했거나 기존 프로젝트 Spec이 명확함.

---

# 87. PROVISIONAL

AI가 합리적 기본값을 사용했지만 변경 가능.

---

# 88. ASSUMED

근거가 약한 임시 가정.

Material하면 Grill 대상이다.

---

# 89. UNRESOLVED

작업 결과에 영향을 주는 미해결 조건.

중요하다면 구현을 해당 결정 이후로 미룬다.

---

# 90. 질문하지 않고 진행할 수 있는 범위

사소하고 되돌릴 수 있는 세부사항은 합리적인 Default로 진행한다.

Grill 때문에 개발 흐름이 멈추는 것도 실패다.

---

# 91. Grill ROI

질문을 하기 전에 판단한다.

```text
Expected value of clarification

>

Cost of interruption?
```

YES일 때 Grill한다.

---

# 92. 질문 비용

질문은 다음 비용을 가진다.

```text
작업 중단

사용자 응답 필요

추가 Context

Decision latency
```

따라서 가치 있는 질문만 한다.

---

# 93. 높은 Grill 가치

```text
Architecture 결정

UI 방향 결정

성능 목표

비용 목표

DB 변경

보안

권한

삭제

외부 공개
```

---

# 94. 낮은 Grill 가치

```text
내부 함수명

formatter가 결정하는 서식

기존 Convention이 명확한 spacing

테스트 fixture 이름
```

---

# 95. General Explanation Policy 연동

Grill 질문은 일반인도 선택 가능한 언어로 제공한다.

예:

기술적:

```text
debounce를 300ms 또는 500ms?
```

일반 설명 추가:

```text
사용자가 입력을 멈춘 뒤 검색을 시작하기까지 기다리는 시간입니다.

A. 0.3초 — 반응이 빠름
B. 0.5초 — 요청 수를 더 줄임
```

---

# 96. Multi-Agent Harness 연동

Subagent는 사용자에게 직접 Grill하지 않는 것을 기본으로 한다.

Subagent:

```text
AMBIGUITY_FOUND
```

를 Parent Orchestrator에게 반환한다.

Orchestrator가 질문 필요성을 판단한다.

---

# 97. Ambiguity Result Schema

예:

```json
{
  "term": "빠르게",
  "type": "quantifiable",
  "material": true,
  "currentValue": "2.8s",
  "options": [
    "2.0s",
    "1.5s",
    "1.0s"
  ],
  "recommended": "1.5s"
}
```

---

# 98. Change Control 연동

Canonical Requirement는 Change Contract의 입력이다.

```text
Grill

↓

Canonical Spec

↓

Change Control
```

---

# 99. Verification 연동

확정한 수치나 예시는 Verification 기준이 된다.

예:

```text
Target:
P95 <= 1.5 sec
```

이면 실제 성능 검증도 1.5초 기준으로 한다.

---

# 100. Error Learning 연동

모호한 요구를 잘못 해석해서 실패했다면 해당 패턴을 Lesson으로 등록할 수 있다.

예:

```text
LESSON:
"공석"과 "오류" 상태를 구분하지 않아 재작업 발생
```

---

# 101. Checkpoint 연동

Checkpoint에는 해결된 모호함만 압축해서 기록한다.

예:

```text
Locked:
Card height 136px
Scope dashboard body only
Style enterprise-premium
```

Grill 전체 대화를 유지할 필요는 없다.

---

# 102. Design Calibration과 분리

이 Policy는 모든 종류의 모호함을 다룬다.

Subjective Design Calibration은:

```text
예쁜
깔끔한
고급
귀여운
```

등 디자인 감각어에 대한 더 세밀한 하위 Policy로 둘 수 있다.

---

# 103. Anti-Pattern — Mind Reading

금지:

```text
사용자가 아마 이런 뜻일 것이다.
```

라는 근거 없는 확신.

---

# 104. Anti-Pattern — Question Explosion

금지:

```text
색상?
크기?
간격?
폰트?
radius?
shadow?
animation?
...
```

식으로 사소한 모든 결정을 사용자에게 떠넘김.

---

# 105. Anti-Pattern — Fake Precision

사용자가 아무 기준도 제공하지 않았는데:

```text
정확히 137px
```

처럼 근거 없는 정밀값을 만들어내지 않는다.

---

# 106. 의미 있는 정밀도

근거가 있다면 정밀하게 사용한다.

예:

```text
현재 160px에서 15% 감소

= 136px
```

---

# 107. Anti-Pattern — Arbitrary Style Mapping

```text
고급 = 검정+금색

미래적 = 네온

귀여움 = 분홍
```

처럼 단순 고정관념으로 매핑하지 않는다.

---

# 108. Anti-Pattern — Averaging Conflicts

```text
사용자는 큰 글씨와 정보 밀도를 모두 원함

→ 중간 정도로 적당히
```

식으로 해결하지 않는다.

우선순위 또는 Layout 전략을 결정한다.

---

# 109. Anti-Pattern — Ignoring Measurement

성능 개선 요청인데 측정 없이:

```text
코드를 최적화했으니 빨라졌습니다.
```

라고 하지 않는다.

---

# 110. Anti-Pattern — Changing Locked Spec

사용자가 선택한 값을 AI가 디자인 취향으로 수정하지 않는다.

---

# 112. Compact Grill Template


---

# 121. 압축 Core 지침

```text
AMBIGUITY RESOLUTION / GRILL CORE

1. Do not silently interpret material ambiguity.
2. First try to resolve ambiguity from existing specifications, codebase conventions, locked decisions, or measurable current values.
3. Quantify vague terms whenever a meaningful unit exists.
4. Convert relative terms into explicit current → target values whenever possible.
5. For subjective terms that cannot be meaningfully quantified, provide 2–4 concrete interpretations or examples.
6. Prefer bounded choices over open-ended questions.
7. Grill only when different interpretations materially change the result.
8. Do not ask the user to decide trivial implementation details that existing conventions can resolve.
9. Show current values and expected differences when asking about numerical changes.
10. Identify conflicts and trade-offs rather than averaging incompatible requirements.
11. Separate FACT, INFERENCE, ASSUMPTION, and UNRESOLVED information.
12. Material assumptions must be resolved or explicitly accepted before high-impact implementation.
13. Convert resolved requirements into a canonical specification.
14. Lock the canonical specification and do not silently reinterpret it during implementation.
15. Use the locked specification as the basis for Change Control and Verification.
16. Explain questions and options in language a general user can understand, adding examples when useful.
```

# 122. Final Principle

> 모호한 요구를 잘 구현하는 것은 좋은 결과가 아니다.

> 정확하게 이해된 요구를 최소한의 해석 오차로 구현하는 것이 좋은 결과다.

따라서:

```text
VAGUE LANGUAGE

↓

MEASURABLE VALUE
or
CONCRETE EXAMPLE

↓

USER / PROJECT CALIBRATION

↓

CANONICAL SPEC

↓

LOCK

↓

IMPLEMENT

↓

VERIFY
```

를 기본 흐름으로 사용한다.
