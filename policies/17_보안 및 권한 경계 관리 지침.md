# ⑮ 보안 및 권한 경계 관리 지침 v1

## Security & Permission Boundary Policy

### 인증·인가·권한·비밀정보·테넌트·관리자 기능·Production 접근 통제 지침

Version: 1.0

---

# 0. 목적

이 지침은 AI Agent가 인증, 권한, 관리자 기능, 비밀정보, 테넌트 경계, Production 접근과 같은 보안 영역을 일반 기능 수정처럼 처리하는 것을 방지한다.

대표적인 실패:

```text
버튼을 숨겼으니 권한 통제가 된 것으로 판단

Frontend 권한 검사만 구현

일반 사용자가 직접 API를 호출하면 Admin 기능 사용 가능

권한 오류를 해결하려고 Administrator 권한 부여

특정 기능 하나 때문에 wildcard 권한 추가

Request body의 userId / tenantId를 그대로 신뢰

다른 사용자의 Resource ID를 바꿔 접근 가능

다른 Tenant 데이터를 조회 가능

Secret/API Key를 코드에 하드코딩

Token을 로그에 출력

Checkpoint/Handoff/Lesson에 Secret 값 저장

CORS를 "*"로 열어 문제 해결

인증 Guard를 임시로 제거

403 오류를 없애기 위해 Authorization 자체를 우회

Test가 정상 사용자 Happy Path만 확인

"admin"이라는 Role 이름만 보고 모든 관리자 권한을 가정
```

이를 방지하기 위한 기본 흐름:

```text
SECURITY-SENSITIVE CHANGE

↓

WHO IS THE ACTOR?

↓

WHAT ACTION?

↓

WHICH RESOURCE?

↓

UNDER WHAT CONDITION?

↓

WHERE IS AUTHENTICATION ENFORCED?

↓

WHERE IS AUTHORIZATION ENFORCED?

↓

WHAT MUST BE ALLOWED?

↓

WHAT MUST BE DENIED?

↓

IMPLEMENT LEAST PRIVILEGE

↓

POSITIVE TEST

+

NEGATIVE TEST

↓

BOUNDARY VERIFICATION
```

최종 목표:

> 허용되어야 할 사용자가 기능을 사용할 수 있게 만드는 것뿐 아니라, 허용되지 않은 사용자·테넌트·리소스에서 같은 기능을 사용할 수 없다는 것까지 검증한다.

# 1. 최상위 원칙

보안이 필요한 기능은 다음 두 질문을 모두 통과해야 한다.

```text
허용된 사용자는 사용할 수 있는가?

+

허용되지 않은 사용자는 사용할 수 없는가?
```

첫 번째만 검증하면 보안 검증이 아니다.

# 3. Authentication

Authentication은:

> 사용자가 누구인지 확인하는 과정

이다.

쉽게:

```text
WHO ARE YOU?
```

---

# 4. Authorization

Authorization은:

> 인증된 사용자가 특정 작업을 수행할 권한이 있는지 확인하는 과정

이다.

쉽게:

```text
WHAT ARE YOU ALLOWED TO DO?
```

---

# 5. AuthN ≠ AuthZ

로그인했다고 모든 기능을 사용할 수 있는 것이 아니다.

```text
Authenticated User
```

와:

```text
Authorized User
```

를 구분한다.

---

# 6. Role

예:

```text
USER

OPERATOR

SUPERVISOR

ADMIN
```

Role은 권한 판단에 사용할 수 있다.

하지만 Role 이름만 보고 정확한 권한을 추측하지 않는다.

---

# 7. Permission

예:

```text

leave.approve

user.delete

billing.read
```

# 9. Actor-Action-Resource-Condition

보안 기능은 가능하면 다음 구조로 표현한다.

```text
ACTOR

↓

ACTION

↓

RESOURCE

↓

CONDITION
```

---

# 10. 예

```text
Actor:
Supervisor

Action:
Approve

Resource:
LeaveRequest

Condition:
same assigned site
```

즉:

```text
ALLOW(
  Supervisor,
  approve,
  LeaveRequest,
  sameSite
)
```

---

# 11. 이 모델이 중요한 이유

단순히:

```text
ADMIN ONLY
```

라고 하면 실제 경계가 불명확하다.

대신:

```text
누가

무엇을

어떤 Resource에

어떤 조건에서
```

할 수 있는지 명확히 해야 한다.

# 15. 보안 Risk

보안 관련 변경은 일반적으로 최소 MEDIUM 이상으로 취급한다.

```text
LOW

MEDIUM

HIGH

CRITICAL
```

---

# 16. LOW

Security에 직접 영향이 없는 UI 표시 정도.

예:

```text
권한에 따라 이미 계산된 상태를
화면에 아이콘으로 표시
```

단 실제 Authorization 로직은 변경하지 않을 때.

---

# 17. MEDIUM

예:

```text
일반적인 Role-based UI + API permission 수정
```

---

# 18. HIGH

예:

```text
Admin 기능

Tenant isolation

IAM

Secret handling

Permission model 변경

Public API exposure
```

---

# 19. CRITICAL

예:

```text
Production root/admin access

Cross-tenant data exposure

Authentication bypass

Private key exposure

Credential rotation incident

Mass destructive permission
```

---

# 20. Least Privilege

> 필요한 최소 권한만 부여한다.

다음 기준을 최소화한다.

```text

Action

Resource

Scope

Environment

Duration
```

```text
누가 새 권한을 받는가?

범위가 더 좁을 수 없는가?
```

# 43. Tenant Boundary

# 46. Authenticated Identity 기반

```text

```

와 실제 Resource ownership/tenant를 Server-side에서 비교한다.

---

# 47. userId 신뢰 금지

Request:

```json
{
  "userId": "admin"
}
```

라고 보냈다고 admin으로 처리하지 않는다.

---

# 48. Ownership Validation

Resource 접근 전:

```text
누가 이 Resource의 Owner인가?

현재 Actor와 어떤 관계인가?
```

를 확인한다.

---

# 49. Object-level Authorization

Endpoint 권한만으로 충분하지 않을 수 있다.

예:

```text
GET /documents/:id
```

모든 로그인 사용자가 Endpoint 접근 가능해도 해당 Document 권한을 별도 검증해야 한다.

---

# 50. Resource ID Enumeration

ID만 바꾸어 다른 사용자 Resource에 접근할 수 없는지 확인한다.

---

# 51. Fail Closed

보호 Resource에서 Identity/Authorization 판단에 실패하면 기본적으로 거부한다.

```text
UNKNOWN AUTH
→ DENY
```

---

# 52. 단 Fail Closed를 무작정 적용하지 않는다

Availability-critical 시스템에서는 실제 Design과 Requirement를 확인한다.

---

# 53. Authentication Failure

인증되지 않은 사용자.

일반적으로:

```text
401
```

이 사용될 수 있다.

Framework/API Contract에 맞춘다.

---

# 54. Authorization Failure

인증됐지만 권한 없음.

일반적으로:

```text
403
```

일 수 있다.

---

# 55. 401/403를 절대 법칙처럼 쓰지 않는다

Resource existence를 숨겨야 하는 API는:

```text
404
```

를 사용할 수도 있다.

현재 Security Design을 따른다.

---

# 56. Error Information Leakage

권한 거부 시 내부 정보를 과도하게 노출하지 않는다.

나쁜 예:

```text
User 123 exists but belongs to tenant B.
```

---

# 57. Sensitive Resource Existence

필요하면 Resource 존재 자체를 숨긴다.

# 320. 압축 Core 지침

```text
보안 및 권한 경계 관리 CORE

1. 인증, 인가, Permission, Secret, Tenant 경계, Production 접근은 일반 기능 변경보다 높은 위험 경계로 취급한다.
2. 모든 보호 작업은 Actor → Action → Resource → Condition → Enforcement Point로 정의한다.
3. UI Visibility는 Authorization이 아니며 민감한 접근은 권한 있는 Server/Data Layer에서 강제한다.
4. Permission Expansion, Auth Scheme Change, Tenant Boundary Change, Secret Storage Change, Public Exposure Change의 기본값은 NO다.
5. Least Privilege를 적용하여 필요한 최소 Actor, Action, Resource, Scope, Duration, Environment만 허용한다.
6. Permission 오류를 해결하기 위해 Guard를 제거하거나 Admin/Wildcard 권한을 광범위하게 부여하지 않는다.
7. Role 이름, 숨겨진 버튼, Client Code 또는 모델 기억만으로 실제 권한을 추측하지 않는다.
8. Caller가 전달한 userId, tenantId, ownerId만 신뢰하지 말고 Authenticated Identity와 Resource 경계를 Server-side에서 검증한다.
9. 보호 기능은 허용 Case뿐 아니라 unauthenticated, wrong-role, wrong-owner, cross-tenant 등 관련 Deny Case를 검증한다.
10. Horizontal 및 Vertical Privilege Escalation 가능성을 관련 기능에서 확인한다.
11. Secret 값은 Source, Client Bundle, Log, Prompt, Checkpoint, Handoff, Lesson, ADR, Snapshot에 저장하지 않는다.
12. Secret을 기록해야 할 경우 실제 값이 아닌 Secret Reference 이름만 보존한다.
13. 보호 Resource의 Identity/Authorization을 확정할 수 없으면 기본적으로 Fail Closed를 고려하되 시스템 Availability 요구와 실제 Architecture를 확인한다.
14. Sensitive Data는 기능에 필요한 최소 범위만 조회·전달·로그한다.
15. 인증/권한 Error를 성공, Empty State 또는 일반 데이터로 조용히 변환하지 않는다.
16. CORS, TLS, Auth Guard, Signature Validation 등 보안 경계를 단순 문제 해결을 위해 광범위하게 완화하지 않는다.
17. 새로운 Permission/Secret/IAM/Tenant/Production 경계를 발견하면 Scope와 Risk를 재평가하고 필요한 전문 Policy를 JIT 활성화한다.
18. 보안 변경은 Compile이나 Happy Path Test만으로 VERIFIED 처리하지 않으며 실제 Enforcement와 Negative Boundary Test가 필요하다.
19. Critical Security Failure는 첫 발생이라도 Test, Validator, CI, Architecture Guardrail 승격을 검토한다.
20. 보안 성공 주장은 실제로 검증한 Actor, Resource, Environment, Test 범위를 넘어서 확대하지 않는다.
```

# 321. Final Principle

보안에서 가장 위험한 사고방식은:

```text
정상 사용자가 된다

↓

완료
```

이다.

정확한 사고방식은:

```text
WHO SHOULD BE ALLOWED?

↓

WHAT EXACTLY MAY THEY DO?

↓

TO WHICH RESOURCE?

↓

UNDER WHICH CONDITION?

↓

WHERE IS IT ENFORCED?

↓

WHO MUST BE DENIED?

↓

CAN THEY BYPASS THE UI?

↓

CAN THEY ACCESS ANOTHER USER?

↓

CAN THEY ACCESS ANOTHER TENANT?

↓

DO THE NEGATIVE TESTS PASS?
```

이다.

가장 약한 보안:

```text
버튼을 숨긴다.
```

그보다 강한 보안:

```text
API에서 Role을 검사한다.
```

더 강한 보안:

```text
Actor + Resource + Tenant + Action을
공통 정책으로 검증한다.
```

더 강한 보안:

```text
허용/거부 경계를 자동 Test하고
CI에서 Regression을 차단한다.
```

가장 좋은 방향은:

```text
실수하기 어려운 Security Architecture
```

로 발전하는 것이다.

최종적으로:

> **보안 기능의 성공은 권한 있는 사람이 사용할 수 있다는 것으로 증명되지 않는다. 권한 없는 사람이 사용할 수 없다는 것까지 증명해야 한다.**

그리고:

> **권한 문제를 가장 넓은 권한으로 해결하는 것이 아니라, 가장 좁고 명확하게 검증된 권한으로 해결한다.**

# 306. MCP와 Agent Skill 보안 경계

MCP는 Filesystem, Browser, Repository, Database, Cloud, Payment, Device를 직접 조작할 수 있으므로 일반 문서 Dependency보다 높은 실행 권한을 가질 수 있다. Agent Skill은 Prompt 지침뿐 아니라 Script와 실행 명령을 포함할 수 있으므로 설치 전 전체 파일을 검토한다.

# 307. 설치 승인과 실행 승인 분리

다음은 서로 같은 승인이 아니다.

```text
Package 또는 Skill 설치
Credential 연결
Write Scope 부여
Production 접근
Destructive Action 실행
```

도구가 설치됐다는 이유만으로 나머지 권한을 획득했다고 간주하지 않는다.

# 308. MCP Credential

Project MCP 설정과 `.ai/mcp/desired.json`, `.ai/capability-lock.json`에는 환경변수명 또는 승인된 Secret Store 참조만 기록한다. Bearer Token, OAuth Refresh Token, API Key, Database Password 실제 값을 기록하지 않는다.

# 309. MCP 최소 Scope

가능하면 Read-only, 특정 Repository, 특정 Project, 특정 Database Schema, 특정 Filesystem Root부터 시작한다. 연결 오류를 해결하기 위해 Admin, wildcard Resource, 전체 Filesystem Root 또는 Production write를 자동 부여하지 않는다.
