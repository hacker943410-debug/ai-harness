# Progress Ledger & Project State Policy v1

## 프로젝트 실제 진행상태·완료근거·현재위치 관리 지침

Version: 1.0

---

# 0. 목적

이 Policy는 장기 개발 프로젝트에서 다음 문제가 발생하지 않도록 한다.

```text
뭐까지 만들었는지 모름

코드는 있는데 검증했는지 모름

완료했다고 생각했지만 일부 기능이 빠짐

다음 Session에서 같은 작업을 다시 조사

Roadmap에는 DONE인데 실제로는 Test 실패

현재 어느 Task에서 멈췄는지 모름

Blocker가 무엇이었는지 잊음

구현 완료와 검증 완료를 혼동

진행률을 근거 없이 추정

Agent마다 프로젝트 상태를 다르게 이해
```

이를 방지하기 위해:

```text
PLANNED STATE

와

ACTUAL VERIFIED STATE
```

를 분리한다.

핵심 흐름:

```text
ROADMAP
   ↓
EXPECTED PROGRESS
   ↓
EXECUTION
   ↓
EVIDENCE
   ↓
PROGRESS LEDGER
   ↓
CANONICAL PROJECT STATE
   ↓
NEXT STARTING POINT
```

최종 목표:

> 어떤 Agent나 Session이 프로젝트를 이어받아도, 다시 전체 프로젝트를 조사하지 않고 실제 현재 상태에서 바로 시작할 수 있게 한다.

---

# 1. 최상위 원칙

> 진행상태는 기억이나 느낌이 아니라 Evidence를 기준으로 기록한다.

예:

```text
"거의 끝난 것 같다."
```

는 Project State가 아니다.

대신:

```text
Implementation:
COMPLETE

Verification:
PARTIALLY_VERIFIED

Remaining:
Browser interaction test
```

처럼 기록한다.

---

# 2. Roadmap과 Progress의 차이

Roadmap:

```text
무엇을 만들 계획인가?
```

Progress Ledger:

```text
실제로 무엇이 완료되었는가?
```

둘은 반드시 분리한다.

---

# 3. 예

Roadmap:

```text
M2.2 Calendar Generation
Status: ACTIVE
```

Progress:

```text
Domain calculation:
DONE / VERIFIED

API:
DONE / VERIFIED

UI:
ACTIVE

E2E:
NOT STARTED
```

---

# 4. Plan ≠ Reality

계획했다고 완료된 것이 아니다.

```text
PLANNED
```

와:

```text
DONE
```

을 혼동하지 않는다.

---

# 5. Progress Ledger의 역할

다음 질문에 답해야 한다.

```text
무엇이 완료됐는가?

무엇이 검증됐는가?

무엇이 아직 남았는가?

무엇이 막혀 있는가?

어디에서 중단됐는가?

다음 작업은 정확히 무엇인가?

어떤 중요한 결정이 이미 내려졌는가?
```

# 16. IMPLEMENTED와 DONE을 분리한다

매우 중요하다.

```text
IMPLEMENTED
```

뜻:

> 코드 작성은 완료.

```text
DONE
```

뜻:

> 필요한 구현과 검증이 완료되어 Task 종료 가능.

# 213. 압축 Core 지침

```text
PROGRESS LEDGER / PROJECT STATE CORE

1. Separate planned state from actual evidenced state; roadmap intent is not proof of completion.
2. Maintain one canonical current project state containing the current phase, milestone, task, status, blocker, and concrete next step.
3. Separate implementation status from verification status. Code written does not equal DONE.
4. Mark milestones DONE only when required success criteria and verification are satisfied.
5. Use evidence such as tests, builds, runtime checks, visual verification, or explicit acceptance to support meaningful completion claims.
6. Keep progress records outcome-oriented; do not turn them into chronological tool logs or transcripts.
7. Use explicit states such as TODO, READY, ACTIVE, BLOCKED, IMPLEMENTED, VERIFIED, PARTIALLY_VERIFIED, DONE, DEFERRED, and CANCELLED as appropriate.
8. Record blockers with a concrete reason and what is required to resolve them.
9. Keep the next action concrete enough that another agent can continue without broad rediscovery.
10. Synchronize roadmap, progress ledger, current state, and verification when milestone status changes.
11. If documentation claims conflict with actual source code or verification evidence, reality wins and the project state must be repaired.
12. Avoid unsupported percentage-complete estimates; prefer milestone/component status unless weighted progress has an explicit basis.
13. Keep current and recent work detailed, but aggressively compress old completed work into brief verified summaries.
14. Preserve current state across checkpoints, interruptions, handoffs, and session changes.
15. The orchestrator owns canonical project state; subagents return evidence and suggested state updates rather than independently redefining project status.
16. Resolved blockers, superseded states, and obsolete details should be removed from the active working state.
17. At any time the state system should answer: Where are we? What is actually done? What remains? What is blocked? What happens next?
```

# 214. Final Principle

Roadmap이 다음을 알려준다면:

```text
우리가 어디로 가야 하는가?
```

Progress Ledger는 다음을 알려준다.

```text
우리가 실제로 어디까지 왔는가?
```

그리고 Current State는 다음을 알려준다.

```text
지금 정확히 어디에 서 있는가?
```

따라서 장기 프로젝트는 항상:

```text
ROADMAP
    ↓
PLAN
    ↓
EXECUTION
    ↓
EVIDENCE
    ↓
PROGRESS
    ↓
CURRENT STATE
    ↓
NEXT ACTION
```

으로 연결되어야 한다.

가장 중요한 원칙은:

> **완료했다고 기억하는 것과 완료됐다는 증거가 있는 것은 다르다.**

좋은 Project State는 AI에게 모든 과거 작업을 기억시키는 것이 아니다.

> **과거를 다시 기억할 필요가 없도록 현재 상태를 정확하게 압축해 두는 것**이다.
