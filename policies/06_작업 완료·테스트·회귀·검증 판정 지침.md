# Verification Gate Policy v1

## AI 작업 완료·테스트·회귀·검증 상태 판정 지침

Version: 1.0

---

# 0. 목적

이 Policy는 AI Agent가 코드 수정 또는 기능 구현을 완료한 뒤,

> "코드를 작성했다"

를

> "작업이 완료되었다"

와 동일하게 취급하지 않도록 하기 위한 최종 품질 Gate다.

AI는 실제 증거를 통해 다음을 확인해야 한다.

```text
요구사항 충족

+

코드 유효성

+

관련 테스트 통과

+

기존 기능 보존

+

변경 범위 검증

+

미확인 영역 식별
```

그 후에만 완료 상태를 선언한다.

---

# 1. 핵심 원칙

> Completion is evidence-based.

AI의 판단이나 코드 모양만으로 완료를 선언하지 않는다.

완료는 다음 근거 중 필요한 수준을 실제로 확인한 결과여야 한다.

```text
Success Criteria

Static Analysis

Type Check

Lint

Unit Test

Feature Test

Integration Test

Build

Runtime Verification

Regression Check

Diff Review
```

---

# 2. 적용 시점

Instruction Router는 다음 단계에서 이 Policy를 활성화한다.

```text
IMPLEMENTATION
      ↓
IMPLEMENTATION COMPLETE
      ↓
VERIFICATION
      ↑
Verification Policy 활성화
      ↓
COMPLETION
```

단순 탐색 단계에서는 전체 Policy를 로드하지 않는다.

---

# 3. Verification은 구현과 분리한다

작업 흐름:

```text
IMPLEMENT

↓

STOP EDITING

↓

VERIFY

↓

FAIL?
 ├─ YES → REWORK
 └─ NO  → COMPLETION
```

테스트가 실패하면 계속 코드를 임의로 덧붙이는 대신 원인을 다시 분석한다.

---

# 4. Success Criteria가 Verification의 기준이다

Verification의 첫 번째 입력은 테스트가 아니라 **Success Criteria**다.

예:

사용자 요청:

```text
야간 근무자가 없으면 "공석"으로 표시
```

Success Criteria:

```text
1. 야간 근무자 없음 → "공석"

2. 야간 근무자 있음 → 기존 이름 표시

3. 주간 근무 영역 영향 없음

4. API Contract 변경 없음

5. 기존 Dashboard 동작 유지
```

Verification은 이 조건들이 충족되었는지 확인해야 한다.

---

# 5. Verification Plan

검증 전에 내부적으로 다음을 정의한다.

```text
Feature:

Risk:

Success Criteria:

Changed Files:

Affected Features:

Required Checks:

Optional Checks:

Unavailable Checks:
```

---

# 6. Risk 기반 검증

모든 작업에 동일한 검증 비용을 사용하지 않는다.

검증 강도는 Change Risk에 비례한다.

기본:

```text
LOW
→ Compact Verification

MEDIUM
→ Standard Verification

HIGH
→ Enhanced Verification

CRITICAL
→ Critical Verification
```

---

# 7. LOW Risk Verification

예:

```text
문구 변경

지역적 CSS

단일 UI 조건
```

일반적으로 확인:

```text
Success Criteria

Affected test 또는 직접 검증

Type/Lint 영향

Final Diff
```

전체 시스템 Integration Test까지 무조건 실행할 필요는 없다.

---

# 8. MEDIUM Risk Verification

예:

```text
일반 Feature

일반 Bug Fix

공용 Hook

일반 Service 변경
```

확인:

```text
Success Criteria

Type Check

Relevant Unit Tests

Feature Tests

Affected Integration Test

Build 또는 해당 Package Build

Diff Review
```

---

# 9. HIGH Risk Verification

예:

```text
API Contract

DB Schema

Global Store

Major Refactor

Infrastructure
```

확인 범위를 확대한다.

```text
Static Analysis

Type Check

Relevant Unit Tests

Integration Tests

Affected Package/Module Tests

Build

Migration Validation

Backward Compatibility

Regression Check

Independent Review 고려
```

---

# 10. CRITICAL Verification

예:

```text
Authentication

Authorization

IAM

Payment

Production Data

Security Boundary

Critical Infrastructure
```

정확성을 비용보다 우선한다.

가능하면:

```text
Enhanced Tests

Independent Review

Security-specific verification

Rollback validation

Runtime/Staging verification

Explicit unverified areas
```

까지 수행한다.

---

# 11. Verification Ladder

기본 검증 순서:

```text
1. SOURCE VALIDATION

2. STATIC ANALYSIS

3. TYPE CHECK

4. LINT

5. UNIT TEST

6. FEATURE TEST

7. INTEGRATION TEST

8. BUILD

9. RUNTIME / UI

10. REGRESSION

11. FINAL DIFF
```

모든 작업에서 전부 수행해야 한다는 의미는 아니다.

현재 Risk와 변경 범위에 맞게 선택한다.

---

# 12. Deterministic Verification First

검증할 수 있는 것을 LLM 추측으로 검증하지 않는다.

금지:

```text
"타입 에러는 없을 것 같다."

"빌드도 잘 될 것이다."

"테스트도 통과할 것 같다."
```

가능하면 실제 도구를 실행한다.

```text
Compiler

Type checker

Linter

Test runner

Build system

Schema validator

Migration checker

Browser automation
```

---

# 13. Test 실행 순서

테스트는 가장 좁은 범위부터 시작한다.

```text
Target Unit Test

↓

Feature Tests

↓

Related Integration Tests

↓

Affected Package Tests

↓

Full Test Suite
```

작은 수정에서 처음부터 전체 Test Suite를 실행해 불필요한 비용을 발생시키지 않는다.

---

# 14. Test Expansion Rule

좁은 테스트가 통과했더라도 변경 영향도가 넓다면 범위를 확대한다.

예:

```text
Shared Utility 수정
```

이면 관련 Consumer Test도 실행한다.

---

# 15. Affected Tests

Codebase OS의 Impact Map / Test Map을 활용할 수 있다.

```text
Target Symbol

↓

Affected Features

↓

Related Tests
```

전체 테스트를 무작정 검색하지 않는다.

---

# 16. Test Intent

테스트는 구현 세부사항이 아니라 사용자 의도를 검증해야 한다.

예:

나쁜 테스트:

```text
render 함수가 한 번 호출됨
```

좋은 테스트:

```text
야간 근무자가 없으면 화면에 "공석" 표시
```

---

# 17. Positive Case

새 기능이 정상 입력에서 작동하는지 확인한다.

예:

```text
nightWorker = 홍길동

→ 홍길동 표시
```

---

# 18. Negative / Empty Case

특히 Bug Fix 및 상태 처리에서는 비정상 또는 Empty Case도 검증한다.

```text
nightWorker = null

→ 공석
```

---

# 19. Error Case

Empty State와 Error State를 구분한다.

예:

```text
API success + no worker
→ 공석
```

```text
API request failed
→ Error behavior
```

API 오류를 "공석"으로 처리해서는 안 된다면 이를 테스트한다.

---

# 20. Edge Case

현재 변경과 직접 관련된 Edge Case만 추가한다.

모든 상상 가능한 Edge Case를 무한히 테스트하지 않는다.

---

# 21. Regression Test

Bug Fix라면 가능하면 다음 패턴을 따른다.

```text
Bug reproduction

↓

Test fails

↓

Minimal fix

↓

Same test passes
```

이렇게 하면 실제 Root Cause가 해결되었는지 근거가 생긴다.

---

# 22. 기존 Test 수정 주의

기존 테스트가 실패한다고 자동으로 기대값을 수정하지 않는다.

먼저 판단:

```text
기존 Behavior가 의도적으로 변경되었는가?

기존 Test가 잘못된 것인가?

새 구현이 잘못된 것인가?
```

---

# 23. Never Delete Tests to Pass

금지:

```text
Test 실패

↓

Test 삭제
```

또는:

```text
skip

only

disable
```

로 성공 처리.

---

# 24. No Assertion Weakening

금지:

기존:

```text
expect(result).toEqual(expected)
```

실패하자:

```text
expect(result).toBeTruthy()
```

처럼 검증을 약화해서 통과시키는 것.

---

# 25. Type Error 우회 금지

금지:

```text
any

@ts-ignore

@ts-expect-error

disable type checking
```

로 실제 문제를 숨기는 것.

단 기존 프로젝트에서 명시적으로 허용된 경우는 별도 판단한다.

---

# 26. Lint 우회 금지

금지:

```text
eslint-disable
```

를 단순히 테스트 통과 목적으로 추가.

실제 예외가 필요한 경우 이유가 있어야 한다.

---

# 27. Error Swallowing 금지

금지:

```text
catch {}
```

또는:

```text
catch {
  return null
}
```

로 오류를 숨겨 테스트를 통과시키는 것.

---

# 28. Build Verification

다음 종류의 변경은 Build 확인 가치가 높다.

```text
Type 변경

Import 변경

Dependency 변경

Build config 변경

Public API 변경

Shared Component 변경
```

가능하면 실제 Build를 수행한다.

---

# 29. Runtime Verification

정적 검사만으로 확인하기 어려운 기능은 실제 실행을 검증한다.

예:

```text
UI Interaction

Routing

Browser rendering

Network flow

Runtime permission

Async behavior
```

---

# 30. UI Verification

UI 변경 시 가능하면 확인:

```text
정상 상태

Empty state

Error state

Responsive 영향

기존 주요 interaction
```

작업 범위에 맞게 선택한다.

---

# 31. API Verification

API 변경 시 확인:

```text
HTTP Method

Path

Request

Response

Status code

Validation

Auth

Permission

Consumers
```

---

# 32. API Compatibility

기존 Consumer가 있는 API라면 다음을 확인한다.

```text
Required Field 삭제?

Type 변경?

Nullable 변경?

Status Code 변경?

Error Structure 변경?
```

의도하지 않은 Contract break를 막는다.

---

# 33. Database Verification

DB 변경 시 최소:

```text
Schema valid

Migration generated

Migration applies

Existing data compatibility

Application type alignment

Rollback possibility
```

를 확인한다.

Migration Policy와 연동한다.

---

# 34. Migration 적용 성공만으로 완료 아님

```text
migration runs
```

외에도:

```text
existing application works
```

를 확인해야 한다.

---

# 35. Dependency Verification

Dependency 변경 시:

```text
Install 상태

Version

Lock File

Build

Affected imports

Runtime compatibility

License/security policy if applicable
```

를 확인한다.

Dependency Policy와 연동한다.

---

# 36. Security Verification

Security Change에서는 일반 테스트만으로 충분하지 않을 수 있다.

예:

```text
Authorized user
→ allowed

Unauthorized user
→ denied

Unauthenticated user
→ denied
```

같이 반대 조건까지 확인한다.

---

# 37. Authorization은 Positive + Negative 검증

예:

```text
Admin → 200

Normal User → 403

Anonymous → 401
```

같은 방식으로 권한 경계를 검증한다.

---

# 38. Regression Boundary

Change Control의 `MUST PRESERVE` 항목을 Verification 입력으로 사용한다.

예:

```text
Must Preserve:

주간 근무자 표시

기존 야간 근무자 표시

Dashboard layout
```

각 항목이 유지되는지 확인한다.

---

# 39. Changed Behavior와 Preserved Behavior

검증 결과를 다음 두 영역으로 생각한다.

```text
Changed Behavior

+

Preserved Behavior
```

새 기능만 맞고 기존 기능이 깨지면 완료가 아니다.

---

# 40. Diff Verification

최종 Diff 자체도 검증 대상이다.

확인:

```text
Unexpected files

Temporary debug code

Unrelated formatting

Unrelated rename

Secrets

Commented-out blocks

Config changes

Generated artifacts
```

---

# 41. Final Diff와 Change Contract 비교

```text
Expected Diff

vs

Actual Diff
```

를 비교한다.

예상하지 않은 변경이 있으면 이유를 확인한다.

---

# 42. Scope Regression

Verification 단계에서:

```text
기능은 맞지만
불필요한 파일 8개가 변경
```

이면 Change Control 실패로 다시 보낸다.

---

# 43. Verification Evidence

각 검증 결과는 가능한 한 증거를 갖는다.

예:

```text
Type Check:
PASS
command: npm run typecheck
```

```text
Unit:
PASS
TodayShiftCard.test.tsx
```

---

# 44. Raw Log는 유지하지 않는다

Checkpoint에는:

```text
npm test 전체 500줄
```

을 넣지 않는다.

대신:

```text
Test:
PASS
8 passed / 0 failed
```

정도로 압축한다.

필요한 실패 메시지만 유지한다.

---

# 45. Verification State

다음 상태를 표준으로 사용한다.

```text
VERIFIED

PARTIALLY_VERIFIED

UNVERIFIED

BLOCKED
```

---

# 46. VERIFIED

필요한 검증이 모두 수행되고 Success Criteria를 충족한 상태.

예:

```text
Implementation: PASS
Relevant tests: PASS
Build: PASS
Regression: PASS
```

---

# 47. PARTIALLY_VERIFIED

주요 검증은 성공했지만 일부 검증을 수행하지 못한 상태.

예:

```text
Unit Test:
PASS

Build:
PASS

Browser Runtime:
NOT RUN
```

최종:

```text
PARTIALLY_VERIFIED
```

---

# 48. UNVERIFIED

코드는 작성했지만 충분한 검증을 수행하지 못함.

예:

```text
Test runner unavailable
```

이 경우:

```text
완료되었습니다
```

라고 단정하지 않는다.

---

# 49. BLOCKED

검증에 필요한 조건이 없어 진행할 수 없는 상태.

예:

```text
필수 DB unavailable

required credentials unavailable

external dependency down
```

---

# 50. Implementation Status와 Verification Status 분리

예:

```text
Implementation:
COMPLETE

Verification:
PARTIALLY_VERIFIED
```

이 둘을 혼동하지 않는다.

---

# 51. No Fake Success

다음은 VERIFIED가 아니다.

```text
코드가 그럴듯함

Syntax가 맞아 보임

Test를 작성했지만 실행하지 않음

Build는 안 했지만 될 것 같음

UI는 보지 않았지만 맞을 것 같음
```

---

# 52. Fail Loud

미확인 영역을 숨기지 않는다.

예:

```text
관련 Unit Test는 통과했습니다.

전체 E2E 테스트는 실행하지 않았으므로
전체 시스템 수준 검증은 완료되지 않았습니다.
```

---

# 53. Verification Confidence

필요하면 검증 상태와 별개로 confidence를 둘 수 있다.

```text
HIGH

MEDIUM

LOW
```

그러나 실제 Test PASS보다 Confidence를 우선하지 않는다.

---

# 54. Tool Failure와 Product Failure 구분

Test 실행이 실패했을 때:

```text
테스트 자체 실패?
```

와:

```text
Test runner/environment 실패?
```

를 구분한다.

예:

```text
npm command missing
```

은 기능 실패가 아니라 환경 문제일 수 있다.

---

# 55. Failure Classification

Verification 실패를 구분한다.

```text
IMPLEMENTATION_FAILURE

REGRESSION_FAILURE

TEST_INFRA_FAILURE

BUILD_FAILURE

TYPE_FAILURE

ENVIRONMENT_FAILURE

EXTERNAL_SERVICE_FAILURE

UNKNOWN
```

---

# 56. 실패 후 무조건 코드 수정 금지

예:

```text
Integration test timeout
```

이 발생했다고 무조건 코드 수정부터 하지 않는다.

원인이:

```text
network unavailable
```

일 수도 있다.

---

# 57. Root Cause 확인

Verification failure:

```text
FAIL
```

↓

```text
Why?
```

↓

```text
Code issue?
Test issue?
Environment issue?
Contract issue?
```

를 구분한다.

---

# 58. Rework Loop

실제 구현 문제라면:

```text
VERIFY FAIL

↓

ROOT CAUSE

↓

CHANGE CONTROL

↓

MINIMAL FIX

↓

VERIFY AGAIN
```

으로 돌아간다.

---

# 59. 무한 수정 Loop 방지

반복 실패가 지속되면 같은 방식으로 계속 수정하지 않는다.

Trigger:

```text
동일 Test 반복 실패

새 Regression 계속 발생

Diff 지속 확대

가설 계속 변경
```

그러면:

```text
STOP

↓

Checkpoint

↓

Re-evaluate root cause
```

한다.

---

# 60. Retry Budget

Verification retry 역시 비용이다.

무한 반복하지 않는다.

작업 난이도에 맞는 합리적 재시도 후 Escalation 또는 BLOCKED 상태를 사용한다.

---

# 61. Multi-Agent Review

다음 경우 독립 Reviewer를 고려한다.

```text
HIGH / CRITICAL Risk

Large refactor

Complex architecture

Security

DB Migration

Shared core component
```

---

# 62. Reviewer 입력 최소화

Reviewer에게 전체 대화를 전달하지 않는다.

필수:

```text
User request

Success Criteria

Relevant Diff

Change Contract

Affected Features

Test Results

Known Risks
```

만 전달한다.

---

# 63. Independent Review 목적

Reviewer는 IMPLEMENTER의 설명을 그대로 믿지 않는다.

검토:

```text
Requirement satisfied?

Unexpected behavior?

Regression risk?

Scope creep?

Missing tests?

Security issue?

Contract break?
```

---

# 64. Reviewer가 코드를 자동 수정하지 않을 수도 있다

기본 역할:

```text
IDENTIFY ISSUE
```

필요하면 Orchestrator가 수정 Task를 다시 배정한다.

Review와 Implementation을 명확히 분리할 수 있다.

---

# 65. Verification Checklist 자동 생성

Success Criteria와 Impact Map을 바탕으로 필요한 검증 목록을 만들 수 있다.

예:

```text
Feature:
dashboard.todayShift
```

→

```text
UI empty state test

UI normal state test

Dashboard regression

Type check
```

---

# 66. Test Map 활용

Codebase OS Test Map이 있다면:

```text
Feature

↓

Tests
```

로 필요한 테스트를 바로 찾는다.

---

# 67. Impact Map 활용

공용 Symbol 변경:

```text
Target Symbol

↓

Consumers

↓

Affected Features

↓

Relevant Tests
```

순서로 회귀 범위를 결정한다.

---

# 68. Test Failure Prioritization

여러 테스트가 실패하면 현재 Change와 직접 관련된 실패부터 분석한다.

기존 unrelated failing test를 새 변경 때문이라고 가정하지 않는다.

---

# 69. Baseline Failure

가능하면 기존 상태에서 이미 실패하던 테스트인지 확인한다.

예:

```text
Before Change:
Test X FAIL

After Change:
Test X FAIL
```

이면 현재 수정의 Regression으로 단정하지 않는다.

---

# 70. New Failure

```text
Before:
PASS

After:
FAIL
```

은 높은 우선순위로 조사한다.

---

# 71. Existing Failure 기록

현재 작업과 무관한 기존 failure 발견 시:

```text
PRE-EXISTING FAILURE
```

로 분류한다.

자동으로 수정 범위를 확장하지 않는다.

---

# 72. Snapshot Test 주의

Snapshot 업데이트만으로 Test를 통과시키지 않는다.

먼저 변경된 UI가 의도된 것인지 확인한다.

---

# 73. Visual Regression

중요 UI 수정에 visual test 환경이 있다면 활용한다.

단 모든 UI 변경에서 필수로 새 도구를 도입하지 않는다.

---

# 74. Browser Verification

브라우저 환경이 제공되면 중요한 상호작용은 실제로 확인할 수 있다.

예:

```text
Route load

Click

Form submit

Error state

Empty state
```

---

# 75. Performance Verification

성능 개선 작업에서는 기능 테스트만으로 완료하지 않는다.

Success Criteria에 측정 기준을 포함한다.

예:

```text
Before:
500ms

After:
< 300ms
```

실제 측정 근거를 요구한다.

---

# 76. Optimization 검증

"더 빨라졌다"는 느낌으로 완료하지 않는다.

Benchmark 또는 측정값을 사용한다.

---

# 77. Token/Cost Optimization Verification

Harness 최적화 작업이라면:

```text
Tokens per successful task

Cost per successful task

Retries

Escalation

Latency
```

등 실제 지표로 평가한다.

---

# 78. Documentation Change Verification

문서 변경도 검증 대상이다.

확인:

```text
실제 코드와 일치?

잘못된 path 없음?

잘못된 model/API name 없음?

stale reference 없음?
```

---

# 79. Code Map Verification

구조 변경 후:

```text
Feature Map

Symbol Map

Code Graph

Impact Map
```

이 실제 코드와 일치하는지 Validator를 실행할 수 있다.

---

# 80. Generated Map 변경

Code Map 자동 생성 결과가 바뀌었다면:

```text
expected generated change?
```

를 확인한다.

---

# 81. Verification Evidence Cache

같은 Commit에서 이미 검증된 결과는 재사용할 수 있다.

예:

```text
Typecheck PASS
commit abc123
```

해당 파일이 변경되지 않았다면 무조건 다시 실행할 필요가 없을 수 있다.

---

# 82. Cache Invalidator

다음 경우 검증 Cache를 무효화한다.

```text
Relevant source changed

Test changed

Config changed

Dependency changed

Build setting changed

Schema changed
```

---

# 83. Verification Token Efficiency

검증에서도 무작정 전체 로그를 읽지 않는다.

```text
execute

↓

machine result

↓

relevant failure only
```

를 선호한다.

---

# 84. Stop on First Useful Failure

대규모 테스트에서 명확한 Blocking Failure가 발생했다면 먼저 그 문제를 해결한다.

불필요하게 수천 줄 추가 로그를 분석하지 않는다.

---

# 85. Parallel Verification

독립 테스트는 Harness가 병렬 실행할 수 있다.

예:

```text
Frontend tests

Backend tests

Static analysis
```

단 실제 실행환경이 지원하고 비용 이점이 있을 때만 사용한다.

---

# 86. Deterministic Verification은 저비용 Agent보다 우선

예:

```text
"JSON Schema가 맞는지 Efficient Agent에게 검토"
```

보다:

```text
Schema validator 실행
```

을 선택한다.

---

# 87. Verification Summary

완료 단계에서 최소 다음을 정리한다.

```text
Success Criteria:

Tests:

Type Check:

Build:

Runtime:

Regression:

Unverified:

Overall Status:
```

---

# 88. Verification Matrix 예

```text
Success Criteria
PASS

PASS

Type Check
PASS

Build
PASS

NOT RUN

PASS

Regression
PASS

```

Integration Test가 작업에 반드시 필요하지 않다면 Overall을 VERIFIED로 판단할 수도 있다.

중요한 것은 필요한 검증 수준을 사전에 정의하는 것이다.

---

# 89. Required vs Optional Verification

각 검증을:

```text
REQUIRED

OPTIONAL

N/A
```

로 구분할 수 있다.

예:

```text
Unit Test:
REQUIRED

E2E:
OPTIONAL

DB Migration:
N/A
```

---

# 90. N/A와 NOT RUN 구분

```text
N/A
```

= 현재 작업에 해당하지 않음.

```text
NOT RUN
```

= 해당할 수 있으나 실행하지 않음.

둘을 혼동하지 않는다.

---

# 91. Completion Gate

다음 조건이 충족되어야 DONE으로 이동할 수 있다.

```text
[ ] Required Success Criteria 충족

[ ] Required Tests 통과

[ ] Blocking static/type/build error 없음

[ ] Known Regression 없음

[ ] Final Diff 확인

[ ] Unexpected Change 해결

[ ] Required Map/Docs 업데이트

[ ] Unverified 항목 명확
```

---

# 92. VERIFIED Completion

다음 조건:

```text
Required checks 모두 PASS

+

No known blocker

+

No unexplained regression
```

이면:

```text
DONE / VERIFIED
```

---

# 93. PARTIAL Completion

구현은 완료했지만 일부 필요한 환경 검증을 수행하지 못했다면:

```text
DONE / PARTIALLY_VERIFIED
```

로 보고할 수 있다.

단 사용자가 추가 실행이 필요함을 이해할 수 있어야 한다.

---

# 94. BLOCKED Completion

필수 검증을 통과하지 못했으면:

```text
NOT DONE / BLOCKED
```

이다.

코드가 작성되었다는 이유로 DONE 처리하지 않는다.

---

# 95. User-visible 완료 보고

사용자에게 모든 내부 검증 로그를 보여줄 필요는 없다.

간결하게:

```text
수정 완료.

- 관련 Unit Test: 통과
- Type Check: 통과
- Build: 통과
- API/DB 변경: 없음
- 검증 상태: VERIFIED
```

정도로 보고할 수 있다.

---

# 96. 미검증 보고

예:

```text
코드 수정과 관련 Unit Test는 완료했습니다.

다만 현재 환경에서 실제 Browser E2E는 실행하지 못했으므로
UI 런타임 부분은 미검증 상태입니다.
```

---

# 97. Fail Loud는 과장하지 않는다

미검증 영역을 정확하게 설명하되 필요 이상으로 작업 전체가 실패한 것처럼 표현하지 않는다.

예:

```text
Unit/Build는 VERIFIED,
Production deploy는 UNVERIFIED
```

처럼 영역별로 구분한다.

---

# 98. Checkpoint 연동

Verification 완료 시 Context Checkpoint를 갱신한다.

예:

```text

VERIFIED

Tests:
PASS

PASS

Open:
None
```

# 99. Handoff 연동

작업을 다른 Agent에게 넘길 경우 Verification 상태를 반드시 포함한다.

```text
VERIFIED

PARTIALLY_VERIFIED

UNVERIFIED

BLOCKED
```

# 100. Change Control 연동

Verification 중 Actual Diff가 Change Contract를 벗어난 것이 발견되면:

```text

```

로 되돌린다.

# 101. Instruction Router 연동

# 103. Verification Agent 역할

```text

```

# 106. Verification Scope Explosion 금지

Impact Map을 기준으로 영향을 받는 영역을 중심으로 검증한다.

---

# 107. Verification Under Constraint

환경 제약으로 모든 검증을 수행할 수 없다면:

```text

+

불가능한 검증 명시

+

Verification 상태 낮춤
```

으로 처리한다.

# 108. Offline Verification


검증은 최대한 수행한다.

# 109. External Dependency Unavailable

```text

```


환경 차이가 중요한 작업이라면 이를 명시한다.

# 126. 압축 Core 지침

전체 문서를 항상 로드하지 못한다면 다음만 유지한다.

```text
VERIFICATION GATE CORE

1. Code written does not mean task complete.
2. Verify against explicit success criteria.
3. Scale verification depth to change risk and impact.
4. Prefer deterministic tools over model judgment whenever possible.
5. Run the narrowest relevant tests first, then expand based on impact.
6. Verify both changed behavior and behavior that must remain unchanged.
7. Do not delete, skip, weaken, or bypass tests merely to make them pass.
8. Do not hide type, lint, build, runtime, or error-handling failures.
9. Compare actual diff against the intended change scope.
10. Separate implementation status from verification status.
11. Use VERIFIED, PARTIALLY_VERIFIED, UNVERIFIED, or BLOCKED.
12. Never claim more than the evidence supports.
13. If verification fails because of the implementation, return to Change Control and make the smallest justified fix.
14. If verification cannot be completed because of environment/tool constraints, state exactly what remains unverified.
15. A task is DONE only when required success criteria and required verification gates are satisfied.
```

# 127. Final Principle

> AI가 코드를 작성했다는 사실은 증거가 아니다.

> 테스트가 존재한다는 사실도 증거가 아니다.

> 실제로 실행되고, 기대 동작이 확인되고, 기존 동작이 보존되었다는 결과가 증거다.

따라서:

```text
IMPLEMENT

↓

PROVE

↓

REPORT
```

순서를 지킨다.

최종 상태는 항상:

```text
What was changed?

What was tested?

What was preserved?

What remains unverified?
```

에 답할 수 있어야 한다.
