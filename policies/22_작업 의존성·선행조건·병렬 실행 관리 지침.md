# Task DAG & Dependency Execution Policy v1

## 작업 의존성·선행조건·병렬 실행·Critical Path 관리 지침

Version: 1.0

---

# 0. 목적

이 Policy는 복잡한 개발 작업에서 다음 문제를 방지한다.

```text
선행조건이 끝나지 않았는데 후속 구현 시작

API 구조가 정해지기 전에 UI 깊게 구현

DB 구조가 확정되지 않았는데 Consumer 코드 작성

병렬화 가능한 작업을 전부 순차 처리

서로 의존하는 작업을 동시에 실행

여러 Agent가 같은 파일을 중복 조사

한 Task가 막혔는데 전체 작업이 멈춤

어떤 Blocker가 무엇을 막는지 불명확

Critical Path를 무시하고 중요하지 않은 작업부터 수행

Task 간 관계를 잊어 실행 순서가 계속 바뀜
```

이를 방지하기 위해 작업을 단순 목록이 아니라 **Directed Acyclic Graph(DAG)** 형태로 관리한다.

핵심 구조:

```text
TASKS

↓

DEPENDENCIES

↓

READY NODES

↓

PARALLELIZABLE NODES

↓

EXECUTION

↓

NODE EVIDENCE

↓

UNBLOCK DOWNSTREAM

↓

CRITICAL PATH

↓

TASK COMPLETION
```

---

# 1. DAG란

DAG는:

```text
Directed Acyclic Graph
```

이다.

쉽게 말하면:

> 작업 사이의 선후관계를 화살표로 연결한 실행 지도다.

예:

```text
T1 요구 확정
   ↓
T2 API Contract
   ↓
T3 Backend
   ↓
T4 Frontend
   ↓
T5 E2E
```

---

# 2. 왜 단순 번호 목록보다 강한가

일반 Plan:

```text
1. DB
2. API
3. UI
4. Test
```

문제:

```text
항상 순서대로 해야 하나?

UI mock은 API 전에 가능한가?

Test 일부는 Backend와 병렬 가능한가?

DB가 막히면 전체가 멈추나?
```

DAG는 이런 관계를 명시한다.

---

# 3. 예

```text
        T1 Spec Lock
             ↓
        T2 Data Model
          ↙        ↘
   T3 Backend     T4 UI Skeleton
          ↘        ↙
        T5 Integration
             ↓
        T6 Verification
```

여기서:

```text
T3와 T4
```

는 조건에 따라 병렬 가능하다.

---

# 4. 최상위 원칙

> 순서가 아니라 의존성을 먼저 본다.

작업을 단순히 앞에서부터 실행하지 않는다.

다음 질문을 한다.

```text
이 Task가 시작되려면 무엇이 먼저 확정되어야 하는가?
```

---

# 5. 모든 작업에 DAG 필요 없음

DAG는 다음에서 유용하다.

```text
Multi-layer feature

Frontend + Backend + DB

3개 이상 독립 Workstream

Multi-agent

긴 작업

복잡한 Migration

여러 선행조건

병렬 실행 가치가 큰 작업
```

---

# 6. DAG를 생략해도 되는 작업

예:

```text
한 파일 Bug Fix

텍스트 수정

작은 UI 변경

3단계 이하의 명확한 순차 작업
```

Active Plan만으로 충분할 수 있다.

---

# 7. DAG 구성 요소

기본 구성:

```text

EVIDENCE

OWNER

```

---

# 8. NODE

하나의 의미 있는 Task.

예:

```text
T1 API Contract 확정
T2 Backend 구현
T3 UI 구현
T4 Contract Test
```

---

# 9. 좋은 Node

하나의 명확한 결과를 가진다.

예:

```text
T2:
GET /api/shifts/today 응답에
nightWorker nullable state 제공
```

---

# 10. 나쁜 Node

```text
T2:
코드 작업
```

결과가 불명확하다.

---

# 11. Node Granularity

Node는 너무 크거나 작지 않게 한다.

너무 큼:

```text
T1 전체 Backend 완성
```

너무 작음:

```text
T1 import 한 줄 추가
```

---

# 12. 적절한 Node 크기

대체로:

> 독립적으로 완료 여부를 판단할 수 있는 작업 단위

가 좋다.

---

# 13. EDGE

Task 간 의존 관계를 나타낸다.

```text
T1 → T2
```

뜻:

> T2를 시작하기 전에 T1 결과가 필요하다.

---

# 14. Edge가 단순 시간 순서를 뜻하지는 않는다

```text
T1이 먼저 하면 편함
```

이 아니라:

```text
T1 결과 없이는 T2의 올바른 실행이 어렵거나 불가능
```

한 경우에 Edge를 둔다.

---

# 15. Dependency Type

필요하면 의존성을 분류한다.

```text
HARD

SOFT

DATA

CONTRACT

DECISION

RESOURCE

VERIFICATION
```

---

# 16. HARD

선행 Task 없이는 후속 Task 시작 불가.

예:

```text
DB schema
→ migration
```

---

# 17. SOFT

선행 Task가 있으면 좋지만 mock/stub으로 진행 가능.

예:

```text
Backend API
→ UI
```

UI가 mock response로 먼저 작업 가능하다면 Soft Dependency.

---

# 18. DATA

실제 데이터 구조가 필요.

예:

```text
Data model
→ serializer
```

---

# 19. CONTRACT

Interface/API Schema가 필요.

예:

```text
API contract
→ frontend integration
```

---

# 20. DECISION

Architecture/Business Decision이 선행돼야 함.

예:

```text
Permission policy
→ authorization implementation
```

---

# 21. RESOURCE

외부 접근/환경 필요.

예:

```text
Cloud credentials
→ deployment
```

---

# 22. VERIFICATION

다음 단계로 넘어가기 전에 특정 검증이 필요.

예:

```text
Migration test
→ staging deploy
```

---

# 23. Task Status

기본 상태:

```text
BLOCKED

NOT_READY

READY

ACTIVE

DONE

FAILED

CANCELLED

SKIPPED
```

---

# 24. NOT_READY

선행 Task가 아직 끝나지 않음.

---

# 25. READY

모든 필수 Dependency 충족.

즉시 실행 가능.

---

# 26. ACTIVE

현재 실행 중.

---

# 27. DONE

Node의 Output과 Exit Criteria 충족.

---

# 28. BLOCKED

Dependency 외 별도 Blocker 때문에 진행 불가.

---

# 29. FAILED

Task 자체 실행 실패.

다시 시도/재계획 필요.

---

# 30. SKIPPED

조사 결과 필요 없어진 Node.

---

# 31. Node Output

각 Task는 후속 Task가 사용할 Output을 정의한다.

예:

```text
T1 API Contract

OUTPUT:
ShiftTodayResponse schema
```

---

# 32. Output 없는 Node 주의

아무 결과도 남기지 않는 Task는 목적이 불명확할 수 있다.

---

# 33. Node Exit Criteria

예:

```text

- response fields defined
- nullability defined
- error semantics defined
```

# 34. Node Evidence

# 36. 병렬성

T4와 T5가 같은 Contract를 기준으로 독립 구현 가능하면 병렬화할 수 있다.

---

# 37. 병렬화 조건

다음을 만족할수록 병렬화 가치가 높다.

```text
입력이 이미 확정

서로 같은 파일을 수정하지 않음

서로 결과에 의존하지 않음

Merge conflict 가능성 낮음

독립적으로 검증 가능
```

---

# 38. 병렬화하면 안 되는 경우

```text
같은 파일 수정

한쪽 결과가 다른 쪽 입력

Contract 아직 미확정

Shared global state 수정

같은 Architecture Decision 필요
```

---

# 39. Parallel ≠ Faster Always

Agent spawn/context/merge 비용도 고려한다.

---

# 40. Delegation Benefit

병렬 Task는:

```text
Expected saved time / context benefit
```

이:

```text
coordination overhead
```

보다 클 때 사용한다.

---

# 43. Critical Path

프로젝트/Task 완료시간에 직접 영향을 주는 가장 긴 의존 경로.

예:

```text
T1 → T2 → T5 → T8
```

이 경로가 막히면 전체 완료가 지연된다.

---

# 44. Critical Path 우선

같은 Priority라면 Critical Path Node를 먼저 처리하는 것이 유리할 수 있다.

---

# 45. 단 사용자 Priority가 더 높을 수 있음

User Authority를 따른다.

---

# 46. Critical Path는 고정되지 않을 수 있다

Task duration/Blocker가 바뀌면 경로가 달라질 수 있다.

---

# 47. Duration Estimate 주의

정확한 시간 예측이 어려우면:

```text
LOW / MEDIUM / HIGH effort
```

등으로 관리 가능.

---

# 48. Effort

예:

```text
T1 LOW
T2 HIGH
T3 MEDIUM
```

Critical Path 분석에 참고.

---

# 49. Task Priority

```text
P0

P1

P2

P3
```

등 별도 사용 가능.

---

# 50. Priority와 Dependency는 다르다

P0 Task라도 Dependency가 안 끝났으면 실행할 수 없다.

---

# 51. Blocking Graph

Blocker가 발생했을 때 어떤 downstream Node가 막히는지 확인한다.

예:

```text
T2 BLOCKED

Blocks:
T4
T5
T6
```

---

# 52. 전체 Task를 막는지 확인

T2가 막혀도 독립적인 T3가 있다면 실행 가능.

---

# 53. Work Conservation

하나가 막혔다고 모든 Agent가 대기하지 않는다.

READY 상태의 독립 Node를 찾는다.

---

# 54. 단 우선순위 없는 Busy Work 금지

Blocker가 있다는 이유로 중요하지 않은 Parking Lot Task를 시작하지 않는다.

---

# 55. Blocked Work 대체 조건

다음 중 하나:

```text
same milestone

approved next milestone

independent required work
```

이어야 한다.

# 224. 압축 Core 지침

```text
TASK DAG / DEPENDENCY EXECUTION CORE

1. Use a task DAG only when dependency structure, branching, parallel work, blockers, or multi-agent coordination materially benefits from it.
2. Represent meaningful executable outcomes as nodes and real prerequisite relationships as directed edges.
3. Do not confuse preferred ordering with true dependency; create an edge only when downstream correctness or execution materially requires upstream output.
4. Give each important node a clear input, output, owner, status, exit condition, and evidence when appropriate.
5. A node becomes READY only when all required hard dependencies and prerequisites are satisfied.
6. Parallelize only nodes with stable inputs, independent scopes, low file/state conflict, and no unresolved shared decision.
7. Do not parallelize work that depends on an unstable contract, modifies the same shared files, or requires a common unresolved architecture decision.
8. Prefer contract-first or decision-first nodes when multiple downstream workstreams depend on the same interface or rule.
9. Track blockers by the downstream nodes they prevent, and continue other approved READY work when possible instead of idling the whole task.
10. Prioritize critical-path, high-unlock-value, high-priority, or risk-reducing READY nodes when choosing what to execute next.
11. Treat newly discovered dependencies, node additions, or major edge changes as replanning signals when they materially alter execution.
12. Keep unrelated discoveries outside the DAG in the Parking Lot.
13. Prevent cycles; a cycle often indicates poor task decomposition, missing shared contract, or architecture coupling that should be resolved.
14. In multi-agent execution, assign one canonical owner per node, partition scopes to reduce overlap, and send only the node-specific context and required upstream outputs.
15. Subagents return structured node results and suggested dependency changes; the orchestrator owns the canonical DAG.
16. Verify important nodes early rather than deferring all testing to one final big-bang verification step.
17. Do not mark nodes DONE without their defined output and required evidence.
18. Keep the DAG scoped to the active task or milestone; the project-wide direction belongs in the roadmap.
```

# 225. Final Principle

복잡한 작업에서 중요한 것은:

```text
"무엇부터 하지?"
```

만이 아니다.

더 중요한 질문은:

```text
무엇이 무엇에 의존하는가?

무엇은 지금 시작 가능한가?

무엇은 동시에 해도 되는가?

무엇이 막혀 있는가?

어떤 작업이 끝나야 가장 많은 다음 작업이 열리는가?

현재 전체 완료를 가장 많이 늦추는 작업은 무엇인가?
```

이다.

따라서 실행은:

```text
DEFINE TASKS

↓

DEFINE DEPENDENCIES

↓

FIND READY WORK

↓

PARALLELIZE ONLY SAFE WORK

↓

VERIFY NODE OUTPUTS

↓

UNLOCK DOWNSTREAM

↓

HANDLE BLOCKERS

↓

REPLAN WHEN GRAPH CHANGES

↓

FINAL INTEGRATION
```

으로 관리한다.

최종적으로:

> **좋은 DAG는 작업을 복잡하게 만드는 문서가 아니라, 복잡한 작업에서 불필요한 기다림과 잘못된 순서를 제거하는 실행 지도다.**

그리고 가장 중요한 원칙은:

> **병렬로 할 수 있는 것은 병렬로 하되, 아직 결정되지 않은 것을 여러 Agent가 각자 다르게 가정한 채 병렬 구현하지 않는다.**
