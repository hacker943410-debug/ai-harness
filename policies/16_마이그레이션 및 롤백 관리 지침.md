# ⑭ 마이그레이션 및 롤백 관리 지침 v1

## Migration & Rollback Policy

### 데이터·스키마·설정·상태·인프라 변경 및 복구 통제 지침

Version: 1.0

---

# 0. 목적

이 지침은 AI Agent가 다음과 같은 되돌리기 어려운 변경을 단순 코드 수정처럼 처리하지 않도록 한다.

```text id="mrp001"
DB Schema 변경

Column 추가/삭제/변경

Table 구조 변경

Data Migration

Data Backfill

Config Format 변경

Persistent State 구조 변경

Storage Format 변경

File Format 변경

Cache 구조 변경

Cloud Resource 변경

Infrastructure 변경

Queue/Event Schema 변경

API Contract와 Data Model 동시 변경

권한 데이터 구조 변경

대규모 Rename

데이터 정규화/비정규화

Identifier 체계 변경
```

대표적인 실패:

```text id="mrp002"
Schema만 바꾸고 기존 데이터는 고려하지 않음

Column 삭제 후 데이터 복구 불가

Production에서 바로 Migration 실행

Forward Migration만 있고 Rollback 없음

Old App과 New DB가 동시에 존재할 상황을 고려하지 않음

Migration 중간 실패 시 상태 불명

Backfill 도중 일부 데이터만 변경

기존 NULL 값을 고려하지 않음

Default 값 때문에 의미가 왜곡

Rollback이 실제로 데이터까지 복구하는지 확인하지 않음

Staging 통과를 Production 안전성으로 과장

Migration 파일을 수정해 이미 적용된 History를 변경

Infra 변경 후 원래 리소스 상태를 복원하지 못함
```

이를 방지하기 위한 기본 흐름:

```text id="mrp003"
CURRENT STATE

↓

TARGET STATE

↓

DIFF

↓

DATA / STATE IMPACT

↓

COMPATIBILITY

↓

FORWARD MIGRATION

↓

FAILURE MODES

↓

ROLLBACK / RECOVERY

↓

DRY RUN / TEST

↓

CONTROLLED EXECUTION

↓

POST-MIGRATION VERIFICATION

↓

CLEANUP
```

# 1. 최상위 원칙

> 되돌리기 어려운 변경은 “변경 방법”과 “실패했을 때 복구 방법”을 함께 설계한다.

다음 계획은 불완전하다.

```text id="mrp004"
Column 추가
→ Migration 실행
→ 완료
```

최소한:

```text id="mrp005"
현재 상태

목표 상태

기존 데이터 영향

Application compatibility

Forward migration

Failure behavior

Rollback

Verification
```

까지 고려한다.

# 3. Rollback의 정의

Rollback은 단순히:

```text id="mrp007"
코드 이전 버전 배포
```

만 의미하지 않는다.

상황에 따라:

```text id="mrp008"
Application rollback

Schema rollback

Data restoration

Config rollback

Infrastructure rollback

Traffic rollback

Feature flag disable

Backup restore
```

중 하나 이상이 필요하다.

# 27. Example — Column Rename

바로:

```text id="mrp028"

→ new_name
```

Rename하면 Old App이 깨질 수 있다.

대신:

```text id="mrp029"

2. old_name + new_name dual support

3. data backfill

4. consumers migrate

5. verify

6. old_name remove
```

가능.

# 280. 압축 Core 지침

```text id="mrp120"
마이그레이션 및 롤백 관리 CORE

1. 되돌리기 어려운 변경은 Forward Migration과 Rollback/Recovery를 함께 설계한다.
2. Migration 전에 실제 Current State, Target State, Existing Data, Application Compatibility를 확인한다.
3. Schema Migration과 Data Migration을 구분하고 각각의 영향을 평가한다.
4. Destructive Change의 기본값은 금지이며, 필요하면 Data Loss, Backup, Recovery, Approval을 명시적으로 검토한다.
5. 가능한 경우 additive change와 Expand → Migrate → Verify → Contract 방식을 사용해 호환성을 유지한다.
6. Column/Table/Contract를 제거하기 전에 모든 필요한 Consumer가 새 구조로 이동했는지 확인한다.
7. 기존 데이터의 NULL, duplicate, orphan, enum, invalid legacy value를 Migration 전에 검증한다.
8. 새로운 Default 값을 모르는 기존 데이터의 실제 의미로 임의 사용하지 않는다.
9. Constraint를 강화하기 전에 기존 데이터가 해당 Constraint를 만족하는지 확인한다.
10. 이미 적용된 Migration을 임의 수정하지 말고 현재 Migration 시스템의 History Convention을 따른다.
11. 자동 생성된 Migration도 destructive operation, data rewrite, lock 위험을 검토한다.
12. Production 규모와 개발 데이터 규모가 다를 수 있으므로 대량 변경은 실행시간, locking, partial failure, resume 가능성을 고려한다.
13. Rollback 가능성을 FULL, PARTIAL, ROLL_FORWARD_ONLY, IRREVERSIBLE 등 실제 상태로 판단한다.
14. 코드 Rollback과 데이터 Rollback을 동일하게 취급하지 않는다.
15. Backup 존재만으로 복구 가능하다고 주장하지 말고 필요하면 Restore 절차도 검증한다.
16. 복잡한 Migration은 Dry Run, Staging, Post-Migration Verification, Monitoring을 Risk에 비례해 수행한다.
17. Migration이 예상 밖에서 필요해지면 Drift Sentinel과 Replanning을 실행하고 Scope/Risk/Verification을 다시 계산한다.
18. DB/Data/Infra Migration의 실제 적용 상태는 Environment별로 구분하여 Progress Ledger에 기록한다.
19. Migration 완료는 Tool 성공 메시지가 아니라 Target State, Data Integrity, Application Behavior, Required Tests로 검증한다.
20. 목표는 Migration을 실행하는 것이 아니라 데이터와 서비스를 안전하게 목표 상태로 이동시키고 실패 시 복구 가능한 상태를 유지하는 것이다.
```

# 281. Final Principle

Migration에서 가장 위험한 질문은:

```text id="mrp121"
어떻게 바꾸지?
```

하나만 하는 것이다.

반드시 함께 물어야 한다.

```text id="mrp122"
현재 상태는 정확히 무엇인가?

↓

어떤 데이터를 바꾸는가?

↓

기존 Application은 계속 동작하는가?

↓

중간에 실패하면 어떤 상태가 되는가?

↓

어떻게 감지하는가?

↓

어떻게 되돌리는가?

↓

되돌릴 수 없다면 어떻게 복구하는가?

↓

무엇으로 성공을 증명하는가?
```

따라서 전체 흐름은:

```text id="mrp123"
UNDERSTAND CURRENT STATE

↓

DEFINE TARGET

↓

PROTECT DATA

↓

MIGRATE COMPATIBLY

↓

VERIFY

↓

CUT OVER

↓

REMOVE OLD ONLY WHEN SAFE

↓

KEEP RECOVERY PATH UNTIL CONFIDENT
```

이다.

가장 중요한 원칙은:

> **데이터 구조를 바꾸는 데 성공한 것이 아니라, 기존 데이터를 잃지 않고 새 구조로 안전하게 이동했을 때 Migration이 성공한 것이다.**

그리고:

> **Rollback은 문제가 생긴 뒤 생각하는 절차가 아니라, Migration을 설계할 때 함께 설계하는 절차다.**
