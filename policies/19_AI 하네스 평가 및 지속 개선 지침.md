# ⑰ AI 하네스 평가 및 지속 개선 지침 v1

## Harness Evaluation & Continuous Improvement Policy

### AI 개발체계 성능·품질·비용·지침 효과·라우팅·컨텍스트·자동화 지속 평가 지침

Version: 1.0

---

# 0. 목적

이 지침은 지금까지 구축한 AI Harness가 단순히:

```text
지침이 많다

Agent가 많다

자동화가 많다

문서가 많다
```

는 이유만으로 좋은 시스템이라고 착각하지 않도록 한다.

Harness의 목적은 다음을 실제로 개선하는 것이다.

```text
작업 성공률 ↑

첫 시도 성공률 ↑

사용자 수정 요청 ↓

같은 실수 재발 ↓

불필요한 Scope 확대 ↓

재작업 ↓

검증 누락 ↓

Context 사용량 ↓

Token 비용 ↓

불필요한 Agent 호출 ↓

잘못된 Model Routing ↓

완료까지 필요한 Iteration ↓
```

따라서 기본 흐름은 다음과 같다.

```text
HARNESS

↓

RUN REAL TASKS

↓

COLLECT EVIDENCE

↓

MEASURE

↓

COMPARE TO BASELINE

↓

FIND FAILURE / WASTE

↓

IDENTIFY ROOT CAUSE

↓

CHANGE ONE MEANINGFUL THING

↓

CANARY / REPLAY

↓

VERIFY IMPROVEMENT

↓

PROMOTE OR ROLLBACK
```

최종 목표:

> 지침을 계속 추가하는 Harness가 아니라, 실제 실패와 비용을 줄이는 방향으로 스스로 정리되고 진화하는 Harness를 만든다.

---

# 1. 최상위 원칙

> Harness 자체도 검증 대상이다.

다음은 충분한 성공 근거가 아니다.

```text
정책을 25개 만들었다.

Agent 역할을 세분화했다.

Router를 추가했다.

Context를 압축했다.

Validator를 많이 만들었다.
```

실제 결과가 개선되어야 한다.

---

# 2. Harness의 성공 기준

Harness가 좋아졌다는 것은 예를 들어:

```text
Before

100개 Task
72개 첫 시도 성공
평균 재작업 1.8회
사용자 수정 24회
평균 42K tokens


After

100개 유사 Task
87개 첫 시도 성공
평균 재작업 0.7회
사용자 수정 9회
평균 29K tokens
```

처럼 실제 변화가 확인되는 것이다.

# 13. User Correction Rate

사용자가:

```text
아니 그게 아니야.

원래 건드리지 말라고 했잖아.

다시 해줘.

내가 말한 건 이거야.
```

같은 Correction을 해야 했던 비율.

---

# 14. User Correction은 매우 강한 Signal

특히 다음 문제를 탐지할 수 있다.

```text

Requirement Interpretation Failure

Design Calibration Failure

Scope Drift

Communication Failure
```

---

# 15. 모든 사용자 추가 요청이 Correction은 아니다

```text

# 17. Repeated Failure Rate

# 18. 이 지표는 Self-learning Harness에서 특히 중요

```

# 406. 압축 Core 지침

```text
AI 하네스 평가 및 지속 개선 CORE

1. Harness의 성공은 지침, Agent, 문서, 자동화의 개수가 아니라 실제 작업 품질과 비용 개선으로 판단한다.
2. Task Success, First-Pass Success, User Correction, Rework, Repeated Failure, Scope Drift, Verification Escape, Token per Successful Task를 핵심 신호로 사용한다.
3. Agent가 DONE이라고 말한 것을 성공으로 계산하지 말고 Locked Success Criteria와 Verification Evidence를 기준으로 판단한다.
4. 사용자 Correction과 새로운 Requirement를 구분하여 Harness 실패율을 왜곡하지 않는다.
5. Replan은 User Change, Planning Error, False Assumption, External Change 등 원인별로 분류한다.
6. 단일 Metric을 최적화하지 말고 Quality, Reliability, Cost, Context, Latency, Safety 사이의 Trade-off를 함께 본다.
7. 저렴한 Model의 반복 실패와 Retry까지 포함하여 Cost per Successful Task를 평가한다.
8. Router는 필요한 Policy를 놓치지 않는 Recall과 불필요한 Policy를 적게 로드하는 Precision을 함께 평가한다.
9. Policy가 존재했는데 실패했다면 새 Policy를 만들기 전에 Router miss, Policy weakness, Model capability, Context, Tool, Verification 원인을 구분한다.
10. 각 Policy는 실제 Failure 감소 효과와 Context/Execution 비용을 함께 평가하며 낮은 가치·중복·오래된 Policy는 축소·통합·폐기할 수 있다.
11. 반복적으로 기계적으로 검사 가능한 Rule은 Prompt보다 Test, Validator, CI, Architecture Guardrail로 승격한다.
12. 새 Hard Guardrail은 False Positive 위험이 있으면 Observe → Warn → Canary → Block 단계로 점진 적용한다.
13. Harness 변경 전 가능한 범위에서 Baseline을 확보하고 비슷한 Task Class끼리 비교한다.
14. Global Router, CORE, Model Routing, Hard Validator 변경은 Targeted/Regression Benchmark로 검증한다.
15. 실제 프로젝트에서 발생했던 실패 Task를 익명화하여 Replay/Regression Benchmark로 사용하는 것을 선호한다.
16. Model 선택은 이름이 아니라 Task별 Capability, 성공률, Retry, Cost, Latency, Tool Reliability로 평가한다.
17. Context는 많을수록 좋지 않으며 현재 판단에 실제 필요한 Policy, ADR, Lesson, Files만 JIT로 로드한다.
18. Checkpoint/Handoff 품질은 새 Agent가 광범위한 재탐색 없이 현재 Task를 복구할 수 있는지로 평가한다.
19. 동일 실패가 재발하면 Lesson 수를 늘리기보다 기존 Rule/Trigger/Validator가 왜 실패했는지 먼저 조사한다.
20. Harness Telemetry에는 Secret이나 불필요한 민감정보를 저장하지 않고 상태·Metric 중심으로 수집한다.
21. Metric을 좋게 보이게 하기 위해 Test를 약화하거나 Scope를 넓히거나 실패 Task를 분리하는 Gaming을 금지한다.
22. Harness 개선은 ADD뿐 아니라 IMPROVE, AUTOMATE, MERGE, SHORTEN, RETIRE를 포함한다.
23. 새 Policy 제안은 실제 Coverage Gap이 있는지, 기존 Policy 수정이나 자동화로 해결할 수 없는지 먼저 평가한다.
24. Harness 변경도 Change Control, Verification, Rollback의 대상이며 효과가 확인되지 않으면 이전 상태로 되돌릴 수 있어야 한다.
25. 최종 목표는 더 많은 지침을 만드는 것이 아니라 더 적은 반복 실패, 더 적은 재작업, 더 작은 Context, 더 정확한 Routing, 더 강한 검증을 만드는 것이다.
```

# 407. Final Principle

Harness가 성장할수록 가장 위험한 착각은:

```text
규칙이 많아졌다

↓

더 똑똑해졌다
```

라고 생각하는 것이다.

실제 확인해야 하는 것은:

```text
같은 실수를 덜 하는가?

↓

첫 시도에 더 잘 끝내는가?

↓

사용자가 덜 고쳐줘도 되는가?

↓

딴길로 덜 새는가?

↓

검증되지 않은 완료 주장이 줄었는가?

↓

불필요한 Context가 줄었는가?

↓

같은 성공을 더 적은 비용으로 만드는가?
```

이다.

좋은 Harness는 계속 커지는 시스템이 아니다.

```text
OBSERVE

↓

MEASURE

↓

FIND ROOT CAUSE

↓

IMPROVE THE RIGHT LAYER

↓

VERIFY

↓

KEEP WHAT WORKS

↓

REMOVE WHAT DOES NOT
```

를 반복하는 시스템이다.

그리고 가장 중요한 원칙은:

> **실패할 때마다 지침을 하나 추가하지 않는다. 실패가 왜 발생했는지 확인하고, Router·Policy·Tool·Model·Context·Validator 중 실제로 고쳐야 할 한 곳을 고친다.**

최종적으로 Harness의 성숙도는:

```text
얼마나 많이 기억하도록 시켰는가
```

가 아니라:

```text
얼마나 적게 기억해도 같은 실수를 반복하지 않는가
```

로 판단한다.
