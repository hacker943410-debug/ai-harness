# Change Control Policy v1

## AI 코드 변경 범위·영향·Diff 제어 지침

Version: 1.0

---

# 0. 목적

이 Policy는 AI Agent가 실제 소스 코드를 수정하기 직전에 적용한다.

목적은 다음과 같다.

```text
사용자 요청
↓
변경 범위 명확화
↓
허용 변경 정의
↓
금지 영역 정의
↓
예상 Diff 정의
↓
실제 수정
↓
Scope Drift 감시
```

AI는 요구사항을 해결한다는 이유로 프로젝트의 다른 부분까지 임의로 변경해서는 안 된다.

핵심 원칙:

> 최소한의 변경으로 요구사항을 충족한다.

---

# 1. 적용 시점

다음 단계에서 활성화한다.

```text
TASK_DISCOVERY
↓
PLANNING
↓
PRE_MODIFICATION
      ↑
Change Control 활성화
↓
IMPLEMENTATION
```

코드 위치를 단순히 찾는 탐색 단계에서는 전체 Policy를 활성화할 필요가 없다.

실제 파일을 수정하기 직전에 활성화한다.

---

# 2. Change Contract

코드 수정 전에 반드시 내부적으로 **Change Contract**를 생성한다.

최소 항목:

```text
Feature

Goal

Success Criteria

Primary Files

Secondary Files

Protected Areas

API Change

DB Change

Dependency Change

Refactoring

Expected Diff

Risk
```

---

# 3. Change Contract 예시

사용자 요청:

```text
"대시보드 야간 근무자가 없으면
공석이라고 표시해줘."
```

Change Contract:

```text
FEATURE

dashboard.todayShift


GOAL

야간 근무자가 없을 경우
야간 근무 영역에 "공석" 표시


PRIMARY FILES

TodayShiftCard.tsx


SECONDARY FILES

없음 또는 관련 Test


PROTECTED AREAS

Backend
Database
Authentication
다른 Dashboard Card


API CHANGE

NO


DATABASE CHANGE

NO


DEPENDENCY CHANGE

NO


REFACTORING

NO


EXPECTED DIFF

1~2 files
small localized change


RISK

LOW
```

---

# 4. Primary Files

Primary Files는 요구사항을 직접 구현하는 파일이다.

예:

```text
TodayShiftCard.tsx
```

AI는 가능하면 Primary Files 안에서 문제를 해결한다.

---

# 5. Secondary Files

Secondary Files는 요구사항 구현에 직접 필요할 수 있지만, Primary는 아닌 파일이다.

예:

```text
useTodayShift.ts

TodayShiftCard.test.tsx
```

Secondary File 수정은 실제 필요성이 확인되었을 때만 수행한다.

---

# 6. Potential Impact Files

영향을 받을 수 있으나 수정 대상은 아닌 파일이다.

예:

```text
Dashboard.tsx
ShiftService.ts
ShiftDTO.ts
```

이 파일들은:

```text
READ / VERIFY
```

대상이지,

자동으로:

```text
MODIFY
```

대상이 아니다.

---

# 7. Protected Areas

현재 작업에서 수정하면 안 되는 영역을 명시한다.

예:

```text
Authentication

Authorization

Database Schema

Shared API Client

Global Store

Unrelated Features
```

Protected Area를 수정해야 한다는 사실이 발견되면 즉시 Scope를 재평가한다.

---

# 8. 변경 권한 분류

각 영역에 다음 상태를 부여할 수 있다.

```text
ALLOW

CONDITIONAL

READ_ONLY

FORBIDDEN
```

예:

```text
TodayShiftCard.tsx
ALLOW

useTodayShift.ts
CONDITIONAL

ShiftService.ts
READ_ONLY

schema.prisma
FORBIDDEN
```

---

# 9. Scope 최소화

사용자가 요청한 동작을 가장 작은 수정으로 구현할 수 있으면 그 방법을 선택한다.

예:

```text
if (!nightWorker) {
  return "공석";
}
```

로 해결 가능한데:

```text
Shift API redesign
+
DTO 추가
+
DB 변경
+
새 상태관리 시스템
```

을 도입해서는 안 된다.

---

# 10. Scope Creep 금지

다음 사고방식은 금지한다.

```text
"이왕 수정하는 김에..."

"여기도 코드가 오래됐으니..."

"조금 더 깔끔하게 만들기 위해..."

"나중에 필요할 것 같아서..."

"관련 파일 전체를 정리하면 좋을 것 같다."
```

사용자 요청과 직접 연결되지 않는 변경은 기본적으로 하지 않는다.

---

# 11. Requirement Traceability

모든 변경은 다음 중 하나로 설명 가능해야 한다.

```text
USER_REQUIREMENT

BUG_ROOT_CAUSE

REQUIRED_DEPENDENCY_CHANGE

TEST_REQUIREMENT

SECURITY_REQUIREMENT

MIGRATION_REQUIREMENT
```

설명할 수 없는 변경은 제거한다.

---

# 12. Every Diff Must Have a Reason

변경된 각 파일에 대해 질문한다.

> 이 파일을 왜 수정했는가?

명확한 답이 없으면 변경하지 않는다.

예:

```text
TodayShiftCard.tsx

Reason:
야간 공석 UI 표시
```

좋음.

```text
utils/date.ts

Reason:
코드가 조금 마음에 안 들어서 정리
```

금지.

---

# 13. Diff Budget

수정 전에 예상 변경 크기를 정의한다.

예:

```text
Expected Files:
1~2

Expected LOC:
small

Expected Layers:
Frontend only
```

정확한 줄 수를 강제할 필요는 없지만 변경 규모의 예상치를 가진다.

---

# 14. Diff Budget 이상 감지

예상:

```text
2 files
```

실제 작업 중:

```text
9 files
```

이 필요해졌다면 자동으로 계속 진행하지 않는다.

먼저:

```text
왜 Scope가 증가했는가?
```

를 분석한다.

---

# 15. Scope Expansion Gate

초기 Change Contract보다 범위가 넓어질 경우 다음을 확인한다.

```text
1. 기존 계획이 잘못되었는가?

2. 숨겨진 Dependency가 발견되었는가?

3. 요구사항 충족을 위해 반드시 필요한가?

4. 더 작은 해결책은 없는가?

5. Risk가 증가했는가?

6. 추가 Policy가 필요한가?
```

---

# 16. Scope Expansion 결과

필요한 확장이라면 Change Contract를 갱신한다.

예:

초기:

```text
Frontend only
```

탐색 결과:

```text
API가 null 상태를 잘못 제거하고 있음
```

발견.

새 Contract:

```text
Frontend
+
Backend API
```

로 확장할 수 있다.

단 이유를 기록한다.

---

# 17. Policy Router 재호출

Scope 확장으로 작업 유형이 변하면 Instruction Router를 다시 적용한다.

예:

```text
UI 변경
↓
DB Schema 변경 필요 발견
```

그러면:

```text
Migration Policy
```

도 활성화한다.

---

# 18. API Change Gate

API를 수정하기 전에는 명시적으로:

```text
API_CHANGE = YES
```

상태가 되어야 한다.

기본값:

```text
NO
```

이다.

---

# 19. API 변경 전 확인

다음을 확인한다.

```text
Frontend Consumers

Other Internal Consumers

External Consumers

Request Schema

Response Schema

DTO

Validation

Authentication

Authorization

Tests
```

---

# 20. API Contract 변경 위험

다음 변경은 단순 내부 수정과 다르게 취급한다.

```text
Path 변경

HTTP Method 변경

Parameter 변경

Request Body 변경

Response Field 변경

Response Type 변경

Status Code 변경
```

가능하면 기존 Contract를 유지한다.

---

# 21. DB Change Gate

Database Schema 변경 기본값:

```text
DB_CHANGE = NO
```

이다.

실제로 필요할 경우에만:

```text
DB_CHANGE = YES
```

로 전환한다.

그 순간 Migration Policy를 활성화한다.

---

# 22. DB 수정과 Application 수정 분리

단순 로직 변경이 DB 변경 없이 가능하다면 DB를 변경하지 않는다.

금지:

```text
작은 UI 상태 하나를 위해
새 Column 추가
```

같은 불필요한 Schema 변경.

---

# 23. Dependency Change Gate

새 Package/Library 추가 기본값:

```text
DEPENDENCY_CHANGE = NO
```

이다.

새 Dependency가 필요하다고 판단하면 먼저 질문한다.

```text
기존 Dependency로 해결 가능한가?

표준 Library로 가능한가?

프로젝트 내부 Utility가 있는가?

몇 줄의 코드로 해결 가능한가?
```

---

# 24. Dependency 추가 조건

새 Dependency는 다음을 만족할 때만 고려한다.

```text
실제 기능에 필요

기존 Dependency로 대체 불가

유지보수 부담보다 가치가 큼

프로젝트 Architecture와 부합
```

Dependency 변경이 발생하면 Dependency Policy를 활성화한다.

---

# 25. Refactoring Gate

기능 구현과 Refactoring은 기본적으로 분리한다.

기본:

```text
REFACTORING = NO
```

---

# 26. 허용되는 Local Refactor

다음 정도는 기능 구현에 필수라면 허용할 수 있다.

```text
중복된 3~5줄의 단순 정리

새 조건을 넣기 위한 작은 함수 분리

관련 타입의 최소 수정
```

단 실제 요구사항 구현에 직접 필요해야 한다.

---

# 27. 별도 Refactor로 분리해야 하는 경우

다음은 별도 작업으로 분리하는 것을 기본으로 한다.

```text
파일 구조 변경

모듈 재설계

대규모 Rename

State Management 변경

Framework Pattern 변경

Shared Utility 재설계
```

---

# 28. Formatting Noise 금지

작업과 무관한 Formatting 변경을 피한다.

예:

```text
전체 파일 quote style 변경

전체 파일 indentation 변경

import 전체 reorder

파일 전체 prettier 재작성
```

특히 실제 수정 Diff를 보기 어렵게 만드는 변경을 피한다.

---

# 29. Rename Noise 금지

사용자 요구와 무관한 Rename을 하지 않는다.

예:

```text
data → shiftData
```

가 실제 기능 구현에 필요하지 않다면 그대로 둔다.

---

# 30. Comment Cleanup 금지

작업과 무관한 기존 Comment 삭제·수정도 기본적으로 하지 않는다.

---

# 31. Dead Code 발견

작업 중 Dead Code를 발견해도 자동 삭제하지 않는다.

다음 중 하나로 처리한다.

```text
현재 기능 구현에 직접 방해됨
→ 필요한 범위만 처리

현재 기능과 무관
→ 그대로 둠
```

---

# 32. 기존 버그 발견

현재 요청과 무관한 버그를 발견했다고 자동 수정하지 않는다.

대신 필요하다면:

```text
Unrelated issue discovered
```

로 기록할 수 있다.

---

# 33. Shared Code 변경

다음은 변경 전에 반드시 Impact Analysis를 수행한다.

```text
Shared Component

Shared Hook

Shared Utility

Global Store

Core Service

API Client

Base Class

Shared Type
```

---

# 34. Shared Code 대안 우선

공용 코드를 바꾸지 않고 Feature 로컬에서 해결할 수 있다면 먼저 로컬 해결책을 고려한다.

단 복제 코드가 심각해지는 경우는 예외.

---

# 35. Global Change Warning

다음 수정은 Local Change가 아니다.

```text
Global CSS

Root Layout

Global Config

Shared API Client

Global State

Base Middleware

App-level Error Handler
```

Risk를 한 단계 이상 높여 평가한다.

---

# 36. Data Flow 변경

데이터 흐름이 바뀌는 경우 다음을 확인한다.

```text
Producer

Transformer

Consumer

Error path

Empty state

Loading state
```

특정 Consumer만 보고 수정하지 않는다.

---

# 37. Behavior Preservation

사용자가 변경을 요청하지 않은 기존 Behavior는 유지한다.

예:

요구사항:

```text
야간 공석 표시
```

변경 후에도:

```text
주간 근무자 표시

근무자 이름 클릭

카드 레이아웃

API 호출 방식
```

등 기존 Behavior는 유지되어야 한다.

---

# 38. Regression Boundary

Change Contract에:

```text
Must Preserve
```

항목을 추가할 수 있다.

예:

```text
Must Preserve:

주간 근무자 표시

기존 데이터가 있을 때 야간 이름 표시

Dashboard layout
```

---

# 39. Success Criteria와 Scope 연결

Success Criteria를 충족하지 않는 변경은 의미가 없다.

반대로 Success Criteria에 필요하지 않은 변경은 의심해야 한다.

---

# 40. Minimal New Concepts

하나의 작은 요구사항을 위해 새로운 개념을 많이 추가하지 않는다.

예:

금지:

```text
new service
new factory
new interface
new provider
new adapter
```

를 단순 조건 하나를 위해 모두 생성.

---

# 41. Abstraction Threshold

새 abstraction은 다음 조건에서 고려한다.

```text
실제 반복이 존재

여러 Consumer가 실제로 사용

현재 요구사항에서 가치가 있음
```

미래 가정만으로 생성하지 않는다.

---

# 42. Feature Boundary

가능하면 변경은 현재 Feature Boundary 안에서 해결한다.

예:

```text
dashboard.todayShift
```

작업이면:

```text
dashboard.todayShift
```

관련 영역을 우선한다.

`ticket.*` 같은 다른 Feature를 건드리지 않는다.

---

# 43. Cross-Feature Change

다른 Feature 수정이 반드시 필요하면 이를 명시한다.

예:

```text
Primary Feature:
dashboard.todayShift

Affected Feature:
shift.schedule
```

Impact Analysis를 다시 수행한다.

---

# 44. User-visible Behavior Change

사용자 화면/동작이 추가로 변한다면 사용자 요구와 일치하는지 확인한다.

요청하지 않은 UX 변경을 피한다.

---

# 45. Error Behavior Change

정상 Flow만 아니라 Error Flow 변경도 Scope에 포함한다.

예:

기존:

```text
API 오류 → Error message
```

수정 후:

```text
API 오류 → "공석"
```

처럼 실제 장애를 정상 Empty State처럼 숨기면 안 된다.

---

# 46. Empty State와 Error State 구분

특히 UI 수정 시:

```text
No Data
```

와:

```text
Failed to Load Data
```

를 혼동하지 않는다.

---

# 47. Security Boundary

다음 영역을 수정하게 되면 기존 Change Contract를 유지한 채 강행하지 않는다.

```text
Auth

Permission

IAM

Session

Token

Secret

Validation

SQL

File Upload
```

Instruction Router를 다시 호출하고 Security Policy를 활성화한다.

---

# 48. Production Boundary

Production 배포/환경 설정까지 변경 범위가 커지면 별도의 Risk로 취급한다.

코드 변경과 Production 변경을 하나의 작은 작업으로 취급하지 않는다.

---

# 49. Generated Files

자동 생성 파일은 가능하면 직접 편집하지 않는다.

예:

```text
generated client

build output

lock-derived artifact

code map output
```

Source 파일 또는 generator를 수정한 뒤 재생성한다.

---

# 50. Lock File

Dependency가 실제로 변경되지 않았다면 lock file을 불필요하게 수정하지 않는다.

---

# 51. Config Files

다음 파일은 영향 범위가 클 수 있다.

```text
package.json

tsconfig.json

vite.config.*

webpack.*

eslint.*

.env*

Dockerfile

CI config
```

단순 Feature 작업에서 임의 수정하지 않는다.

---

# 52. Test Code도 Scope 대상

테스트 파일이라고 해서 마음대로 수정하지 않는다.

금지:

```text
테스트 실패
↓
기대값을 새 잘못된 동작에 맞춰 수정
```

테스트가 잘못되었음을 근거로 확인한 경우에만 기대값을 변경한다.

---

# 53. Never Delete Failing Tests to Pass

실패하는 테스트를 삭제하거나 skip 처리해서 작업을 완료하지 않는다.

---

# 54. Implementation Drift Detection

작업 중 주기적으로 확인한다.

```text
현재 변경이 여전히 원래 Goal과 직접 연결되는가?
```

NO라면 작업 방향을 재평가한다.

---

# 55. Change Contract Reconciliation

구현 완료 후 실제 Diff와 초기 Contract를 비교한다.

```text
Expected Files
vs
Actual Files

Expected Layers
vs
Actual Layers

Expected API Change
vs
Actual

Expected DB Change
vs
Actual
```

---

# 56. Unexpected Diff

예상하지 않은 파일이 수정된 경우 반드시 이유를 확인한다.

```text
왜 변경되었는가?

필요한가?

자동 생성 결과인가?

도구가 formatting을 바꿨는가?
```

불필요하면 되돌린다.

---

# 57. Git Diff Review

가능하면 완료 전 실제 Diff를 검토한다.

```text
git diff
```

또는 동등한 기능 사용.

검토:

```text
Unrelated Changes

Debug Code

Temporary Logs

Secrets

Commented-out Code

Unexpected Config Changes
```

# 58. Debug Artifact 제거

완료 전에 제거한다.

```text
console.log

temporary print

debug flag

test-only bypass

temporary hardcoded value
```

단 의도된 Logging은 제외.

# 59. Temporary Workaround

임시 Workaround가 필요하다면 영구적인 정상 해결인 것처럼 보고하지 않는다.

상태를 명확히 한다.

---

# 60. Change Risk 재평가

구현 완료 후에도 Risk를 다시 평가한다.

초기:

```text
LOW
```

였더라도 실제:

```text
Shared Hook 수정
```

이면:

```text
MEDIUM
```

으로 바뀔 수 있다.

Verification 범위를 Risk에 맞춰 확대한다.

---

# 61. Compact Mode

LOW Risk 작업에서는 Change Control 전체 절차를 축소할 수 있다.

최소:

```text
Goal

Target File

Forbidden Scope

API/DB/Dependency change 여부

Expected Diff
```

정도만 확인한다.

---

# 62. Standard Mode

MEDIUM Risk 이상:

```text
Full Change Contract
+
Impact Analysis
+
Diff Review
```

를 사용한다.

---

# 63. Enhanced Mode

HIGH/CRITICAL Risk:

```text
Full Change Contract

Impact Analysis

Explicit Protected Areas

Rollback consideration

Independent Review

Enhanced Verification
```

을 사용한다.

# 66. Change Contract는 사용자 승인서가 아니다

내부적으로 사용하는 작업 통제 구조다.

모든 변경에서 사용자에게 Contract 전체를 보여주거나 별도 승인을 받을 필요는 없다.

단 위험한 Scope Expansion이나 사용자 요구를 실질적으로 바꾸는 경우에는 명확히 알려야 한다.

---

# 67. Agent Delegation과 Change Contract

Multi-Agent Harness를 사용하는 경우에도 Change Contract는 Parent/Orchestrator가 관리한다.

Subagent에게는 필요한 부분만 전달한다.

예:

```text
Allowed Files:
TodayShiftCard.tsx

Read-only:
useTodayShift.ts

Forbidden:
Backend
DB
```

---

# 68. Subagent Scope

Subagent는 자신의 Task Packet 범위를 넘어 수정하지 않는다.

추가 수정 필요성을 발견하면:

```text
REQUEST_SCOPE_EXPANSION
```

상태로 반환한다.

직접 확장하지 않는다.

---

# 69. Parallel Agent 충돌 방지

두 Agent가 동일 파일을 동시에 수정하지 않도록 가능하면 파일 Ownership을 분리한다.

예:

```text
Agent A
Frontend

Agent B
Tests
```

---

# 70. Modification Ownership

복잡한 Harness 환경에서는 각 파일에 Temporary Owner를 둘 수 있다.

```text
TodayShiftCard.tsx
→ IMPLEMENTER_A

today-shift.spec.ts
→ IMPLEMENTER_B
```

충돌 가능성을 줄인다.

---

# 71. No Hidden Scope Expansion

AI가 내부적으로만 Scope를 확장해놓고 최종 결과에서 숨기지 않는다.

중요한 범위 변경은 최종 보고에 나타나야 한다.

# 74. Definition of Controlled Change

다음 조건을 만족하면 Change Control을 통과한 것으로 본다.

```text
[ ] Goal과 모든 Diff가 연결됨

[ ] Primary Scope가 명확함

[ ] 불필요한 파일 변경 없음

[ ] API 변화가 사전에 식별됨

[ ] DB 변화가 사전에 식별됨

[ ] Dependency 변화가 사전에 식별됨

[ ] Refactor 범위가 통제됨

[ ] Protected Area 위반 없음

[ ] Scope Expansion이 정당화됨

[ ] Actual Diff가 최종 검토됨
```

---

# 75. 실패 조건

다음은 Change Control 실패로 본다.

```text
작은 요청인데 대규모 Diff

왜 변경됐는지 설명 못하는 파일 존재

사용자 요청과 무관한 Refactor

몰래 API Contract 변경

몰래 DB Schema 변경

몰래 Package 추가

테스트를 삭제해 성공 처리

Auth/Security 영역을 일반 변경처럼 처리

Generated File 직접 수정

작업 후 Diff를 확인하지 않음
```

---

# 76. 작업 완료 후 Verification으로 전달

Change Control은 코드가 올바르다는 것을 증명하는 Policy가 아니다.

담당:

```text
무엇을 바꿀 수 있는가?
```

Verification Policy 담당:

```text
바꾼 것이 실제로 맞는가?
```

따라서 구현 완료 후:

```text
Change Control
↓
Verification Policy
```

로 제어권을 넘긴다.

# 77. Instruction Router 연동

Router는 다음 상황에서 Change Control을 활성화한다.


유지:

```text
Final Change Contract

Actual Changed Files

Risk
```

# 81. 최종 압축 지침

전체 문서를 매번 로드하기 어렵다면 다음 Core만 사용한다.

```text
CHANGE CONTROL CORE

Before modifying code:

1. Define the exact goal and success criteria.
2. Identify primary files, secondary files, and protected areas.
3. Default API, DB, dependency, and refactoring changes to NO.
4. Define an expected diff scope before editing.
5. Every changed file must have a direct reason traceable to the requirement.
6. Do not perform unrelated cleanup, formatting, renaming, or refactoring.
7. Treat shared code, global config, API contracts, DB schemas, and security boundaries as scope escalation.
8. If actual scope exceeds expected scope, stop and re-evaluate before continuing.
9. Activate additional policies when a new risk boundary is crossed.
10. Review the final diff and remove unrelated changes.
11. Preserve existing behavior that the user did not request to change.
12. A controlled change is the smallest justified diff that satisfies the success criteria.
```

# 82. Final Principle

> 좋은 수정은 가장 많은 코드를 개선하는 수정이 아니다.

> 좋은 수정은 요구사항을 만족시키기 위해 반드시 필요한 코드만 정확하게 변경하는 수정이다.

따라서 모든 변경은 다음 구조를 따른다.

```text
Know the Goal

↓

Define the Boundary

↓

Change the Minimum

↓

Detect Scope Drift

↓

Review the Diff

↓

Verify the Result
```
