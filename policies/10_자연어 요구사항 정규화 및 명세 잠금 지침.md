# Requirement Canonicalization & Spec Lock Policy v1

## 자연어 요구사항 정규화·명세 고정·변경 통제 지침

Version: 1.0

---

# 0. 목적

이 Policy는 사용자의 자연어 요청을 AI가 작업 중 계속 다르게 해석하는 문제를 방지한다.

자연어 요청은 다음 특성을 가질 수 있다.

```text id="ywrdpi"
모호함

상대적 표현

주관적 표현

범위 불명확

성공 기준 부재

서로 충돌하는 요구

숨겨진 전제
```

따라서 실제 구현 전에 다음 흐름을 따른다.

```text id="1sj0g2"
USER REQUEST

↓

EXTRACT REQUIREMENTS

↓

RESOLVE AMBIGUITY

↓

QUANTIFY / CALIBRATE

↓

DEFINE SCOPE

↓

DEFINE SUCCESS CRITERIA

↓

CANONICAL SPEC

↓

SPEC LOCK

↓

IMPLEMENT

↓

VERIFY AGAINST LOCKED SPEC
```

핵심 목표:

> 사용자가 말한 것을 AI가 매 단계마다 다시 해석하는 것이 아니라, 한 번 정확하게 해석한 뒤 그 결과를 작업의 기준점으로 고정한다.

---

# 1. 최상위 원칙

자연어 원문은 요구의 출발점이다.

그러나 실제 구현 기준은:

```text id="4hhwuf"
LOCKED CANONICAL SPEC
```

이다.

즉:

```text id="do9fww"
Original Request
→ Meaning Resolution
→ Canonical Spec
→ Locked Requirement
```

순서로 변환한다.

---

# 2. 왜 Spec Lock이 필요한가

사용자:

```text id="eztxym"
대시보드를 조금 더 깔끔하게 해줘.
```

AI가 작업을 시작한 뒤:

```text id="u9o0kl"
카드 간격도 줄이고

Sidebar도 바꾸고

색상도 변경하고

Header도 재설계하고

Animation도 추가
```

하는 것은 위험하다.

처음에 Scope를:

```text id="0dsmae"
Dashboard 본문 Card 영역만
```

으로 확정했다면 이후 임의로 확장하지 않는다.

---

# 3. Canonicalization이란

사용자의 표현을 기계적으로 실행 가능한 구조로 바꾸는 과정이다.

예:

사용자:

```text id="f7fq5v"
카드를 조금 작게 하고
중요한 장애는 더 눈에 띄게 해줘.
```

Canonicalization:

```text id="w0nhmk"
Target:
Dashboard incident cards

Card Height:
160px → 136px

Critical Incident:
font-weight 700
status icon visible
existing critical color token 유지

Scope:
Dashboard cards only

Do Not Change:
Sidebar
Header
API
DB

Success:
1440px 화면에서 정보 잘림 없음
Critical 상태가 Normal 상태보다 명확하게 구분됨
```

---

# 4. Canonical Spec의 역할

Canonical Spec은 다음 Policy들의 공통 입력이 된다.

```text id="t13wjl"
Change Control

Verification

Multi-Agent Task Packet

Checkpoint

Handoff

Error Learning
```

---

# 5. Requirement Extraction

원래 요청에서 다음 정보를 추출한다.

```text id="zixxai"
Target

Desired Behavior

Current Problem

Scope

Constraints

Priority

Success Criteria

Do Not Change

Unknowns

Assumptions
```

---

# 6. Target

무엇을 변경하는가?

예:

```text id="dgj3vd"
Dashboard

TodayShiftCard

Ticket Assignment

API Response

Shift Pattern Engine
```

Target은 가능한 한 구체적이어야 한다.

---

# 7. Desired Behavior

변경 후 원하는 동작을 정의한다.

나쁜 예:

```text id="045smt"
더 좋게
```

좋은 예:

```text id="zrbndv"
야간 근무자가 없으면
"공석"을 표시한다.
```

---

# 8. Current Problem

가능하면 현재 동작도 기록한다.

```text id="scyo9b"
Current:
야간 근무자가 없으면 "-"
```

```text id="lxr1w0"
Desired:
"공석"
```

Before / After 구조가 좋다.

---

# 9. Scope

어디까지 적용하는가?

예:

```text id="jmvydh"
Current Component only

Current Page

Current Feature

Application-wide
```

---

# 10. Explicit Non-Scope

무엇을 바꾸지 않는지도 중요하다.

예:

```text id="5tuwtm"
Do Not Change:

Sidebar

API

DB

Permission

Mobile Layout
```

---

# 11. Constraint

반드시 지켜야 하는 조건.

예:

```text id="9qk7xa"
기존 API Response 유지

추가 Dependency 금지

Desktop 1440 기준

기존 Design Token 사용
```

---

# 12. Priority

요구가 여러 개라면 우선순위를 정의한다.

예:

```text id="tnhh4z"
P1 상태 인지

P2 가독성

P3 정보 밀도

P4 시각적 장식
```

---

# 13. Success Criteria

완료 여부를 판단할 수 있어야 한다.

예:

```text id="6ussf6"
[ ] 근무자 없음 → 공석

[ ] 근무자 있음 → 기존 이름

[ ] API 오류 → 오류 상태

[ ] 주간 근무 표시 유지
```

---

# 14. Requirement Type

각 요구를 다음처럼 분류할 수 있다.

```text id="h6wgzy"
FUNCTIONAL

NON_FUNCTIONAL

VISUAL

PERFORMANCE

SECURITY

COMPATIBILITY

CONSTRAINT

OUT_OF_SCOPE
```

---

# 15. Functional Requirement

예:

```text id="oqm2gr"
관리자만 승인 버튼을 볼 수 있다.
```

---

# 16. Non-Functional Requirement

예:

```text id="xwwmzm"
검색 응답시간 P95 <= 1.5초
```

---

# 17. Visual Requirement

예:

```text id="mlvnu5"
Card gap 24px → 16px
```

---

# 18. Compatibility Requirement

예:

```text id="xfbkbd"
기존 API Consumer가 깨지지 않아야 한다.
```

---

# 19. Requirement ID

복잡한 Spec에서는 각 요구에 ID를 부여할 수 있다.

```text id="6y7w8v"
REQ-001

REQ-002

REQ-003
```

예:

```text id="p9fv27"
REQ-001
야간 근무자 없음 → 공석

REQ-002
API 오류 → 오류 상태 유지

REQ-003
주간 근무 표시 변경 금지
```

---

# 20. Traceability

각 구현과 테스트를 Requirement ID에 연결할 수 있다.

예:

```text id="7c5x9e"
REQ-001
→ TodayShiftCard.tsx
→ test: shows vacant state
```

---

# 21. Requirement Source

각 요구가 어디서 왔는지도 구분할 수 있다.

```text id="zdy06j"
USER_EXPLICIT

USER_CONFIRMED

PROJECT_CONVENTION

DERIVED

ASSUMPTION
```

---

# 22. USER_EXPLICIT

사용자가 직접 명시.

가장 높은 신뢰도.

---

# 23. USER_CONFIRMED

Grill 과정에서 사용자가 선택.

예:

```text id="vw953h"
136px 선택
```

---

# 24. PROJECT_CONVENTION

프로젝트 표준으로 자동 해결.

예:

```text id="6j6gek"
Button M → L
```

---

# 25. DERIVED

다른 요구를 충족하기 위해 필수적으로 도출된 요구.

예:

```text id="853yjf"
기존 API Contract 유지
```

때문에:

```text id="uxunxw"
Frontend-only implementation
```

이 도출됨.

---

# 26. ASSUMPTION

AI가 임시로 선택한 값.

Material하면 Grill 대상.

---

# 27. Confidence

각 항목에 필요한 경우 상태를 둔다.

```text id="cvzlid"
LOCKED

PROVISIONAL

ASSUMED

UNRESOLVED
```

---

# 28. LOCKED

명확하게 확정.

작업 중 임의 변경 금지.

---

# 29. PROVISIONAL

낮은 위험의 기본값.

새 정보가 나오면 변경 가능.

---

# 30. ASSUMED

근거가 약한 임시 가정.

가능하면 줄인다.

---

# 31. UNRESOLVED

중요한 미확정 항목.

결과를 크게 바꾸면 구현 전에 해결한다.

---

# 32. Ambiguity Policy 연동

Canonicalization 전에 모호한 표현을 해소한다.

예:

```text id="s02g7c"
"조금 작게"
```

↓

```text id="s3djb6"
160px → 136px
```

---

# 33. Subjective Requirement

예:

```text id="byngkl"
"고급스럽게"
```

↓

```text id="ln849g"
Enterprise Premium 방향

- navy/gray
- restrained accents
- minimal decoration
- strong hierarchy
```

처럼 해석을 고정한다.

---

# 34. 같은 표현을 작업 중 재해석 금지

한 번:

```text id="83dts5"
깔끔함
=
정보 밀도 유지 + 장식 감소
```

로 확정했다면 작업 중:

```text id="rkrrk4"
깔끔함
=
정보량 절반으로 감소
```

로 바꾸지 않는다.

---

# 35. Spec Lock

Canonical Spec이 충분히 확정되면:

```text id="z9b8nh"
SPEC_STATUS = LOCKED
```

로 전환한다.

---

# 36. Lock 조건

다음에 답할 수 있으면 Lock 가능하다.

```text id="9lm1fb"
무엇을 바꾸는가?

어디까지 바꾸는가?

어떻게 바뀌는가?

무엇을 바꾸지 않는가?

무엇이 성공인가?

중요한 미확정 사항이 있는가?
```

---

# 37. 모든 세부사항이 확정될 필요는 없다

작은 구현 세부사항까지 모두 Lock하지 않는다.

예:

```text id="bhgccu"
내부 변수명

함수 내부 코드 순서

Test fixture 이름
```

등은 프로젝트 Convention에 맡긴다.

---

# 38. Lock 대상

결과를 실질적으로 바꾸는 항목을 Lock한다.

```text id="wpgpuq"
Scope

Behavior

Performance Target

Visual Direction

API Contract

DB Impact

Security Boundary

User-visible Output
```

---

# 39. Silent Spec Change 금지

AI가 작업 중:

```text id="kfzniu"
이게 더 좋아 보여서
```

Spec을 변경해서는 안 된다.

---

# 40. Spec Change Trigger

다음 상황에서는 Spec 변경을 고려할 수 있다.

```text id="657edn"
새로운 필수 Dependency 발견

현재 Spec이 기술적으로 불가능

사용자 요구끼리 충돌

Security 문제 발견

기존 Architecture와 치명적 충돌

사용자가 요구 변경
```

---

# 41. Spec Change Request

변경 시 내부적으로 다음을 만든다.

```text id="yn7hsx"
SPEC CHANGE

Original:
...

New:
...

Reason:
...

Impact:
...

Risk:
...
```

---

# 42. Minor Spec Change

낮은 위험이고 결과 의미가 거의 같으면 내부적으로 갱신 가능.

예:

```text id="thnykz"
136px → Design Token상 134px
```

단 Design System 강제 때문이라는 근거가 있어야 한다.

---

# 43. Material Spec Change

다음은 중요한 변경이다.

```text id="647g4m"
Frontend only
→ Backend 변경 필요

No DB change
→ Schema change

Current page
→ Application-wide

Local auth
→ Global permission model
```

Router 및 Change Control을 다시 실행한다.

---

# 44. User Authority

Spec 충돌 시 우선순위:

```text id="s4gcrt"
현재 사용자의 명시적 요구

>

사용자가 확정한 Spec

>

프로젝트의 강제 Constraint

>

기존 Convention

>

AI 추천
```

안전/보안상 강제 제약은 별도로 우선한다.

---

# 45. AI 추천은 Spec이 아니다

AI:

```text id="iqv8io"

```

```text id="c8hkk4"

```


# 49. 예시 — 기능 변경


# 53. Negative Requirement

`하지 말아야 하는 것`도 정식 Requirement로 취급한다.

예:

```text id="bk2994"
REQ-004
API Response Schema 변경 금지
```

---

# 54. Must Preserve

기존 기능 중 유지해야 하는 동작.

예:

```text id="sytrol"
주간 근무 표시

기존 클릭 동작

현재 permission behavior
```

---

# 55. Out of Scope

이번 작업에서 다루지 않는 항목.

예:

```text id="dqka6q"
Mobile layout

Analytics

Admin page
```

---

# 56. Do Not Change와 Out of Scope 차이

Out of Scope:

```text id="lfwpar"
이번 작업 대상이 아님
```

Do Not Change:

```text id="pehpsp"
명시적으로 변경 금지
```

후자가 더 강한 제약이다.

---

# 57. Constraint와 Requirement 차이

Requirement:

```text id="2bermq"
해야 하는 것
```

Constraint:

```text id="gpgi0j"
그 과정에서 지켜야 하는 조건
```

---

# 58. Conflict Detection

Spec 작성 중 요구끼리 충돌하는지 확인한다.

예:

```text id="47u84v"
정보량 최대화

+

모든 여백 크게
```

충돌 가능.

---

# 59. Conflict Resolution

임의로 중간값을 선택하지 않는다.

```text id="s4z9hb"
Priority

Trade-off

Alternative
```

중 하나로 해결한다.

---

# 60. Requirement Consistency Check

Lock 전 확인:

```text id="z2d02k"
Scope와 Do Not Change 충돌?

Success Criteria가 Requirement와 일치?

Performance target이 현실적인가?

API 변경 금지인데 API requirement 있음?

DB 변경 금지인데 새 저장 필드 요구?
```

---

# 61. Feasibility Check

Lock 전에 기술적으로 가능한지 최소 확인한다.

단 전체 구현을 미리 하지 않는다.

---

# 62. Impossible Requirement

현재 제약으로 불가능하면 그대로 Lock하지 않는다.

예:

```text id="3kxptc"
No Backend Change

+

새로운 서버 데이터 필요
```

이면 충돌을 해결한다.

---

# 63. Spec Version

Spec에 Version을 둘 수 있다.

```text id="sqrazm"
SPEC-012 v1

SPEC-012 v2
```

---

# 64. Version 증가 조건

Material Spec Change가 발생하면 Version 증가.

사소한 표현 수정은 필요 없을 수 있다.

---

# 65. Spec History

복잡한 프로젝트에서는 중요한 Spec 변경 이유를 남긴다.

예:

```text id="40hi7z"
v1:
Frontend only

v2:
Backend validation 추가

Reason:
```

# 141. 최종 압축 Core 지침

```text id="2yjgqs"
REQUIREMENT CANONICALIZATION / SPEC LOCK CORE

1. Do not implement material natural-language requirements directly when their meaning remains ambiguous.
2. Extract target, desired behavior, current behavior, scope, constraints, priorities, success criteria, and important non-goals.
3. Resolve material ambiguity using existing specs, conventions, measurable values, or the Grill Protocol.
4. Convert vague requirements into measurable values or concrete calibrated interpretations whenever possible.
5. Create a minimal sufficient canonical specification before non-trivial implementation.
6. Preserve explicit user constraints and "do not change" instructions in the canonical spec.
7. Separate requirements, constraints, assumptions, out-of-scope items, and must-preserve behaviors.
8. Use LOCKED, PROVISIONAL, ASSUMED, and UNRESOLVED states where useful.
9. Lock all material requirements before implementation; do not silently reinterpret them later.
10. Any material spec change must have a reason and must trigger scope/risk re-evaluation when appropriate.
11. Use the locked spec as the source for Change Control, Task Packets, Verification, Checkpoints, and Handoffs.
12. Every meaningful code change should be traceable to a requirement, and every required behavior should be implemented and verified.
13. Keep specs proportional to task size: compact for small changes, structured and versioned for complex work.
14. The goal is minimum sufficient precision, not exhaustive documentation.
15. Completion is judged against the latest locked specification, not against the agent's evolving interpretation of the original request.
```

# 142. Final Principle

> 사용자의 자연어는 의도를 전달한다.

> Canonical Spec은 그 의도를 실행 가능한 형태로 고정한다.

따라서:

```text id="87y715"
UNDERSTAND

↓

RESOLVE

↓

CANONICALIZE

↓

LOCK

↓

IMPLEMENT

↓

TRACE

↓

VERIFY
```

를 따른다.

가장 중요한 원칙은:

> **작업을 시작한 뒤 요구사항의 뜻이 AI의 판단에 따라 움직이지 않아야 한다.**

한 번 정확하게 확정된 요구는 작업의 끝까지 동일한 기준으로 유지되어야 한다.
