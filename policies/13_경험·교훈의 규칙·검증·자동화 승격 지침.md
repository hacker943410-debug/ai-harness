# Lesson → Rule → Automation Promotion Policy v1

## 경험 승격·자동화·폐기·Harness 진화 지침

Version: 1.0

---

# 0. 목적

이 Policy는 작업 중 발견된 실수, 교훈, 반복 문제를 단순한 `LESSON` 파일로 계속 쌓아두지 않고 적절한 수준의 재발 방지 장치로 승격시키기 위한 정책이다.

기본 흐름:

```text
FAILURE / CORRECTION
        ↓
      LESSON
        ↓
재발 가능성 / 위험도 평가
        ↓
       RULE
        ↓
기계적 검증 가능?
   ├─ NO → POLICY / CHECKLIST
   └─ YES
        ↓
       TEST
        ↓
    VALIDATOR
        ↓
    CI GUARDRAIL
        ↓
ARCHITECTURAL PREVENTION
```

궁극적인 목표:

> AI에게 기억해야 할 규칙을 계속 늘리는 것이 아니라, 가능한 규칙을 실행 가능한 보호 장치로 변환한다.

---

# 1. 핵심 원칙

가장 중요한 원칙:

> Prompt에 적어둔 규칙보다 자동으로 실패를 검출하는 Test가 강하다.

> Test보다 변경 자체를 막는 Validator가 강하다.

> Validator보다 잘못된 상태를 구조적으로 만들 수 없게 하는 Architecture가 더 강하다.

따라서 가능한 경우:

```text
MEMORY
↓
RULE
↓
CHECK
↓
AUTOMATION
↓
STRUCTURAL PREVENTION
```

방향으로 진화한다.

---

# 2. 이 Policy가 필요한 이유

Error Learning만 사용하면 시간이 지나면서 다음과 같은 문제가 생길 수 있다.

```text
LESSON-001

LESSON-002

LESSON-003

...

LESSON-247
```

Lesson이 많아질수록:

```text
검색 비용 증가

Context 증가

비슷한 Rule 중복

충돌하는 교훈 발생

오래된 Rule 누적

Agent가 모든 Rule을 읽지 못함
```

문제가 생긴다.

따라서 Lesson Store 자체가 최종 목적이 되어서는 안 된다.

---

# 3. 목표 상태

좋지 않은 Harness:

```text
과거 실수 300개

↓

AGENTS.md 20,000줄

↓

AI가 매 작업마다 모두 읽음
```

좋은 Harness:

```text
과거 실수 300개
       ↓
중복 제거 / 일반화
       ↓
Rule 30개
       ↓
Test / Validator 20개
       ↓
항상 필요한 Core Rule 5개
```

이다.

---

# 4. Promotion Level

재발 방지 수준을 다음 단계로 구분한다.

```text
L0 — TASK NOTE

L1 — LESSON

L2 — RULE

L3 — CHECKLIST / GATE

L4 — REGRESSION TEST

L5 — STATIC / DETERMINISTIC VALIDATOR

L6 — CI / PRE-COMMIT GUARDRAIL

L7 — ARCHITECTURAL PREVENTION
```

---

# 5. L0 — Task Note

일회성 정보.

예:

```text
이번 테스트 환경에서
포트 5173이 이미 사용 중이었다.
```

재발 가능성이 낮거나 프로젝트 일반 규칙으로 만들 가치가 없으면 Task Note로 끝낸다.

영구 Lesson을 만들지 않는다.

---

# 6. L1 — Lesson

재사용 가능성이 있는 경험.

예:

```text
Empty State와 API Error를
같은 null 상태로 처리해 장애를 숨겼다.
```

다음 유사 작업에서 참고 가치가 있다.

---

# 7. L2 — Rule

앞으로 반드시 지켜야 할 행동 규칙.

예:

```text
RULE:

Empty State와 Transport Error는
별도 상태로 처리한다.
```

Lesson은 과거 사건 중심이고 Rule은 미래 행동 중심이다.

---

# 8. L3 — Checklist / Gate

Agent가 작업 단계에서 반드시 확인해야 하는 항목.

예:

```text
Shared Hook Modification Gate

[ ] Consumer 확인
[ ] Impact Map 확인
[ ] 관련 Test 확인
```

Rule을 실행 절차로 만든 상태다.

---

# 9. L4 — Regression Test

특정 오류를 자동으로 재현하고 방지할 수 있다.

예:

```text
API request failure

→ "공석"이 아닌 Error 표시
```

테스트가 실패하면 과거 버그가 재발했음을 자동 탐지한다.

---

# 10. L5 — Validator

여러 파일이나 구조를 기계적으로 검사한다.

예:

```text
Shared Hook 변경

↓

find_references 실행 여부

↓

영향 Consumer Test 존재 여부
```

또는:

```text
금지된 직접 axios 사용 탐지
```

---

# 11. L6 — CI Guardrail

문제가 Repository에 들어가기 전에 자동 차단한다.

예:

```text
PR

↓

API Contract Validator

↓

BREAKING CHANGE

↓

CI FAIL
```

Agent가 Rule을 기억하지 않아도 Merge가 차단된다.

---

# 12. L7 — Architectural Prevention

잘못된 구현 자체를 어렵거나 불가능하게 만든다.

예:

기존:

```text
각 Controller가 직접 권한 검사
```

실수가 반복됨.

개선:

```text
Global Authorization Guard
```

이후 Controller 작성자가 권한 검사를 빼먹을 가능성을 구조적으로 줄인다.

---

# 13. 무조건 최고 단계까지 올리지 않는다

모든 Lesson을:

```text
Architecture Constraint
```

까지 올릴 필요는 없다.

승격 비용과 위험을 고려한다.

---

# 14. Promotion 판단 기준

다음 요소를 평가한다.

```text
RECURRENCE
재발 가능성

SEVERITY
발생 시 영향

DETECTABILITY
기계적으로 감지 가능한가

GENERALITY
여러 작업에 적용 가능한가

AUTOMATION_COST
자동화 비용

FALSE_POSITIVE_RISK
잘못 차단할 가능성

RECOVERY_COST
재발 후 복구 비용
```

---

# 15. 간단한 승격 판단

```text
재발 가능성 높음
+
영향 큼
+
자동 검증 가능
```

이라면 강한 자동화 후보이다.

---

# 16. Promotion Priority

대략적인 우선순위:

```text
High recurrence + High impact
→ 즉시 자동화 고려

High impact + Low recurrence
→ Guardrail 고려

High recurrence + Low impact
→ Rule / Linter 고려

Low recurrence + Low impact
→ Lesson 또는 기록 안 함
```

---

# 17. Severity Matrix

기본 Severity:

```text
S1 — LOW

S2 — MEDIUM

S3 — HIGH

S4 — CRITICAL
```

---

# 18. S1 Promotion

예:

```text
Formatting 불일치

작은 Naming 문제
```

대부분:

```text
Formatter

Linter

Convention
```

수준으로 처리한다.

Lesson으로 계속 쌓지 않는다.

---

# 19. S2 Promotion

예:

```text
Feature의 일반 Bug

Scope Drift

일반 Regression
```

권장:

```text
Lesson

+

Regression Test
```

또는 반복되면 Rule로 승격.

---

# 20. S3 Promotion

예:

```text
Shared API Regression

DB Migration 문제

Cross-feature 영향 누락

중요 사용자 요구 위반
```

권장:

```text
Rule

+

Test

+

Gate 또는 Validator
```

를 적극 검토한다.

---

# 21. S4 Promotion

예:

```text
Auth bypass

권한 상승

Production data loss

Secret 노출

결제 계산 오류
```

첫 발생이라도:

```text
Hard Guardrail

Independent Verification

Automated Check

Architectural Prevention
```

을 검토한다.

반복 횟수를 기다리지 않는다.

# 22. Occurrence Count

Lesson에는 반복 횟수를 기록할 수 있다.

예:

```text
Occurrences: 1
```

재발:

```text
Occurrences: 2
```

다시:

```text
Occurrences: 3
```

---

# 23. 반복 기준

일반적으로:

```text
1회
→ Lesson 후보

2회
→ Rule 승격 적극 검토

3회 이상
→ 자동화 가능한지 반드시 검토
```

할 수 있다.

단 절대 법칙은 아니다.

---

# 24. Critical Exception

다음은 첫 번째 사고만으로도 자동화 가능하다.

```text
데이터 삭제

Secret leakage

Auth bypass

Production destructive action
```

# 25. Promotion Score

필요하면 내부적으로 다음과 같은 간단한 Score를 사용할 수 있다.

```text
Promotion Score =

Recurrence
+
Severity
+
Generality
+
Detectability
+
Recovery Cost
-
Automation Cost
-
False Positive Risk
```

고정 수학 공식으로 사용할 필요는 없다.

판단 구조를 제공하기 위한 개념이다.

---

# 26. Rule Promotion 조건

Lesson을 Rule로 승격하기 전에 질문한다.

```text
이 교훈이 특정 사건에만 해당하는가?

아니면 앞으로 반복 적용할 수 있는가?
```

반복 적용할 수 있어야 Rule 가치가 있다.

---

# 27. 좋은 Rule

```text
Shared Hook 수정 전
모든 Consumer를 확인한다.
```

---

# 28. 나쁜 Rule

```text
useShiftData.ts를 수정할 때 조심한다.
```

너무 구체적이다.

---

# 29. 지나치게 일반적인 Rule도 피한다

나쁜 예:

```text
버그를 만들지 않는다.

항상 잘 확인한다.

코드를 신중하게 작성한다.
```

Agent의 행동을 바꾸지 못한다.

---

# 30. Rule에는 Trigger가 필요하다

모든 Rule은 가능하면:

```text

THEN
```

구조를 가진다.

예:

```text
WHEN:
Shared Hook 변경

THEN:
Impact Analysis 실행
```


# 33. Rule Example

```text

RULE-007

Title:
Shared Hook 변경 전 영향 확인

Trigger:
shared-hook modification

Required Action:

Forbidden Action:
Consumer 확인 없이 수정

Reason:
과거 두 차례 다른 Feature Regression 발생

Origin:
LESSON-014
LESSON-021

Automation:
shared-impact-validator
```

---

# 34. Lesson을 Rule로 승격하면 중복 Context를 줄인다

승격 전:

```text
LESSON-014

LESSON-032
```

모두 비슷한 내용.

승격 후:

```text
RULE-007
```

하나만 적용한다.

---

# 35. Lesson Status 변경

Rule로 승격하면 기존 Lesson:

```text
ACTIVE
```

↓

```text
PROMOTED
```

로 바꿀 수 있다.

---

# 36. PROMOTED Lesson Recall

이미 Rule로 승격된 Lesson 원문은 일반 작업에서 다시 Context에 넣지 않는다.

필요하면 역사적 근거로만 참조한다.

---

# 37. Rule과 Policy 구분

Rule:

```text
특정 Trigger에 따른 간단한 행동
```

Policy:

```text
여러 Rule과 절차를 포함하는 체계적 지침
```

이다.

---

# 38. Policy Promotion

관련 Rule이 여러 개 모이면 별도 Policy로 승격할 수 있다.

예:

```text
RULE:
외부 API 버전 확인

RULE:
기존 usage 확인

RULE:
공식 문서 확인

RULE:
새 dependency 최소화
```

↓

```text
Dependency / External Contract Policy
```

---

# 39. Policy 생성 조건

다음 상황이면 별도 Policy 가치가 있다.

```text
같은 Domain Rule이 여러 개 존재

특정 단계의 Workflow를 구성

고위험 작업

조건부로만 필요한 지침
```

---

# 40. Core Policy에 바로 넣지 않는다

새 Lesson 하나가 생겼다고:

```text
CORE.md
```

에 바로 추가하지 않는다.

Core Context 비대화를 막는다.

---

# 41. Core Rule 승격 기준

다음 조건을 거의 모두 만족해야 한다.

```text
거의 모든 작업에 적용

짧게 표현 가능

높은 재발 위험

높은 중요도

Context 비용이 낮음
```

---

# 42. Local Rule 우선

특정 영역에만 적용된다면:

```text
/prisma/AGENTS.md

/src/auth/AGENTS.md

migration-policy.md
```

처럼 좁은 범위에 둔다.

---

# 43. Specific Rule Placement

예:

```text
Frontend-only Rule
→ src policy

Database Rule
→ DB policy

Test Rule
→ test policy
```

Root Core에 넣지 않는다.

# 44. Automation Candidate 판정

Rule 생성 후 반드시 질문한다.

```text
이 Rule을 AI가 읽지 않아도
기계적으로 검사할 수 있는가?
```

YES라면 Automation 후보다.

# 46. Test Promotion

실패가 입력/출력 또는 동작으로 재현 가능하면 Test로 승격한다.

예:

```text
Given:
API request failed

Then:
Error UI 표시
```

---

# 47. Regression Test Template

```text
Origin:
LESSON-001

Bug:
API failure treated as empty data.

Given:
request status = error

Expected:
Error UI

Forbidden:
"공석"

Result:
PASS / FAIL
```

---

# 48. Test는 Lesson의 실행 가능한 형태

Lesson:

```text
오류와 Empty를 구분해야 한다.
```

Test:

```text
오류일 때 "공석"이 나오면 실패.
```

후자가 훨씬 강하다.

---

# 49. Test를 만들 수 없는 경우

모든 Rule이 Test로 표현되지는 않는다.

예:

```text
대규모 Refactor 전 사용자 Scope를 확인
```

이 경우:

```text
Checklist

Change Gate

Spec Validator
```

등을 사용할 수 있다.

---

# 50. Validator Promotion

Validator는 여러 상황을 검사하는 독립적 기계 검증 도구다.

예:

```text
Code Map Validator

Spec Validator

Migration Validator

Dependency Validator

Impact Validator
```

---

# 51. Validator 예 — Code Map

과거 문제:

```text
Feature Map이 오래된 파일을 가리켜
AI가 잘못된 파일 수정
```

Lesson:

```text
Map freshness 확인 필요
```

Validator:

```text
Referenced symbol exists?

File exists?

Map git commit matches?
```

---

# 52. Validator 예 — Scope

Change Contract:

```text
Allowed:
src/dashboard/**
```

실제 Diff:

```text
src/auth/**
```

발견.

Validator:

```text
UNEXPECTED_SCOPE_CHANGE
```

로 실패시킬 수 있다.

---

# 53. Validator 예 — API Contract

기존 Schema:

```text
name: string
```

변경:

```text
username: string
```

Validator가 Breaking Change를 탐지한다.

---

# 54. Validator 예 — Dependency

Rule:

```text
직접 axios 사용 금지
```

Validator:

```text
import axios from "axios"
```

발견 시 실패.

---

# 55. Validator 예 — Generated Files

Rule:

```text
Generated file 직접 수정 금지
```

Validator가:

```text
generated/**
```

Diff를 탐지하고 generator source 변경 여부를 확인할 수 있다.

---

# 56. Validator의 False Positive

자동화는 너무 엄격해서 정상 변경까지 막을 수 있다.

따라서 반드시:

```text
False Positive Risk
```

를 평가한다.

---

# 57. Validator가 판단하기 어려운 것

예:

```text
"이 디자인이 고급스러운가?"
```

는 deterministic validator로 완전히 판단하기 어렵다.

이런 문제를 억지 자동화하지 않는다.

---

# 58. Human / AI Judgment 유지 영역

다음은 Judgment가 필요할 수 있다.

```text
Architecture trade-off

Ambiguous product intent

Novel UX decisions

Complex root cause
```

# 60. CI Promotion

Validator가 안정적으로 동작하고 중요도가 높다면 CI에 연결한다.

```text
LOCAL VALIDATOR
↓
CANARY
↓
CI WARNING
↓
CI REQUIRED
```

단계를 사용할 수 있다.

---

# 61. 바로 Blocking CI로 넣지 않을 수도 있다

새 Validator는 처음부터 Merge를 차단하면 문제가 발생할 수 있다.

먼저:

```text
Warning Mode
```

로 관찰할 수 있다.

---

# 62. Canary Phase

예:

```text
첫 20개 PR

Validator 결과 기록

False Positive 분석
```

후 안정되면 Required Gate로 승격한다.

---

# 63. CI Guardrail 예

```text
PR opened

↓

Run scope validator

Run API contract check

Run migration validator

Run affected tests

↓

Any required check fails?

YES
→ Merge blocked
```

# 64. Architectural Prevention

같은 실수가 반복되며 Rule/Test/Validator로도 자주 발생한다면 Architecture 자체를 개선한다.

---

# 65. Architecture Promotion 질문

```text
왜 매번 사람이/Agent가
이 Rule을 기억해야 하는가?

구조적으로 필요 없게 만들 수 있는가?
```

---

# 66. 예 — Auth

Before:

```text
Controller A → permission check

Controller B → permission check

Controller C → permission check
```

반복 누락 발생.

After:

```text
Global Authorization Middleware

↓

All Controllers
```

---

# 67. 예 — API Client

Before:

```text
각 Feature가 직접 fetch / axios 선택
```

규칙 위반 반복.

After:

```text
Single Approved API Client
```

구조로 강제.

---

# 68. 예 — DB Migration

Before:

```text
개발자가 Migration 절차를 기억
```

After:

```text
Migration tool

+

Schema validation

+

CI check
```

---

# 69. 예 — Design

반복되는:

```text
Card radius

Spacing

Typography
```

실수를:

```text
Design Token

+

Reusable Component
```

로 구조화한다.

---

# 70. Automation이 Architecture보다 항상 좋은 것은 아니다

큰 Architecture 변경에는 비용과 Regression 위험이 있다.

다음이 충분히 커야 한다.

```text
반복 비용

Risk

Maintenance burden
```

# 71. Promotion ROI

# 73. Expected Value

개념적으로:

```text

=

Probability of recurrence
×
```

이 값이 자동화 비용보다 크다면 자동화 가치가 높다.

# 76. Promotion 상태

각 Rule/Automation은 상태를 가진다.

```text
PROPOSED

CANDIDATE

CANARY

ACTIVE

DEGRADED

DEPRECATED

RETIRED
```

---

# 77. PROPOSED

승격 아이디어가 생긴 상태.

아직 적용하지 않는다.

---

# 78. CANDIDATE

구현 또는 적용 후보.

---

# 79. CANARY

실제 작업 일부에 적용하며 품질 평가.

---

# 80. ACTIVE

정식으로 Enforcement 중.

---

# 81. DEGRADED

오탐/문제 때문에 신뢰도 하락.

Blocking 대신 Warning으로 내릴 수 있다.

---

# 82. DEPRECATED

대체 Rule/Validator가 존재.

신규 작업에서는 사용하지 않는다.

---

# 83. RETIRED

더 이상 필요 없음.

---

# 86. 왜 Traceability가 필요한가

```text
왜 이 CI 검사 기능이 존재하는가?
```

```text
과거 Shared Hook Regression 두 건 때문에 추가.
```

# 87. 불필요한 Guardrail 제거에도 필요

원래 원인이 사라졌다면 Guardrail을 제거할 수 있다.

---

# 88. Rule Staleness

Architecture가 바뀌면 Rule도 낡을 수 있다.

예:

```text
axios 직접 사용 금지
```

인데 axios 자체가 프로젝트에서 제거됨.

Rule은 더 이상 필요하지 않을 수 있다.

---

# 89. Automation Staleness

Validator도 오래될 수 있다.

다음 확인:

```text
현재 Architecture에 맞나?

현재 file structure에 맞나?

새 Pattern을 잘못 막고 있나?

중복 Check가 생겼나?
```

---

# 90. Rule Cleanup

주기적으로:

```text
ACTIVE rules

PROMOTED lessons

CI checks

Validators
```

를 검토한다.

---

# 91. Rule Merge

비슷한 Rule:

```text
Shared Hook references 확인

Shared Component references 확인

Shared Utility references 확인
```

을:

```text
Shared Symbol 변경 전 Impact Analysis
```

로 일반화할 수 있다.

---

# 92. 그러나 과도한 일반화 금지

너무 일반화하면 행동 기준이 약해진다.

예:

```text
변경 전에 영향을 확인한다.
```

보다:

```text
Shared Symbol 변경 전 find_references + affected tests 확인.
```

이 더 실행 가능하다.

---

# 93. Rule Split

하나의 Rule이 너무 많은 상황을 포함하면 나눌 수 있다.

예:

```text
모든 고위험 작업을 조심한다.
```

는 나쁘다.

다음처럼:

```text
DB Migration Gate

Security Gate

API Contract Gate
```

로 분리하는 편이 좋다.

---

# 94. Conflict Detection

Rule A:

```text
Shared Utility 중복 금지
```

Rule B:

```text
작은 Feature는 Shared Code 수정보다 local implementation 우선
```

충돌 가능.

---

# 95. Rule Conflict Resolution

평균내지 않는다.

다음을 확인한다.

```text
Scope

Risk

Feature count

Actual duplication

Project convention
```

그리고 보다 구체적인 Rule 또는 Decision Table로 해결한다.

---

# 96. Decision Table Promotion

Rule 충돌이 반복되면 Decision Table을 만든다.

예:

```text
IF usage count = 1
→ local

IF usage count >= 2 and semantics identical
→ shared abstraction 고려

IF shared change risk high
→ impact analysis 필수
```

---

# 97. Decision Table도 자동화 가능

정량적 조건이면 Router에 포함할 수 있다.

---

# 98. Router Promotion

Lesson이 작업 분류 문제라면 Instruction Router를 개선한다.

예:

```text
DB 파일 수정했는데
Migration Policy가 로드되지 않음.
```

수정:

```text
Trigger:
schema.prisma changed
→ migration-policy
```

---

# 99. Harness Promotion

실수가 Agent 분배 문제라면 Multi-Agent Harness를 개선한다.

예:

```text
Architecture 판단을 Efficient Worker에게 맡겨 실패.
```

Rule:

```text
Architecture class
→ required reasoning >= HIGH
```

---

# 100. Model Registry Promotion

특정 모델이 특정 역할에서 반복 실패한다면 Core Policy가 아니라:

```text
Model Registry

Benchmark

Role Qualification
```

을 수정한다.

---

# 101. Provider-specific 문제를 Core에 넣지 않는다

금지:

```text
Model X는 절대 쓰지 않는다.
```

장기 지침에 하드코딩.

대신:

```text
tool_use reliability threshold 미달
→ reviewer role 비승인
```

처럼 Capability 기반으로 처리한다.

---

# 102. Context Lesson Promotion

반복적으로 Context가 비대해진다면:

```text
Checkpoint Trigger

Task Packet

Compaction Rule
```

을 개선한다.

---

# 103. Token Lesson Promotion

예:

실패:



# 104. Requirement Lesson Promotion

사용자 요구 오해가 반복되면:

```text

```

을 개선한다.

---

# 105. Communication Lesson Promotion

사용자가 설명을 반복해서 이해하지 못한다면:

```text
Plain Language Policy
```

의 Rule 후보가 된다.

---

# 106. Design Lesson Promotion

반복되는 디자인 수정:

```text
radius 너무 큼

gradient 제거 요청

accent 줄임
```

이 충분히 반복되고 명시적으로 확정되면:

```text
Design Vocabulary

Design Token
```

으로 승격할 수 있다.

---

# 107. User Preference와 Guardrail을 구분

예:

```text
사용자는 작은 Radius 선호
```

는 Preference.

```text
브랜드 로고 색상 변경 금지
```

는 Constraint / Guardrail.

동일하게 다루지 않는다.

---

# 108. 사용자 Preference는 강제 CI 대상이 아닐 수 있다

미적 선호를 과도하게 자동화하지 않는다.

---

# 109. Security Rule은 강한 자동화 후보

예:

```text
Secret이 git diff에 포함되면 실패
```

는 deterministic CI Guardrail에 적합하다.

---

# 110. Migration Rule도 강한 자동화 후보

예:

```text
Schema changed

but

Migration missing

→ CI FAIL
```

---

# 111. Verification Rule 자동화

예:

```text
코드 변경됨

관련 Test 없음

→ Warning
```

또는 Critical 영역이면 Failure.

# 120. 좋은 Guardrail


# 122. Plain Language 연동

Guardrail 메시지도 일반 개발자가 이해 가능한 형태로 작성한다.

---

# 123. Self-Healing은 Guardrail 삭제가 아니다

자동화가 실패했다고 AI가 Guardrail을 자동 완화하지 않는다.

먼저 원인을 확인한다.

---

# 124. Self-Healing 대상

다음은 자동 복구 가능할 수 있다.

```text
Stale Code Map 재생성

Generated index 업데이트

Cache invalidate

Missing generated metadata
```

---

# 125. Self-Healing 금지 영역

다음은 임의 자동 수정하지 않는다.

```text
Security Rule

Permission

Production data

Destructive migration

User requirement
```

# 126. Promotion 이후 Error Learning

# 145. Human-readable Rule 유지

# 146. Promotion Evidence

---

# 147. Overfitting 방지

특정 한 번의 특수 상황을 전체 프로젝트 Rule로 만들지 않는다.

---

# 148. Example of Overfitting

한 Feature에서:

```text
500ms debounce 필요
```

했다고:

```text
모든 입력은 debounce 500ms
```

Rule로 승격하면 안 된다.

---

# 149. Generalization Check

승격 전 질문:

```text
이 Rule이 다른 상황에서도
같은 의미를 유지하는가?
```

NO라면 Local Lesson으로 유지한다.

---

# 150. Underfitting 방지

반대로 매우 반복되는 문제를 계속 개별 Lesson으로만 관리하지 않는다.

# 152. Rule Granularity

# 153. Enforcement Level

Rule마다 Enforcement를 둘 수 있다.

```text

WARNING

REQUIRED

```

---

# 154. ADVISORY

권장.

위반해도 작업 가능.

---

# 155. WARNING

위반 시 경고.

---

# 156. REQUIRED

작업 완료 전 반드시 충족.

# 225. 압축 Core 지침

전체 문서를 필요할 때마다 읽기 어렵다면 다음 Core만 사용할 수 있다.

```text
LESSON → RULE → AUTOMATION PROMOTION CORE

1. Do not accumulate lessons indefinitely; repeated or high-risk lessons must be evaluated for promotion.
2. Treat prevention strength as a ladder: task note → lesson → rule → gate → regression test → validator → CI guardrail → architectural prevention.
3. Select the lowest-cost level that reliably prevents the failure.
4. Promote based on recurrence, severity, generality, detectability, recovery cost, automation cost, and false-positive risk.
5. Critical failures may require hard guardrails after the first occurrence.
6. Every promoted rule should have a clear trigger, required action, scope, enforcement level, and origin.
7. Prefer deterministic tests and validators over permanent prompt instructions whenever the condition can be checked mechanically.
8. Do not put local or domain-specific rules into the global Core unless they apply broadly.
9. Deduplicate similar lessons and rules; generalize only as far as the behavior remains concrete and actionable.
10. When automation becomes authoritative, reduce redundant prompt context while retaining a short human-readable explanation.
11. Introduce new validators through candidate/canary stages when false-positive risk is meaningful.
12. Never bypass a failing guardrail merely to complete the task; investigate the failure or create a controlled exception.
13. Treat failures of rules, routers, validators, and automations as learning signals for the Harness itself.
14. Periodically retire obsolete lessons, rules, and checks so the Harness does not grow without bound.
15. Measure success by lower same-class failure recurrence, not by the number of lessons or rules created.
16. The long-term objective is to convert repeated human/AI memory requirements into executable guardrails wherever practical.
```

# 226. Final Principle

가장 약한 시스템:

```text
"다음에는 조심해."
```

그보다 강한 시스템:

```text
"다음에는 이 Rule을 읽어."
```

더 강한 시스템:

```text
"틀리면 Test가 실패해."
```

더 강한 시스템:

```text
"틀리면 CI가 막아."
```

가장 강한 시스템:

```text
"그 실수를 만들기 어려운 구조로 설계되어 있어."
```

따라서 Harness는 가능한 경우 다음 방향으로 진화해야 한다.

```text
REMEMBER

↓

RECOGNIZE

↓

REQUIRE

↓

VERIFY

↓

BLOCK

↓

PREVENT
```
