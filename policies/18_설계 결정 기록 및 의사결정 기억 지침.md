# ⑯ 설계 결정 기록 및 의사결정 기억 지침 v1

## Architecture Decision Record & Decision Memory Policy

### 중요한 설계 결정·선택 근거·대안·폐기 이유·의사결정 변경 이력 관리 지침

Version: 1.0

---

# 0. 목적

이 지침은 장기 개발 프로젝트에서 다음과 같은 문제를 방지한다.

```text
왜 이 구조로 만들었는지 모름

왜 A 대신 B를 선택했는지 잊음

이미 검토해서 버린 대안을 다시 검토

새 Agent가 기존 Architecture를 이유 없이 뒤집음

과거 임시 결정이 영구 규칙처럼 굳어짐

중요 결정이 Chat 대화 안에만 존재

사용자가 확정한 선택을 후속 Agent가 재해석

기술 제약 때문에 선택한 구조를 단순 취향으로 오해

계획 변경 이유가 사라짐

과거 결정이 현재에도 유효한지 알 수 없음

Architecture와 Business Decision이 뒤섞임

모든 사소한 선택을 ADR로 기록해 문서가 폭증
```

이를 방지하기 위해 중요한 의사결정을:

```text
QUESTION

↓

CONTEXT

↓

OPTIONS

↓

EVIDENCE / CONSTRAINTS

↓

DECISION

↓

WHY

↓

REJECTED ALTERNATIVES

↓

CONSEQUENCES

↓

SCOPE

↓

STATUS

↓

REVISIT CONDITION
```

형태로 저장한다.

핵심 목표:

> 미래의 Agent가 “무엇을 선택했는가?”뿐 아니라 “왜 그렇게 선택했는가?”까지 빠르게 이해할 수 있게 한다.

---

# 1. 최상위 원칙

> 중요한 결정은 결과뿐 아니라 결정 근거를 보존한다.

다음 정보만 남기는 것은 부족하다.

```text
Frontend에서 처리하기로 함.
```

좋은 기록:

```text
Decision:
공석 표시 문구는 Frontend에서 처리한다.

Reason:
API가 이미 필요한 null 상태를 제공하고 있으며
표시 문자열은 UI 표현 책임이기 때문이다.

Rejected:
Backend에서 "공석" 문자열 반환

Reason rejected:
API에 presentation text가 들어가고
다른 Consumer에도 영향을 줄 수 있음.
```

---

# 2. ADR이란

ADR:

```text
Architecture Decision Record
```

쉽게 말하면:

> 시스템의 중요한 설계 결정을 짧게 기록하는 문서

다.

---

# 3. Decision Memory

ADR보다 더 넓은 개념이다.

다음을 포함할 수 있다.

```text
Architecture Decision

Business Rule Decision

Technology Choice

Data Model Decision

Security Decision

Design-system Decision

Project-level Constraint Decision

Operational Decision
```

---

# 4. ADR과 일반 메모의 차이

일반 메모:

```text
Redis를 검토함.
```

ADR:

```text
Question:
실시간 Session 저장소를 무엇으로 사용할 것인가?

Decision:
현재 Release에서는 기존 DB 사용.

Why:
현재 동시 접속 규모에서 Redis 필요성 없음.

Rejected:
Redis

Why rejected:
새 Infra/운영 부담 대비 현재 필요성 부족.

Revisit:
실측 부하가 현재 DB 한계를 초과할 때.
```

---

# 5. 무엇을 기록해야 하는가

다음 중 하나 이상이면 Decision Record 후보다.

```text
Architecture를 장기간 제약

여러 Feature에 영향

API Contract에 영향

Data Model에 영향

Dependency 선택

Security Boundary

Deployment 구조

중요 Design System 방향

비즈니스 규칙

사용자가 명시적으로 확정한 중요한 방향

대안 간 Trade-off가 큼

나중에 다시 논쟁할 가능성이 높음

되돌리기 비용이 큼
```

---

# 6. 무엇을 기록하지 않아도 되는가

다음 같은 사소한 선택은 일반적으로 ADR 불필요.

```text
변수명

local helper 이름

사소한 함수 분리

일반적인 formatting

한 번 쓰는 작은 implementation detail

기존 Convention을 그대로 따른 결정
```

---

# 7. ADR 남발 금지

목표는:

```text
모든 결정을 기록
```

이 아니라:

```text
미래에 "왜?"가 다시 중요해질 결정을 기록
```

하는 것이다.

---

# 8. Decision Significance Test

질문:

```text
이 결정을 3개월 뒤 다른 Agent가 뒤집으려 할 가능성이 있는가?

뒤집었을 때 영향이 큰가?

결정 이유를 잊으면 재조사 비용이 큰가?

여러 합리적인 대안이 존재했는가?
```

YES가 많을수록 ADR 가치가 높다.

# 36. Context

결정이 필요했던 상황을 설명한다.

---

# 37. 나쁜 Context

```text
구조를 결정해야 했다.
```

---

# 38. 좋은 Context

```text
공석 상태를 UI에 표시해야 하지만
API는 이미 nullable worker 상태를 제공한다.

표시 문자열을 Backend에서 만들 경우
API Consumer 전체에 presentation concern이 전파될 수 있다.
```

# 39. Problem / Question

예:


# 40. Constraints

```text

```

# 41. Options

```text

```

# 42. 모든 상상 가능한 대안을 기록하지 않는다

실제로 합리적으로 고려할 가치가 있던 것만.

---

# 43. Option A

예:

```text
Backend가 "공석" 문자열 반환
```

---

# 44. Option B

```text
Backend는 상태만 제공하고
Frontend가 표시 문자열 결정
```

---

# 45. Decision

최종 선택을 짧고 명확하게.

```text
Option B를 사용한다.
```

---

# 46. Rationale

왜 이 선택을 했는가?

---

# 47. 좋은 Rationale

```text
표시 문자열은 UI 책임이며,
현재 API가 상태 표현에 필요한 정보를 이미 제공한다.

따라서 Backend Contract를 변경하지 않고
Frontend에서 처리하는 것이 영향 범위가 가장 작다.
```

---

# 48. 나쁜 Rationale

```text
이 방법이 더 좋아 보였음.
```

---

# 49. Evidence-based Rationale

가능하면:

```text
현재 코드

Test

Runtime

Benchmark

Provider Contract

User Priority
```

같은 Evidence에 연결한다.

# 50. Rejected Alternatives

# 51. Rejected 이유가 중요한 이유

# 52. 예

# 53. Rejected ≠ 영원히 금지

---

# 54. Revisit Condition

조건이 달라지면 다시 검토할 수 있다.

예:

```text

```

# 55. 이 항목이 중요하다

# 57. Local Decision ≠ Global Architecture

한 Feature 결정이 전체 프로젝트 규칙으로 자동 승격되지 않는다.

# 58. Do Not Infer

```text

```

# 94. Decision vs Canonical Spec


# 297. 압축 Core 지침

```text
설계 결정 기록 및 의사결정 기억 CORE

1. 장기적으로 의미 있는 Architecture, Data, API, Dependency, Security, Business Rule, Design 방향은 필요할 때 Decision Record로 보존한다.
2. 모든 작은 구현 선택을 ADR로 기록하지 말고 미래에 "왜?"가 다시 중요해질 결정만 기록한다.
3. Decision에는 최소한 Question, Context, Decision, Rationale, Scope, Status가 있어야 한다.
4. 의미 있는 대안을 실제로 검토했다면 Rejected Alternative와 거절 이유를 남긴다.
5. 장점뿐 아니라 비용, 단점, Trade-off도 기록한다.
6. User-owned Decision과 AI-owned Decision을 구분하고, AI Recommendation을 최종 결정처럼 취급하지 않는다.
7. 최신 명시적 사용자 요구와 Mandatory Constraint는 기존 ADR보다 높은 권한을 가진다.
8. ADR은 당시 조건에서의 Decision이지 영원한 절대 법칙이 아니며, 필요하면 Revisit Condition을 정의한다.
9. 새 Evidence, Requirement, External Contract, Security Risk가 기존 Decision의 전제를 깨면 공식적으로 Revisit한다.
10. Material Decision 변경 시 기존 History를 지우지 말고 SUPERSEDED 상태와 새 Decision을 연결한다.
11. Decision 적용 범위를 명확히 하여 Local Decision을 Project-wide Rule로 자동 일반화하지 않는다.
12. 실제 Source/Runtime이 ADR과 충돌하면 ADR을 Current Reality로 강제하지 말고 Staleness 또는 구현 불일치를 판정한다.
13. 관련 ADR은 Feature/Spec/Code Map과 연결하고 현재 Task에 필요한 ADR만 JIT로 로드한다.
14. Subagent는 기존 Decision 문제를 보고할 수 있지만 Canonical ADR 변경은 Orchestrator가 관리한다.
15. 동일 Architecture 논의가 반복되면 ADR Recall/Indexing 실패를 Harness 문제로 본다.
16. 반복되는 Decision이 실제 Project-wide 원칙으로 굳어지면 Convention/Architecture Rule/Validator 승격을 검토한다.
17. Active Context에는 ADR 전체 이력이 아니라 현재 관련 ACTIVE Decision의 ID와 핵심 Summary만 유지한다.
18. 중요한 Replanning 결과가 장기 Architecture를 바꾸면 ADR 생성 또는 Revisit 여부를 평가한다.
19. Decision의 성공은 문서 작성 자체가 아니라 미래 Agent가 같은 논의를 반복하거나 이유 없이 구조를 뒤집는 것을 줄이는 데 있다.
20. 목표는 Architecture를 영구 고정하는 것이 아니라, 현재 선택의 이유를 보존하면서 새로운 Evidence가 생기면 통제된 방식으로 변경할 수 있게 하는 것이다.
```

# 298. Final Principle

장기 프로젝트에서 다음 문장은 위험 신호다.

```text
"왜 이렇게 되어 있는지 모르겠는데
내가 보기엔 이쪽이 더 좋아 보여서 바꾸겠습니다."
```

먼저 확인해야 한다.

```text
현재 구조는 무엇인가?

↓

관련 Decision이 존재하는가?

↓

왜 그렇게 결정했는가?

↓

당시 Constraint가 지금도 유효한가?

↓

새로운 Evidence가 있는가?

↓

기존 Decision을 유지할 것인가?

↓

재검토할 것인가?

↓

대체한다면 무엇이 바뀌는가?
```

좋은 Decision Memory는:

```text
과거 결정을 무조건 지키게 하는 장치
```

가 아니다.

좋은 Decision Memory는:

```text
과거의 이유를 알고
현재의 Evidence와 비교한 뒤
같은 논의를 반복하지 않고
필요할 때만 의도적으로 변경하게 하는 장치
```

다.

최종적으로:

> **코드는 현재 구조를 보여주고, ADR은 그 구조가 왜 존재하는지를 보여준다.**

그리고:

> **어제 내린 결정을 맹목적으로 지키지 않되, 어제 왜 그렇게 결정했는지도 잊지 않는다.**

이 원칙이 여러 AI Agent와 여러 Session에 걸친 장기 개발에서 Architecture Drift를 크게 줄이는 핵심이다.
