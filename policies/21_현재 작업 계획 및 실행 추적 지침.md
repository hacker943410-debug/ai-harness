# Active Work Plan & Execution Plan Policy v1

## 현재 작업 계획·단계·근거·진행상태 관리 지침

Version: 1.0

---

# 0. 목적

이 Policy는 AI Agent가 작업을 시작한 뒤 다음과 같은 문제가 발생하지 않도록 한다.

```text
무엇을 하려는지 불명확

왜 그 작업을 먼저 하는지 알기 어려움

계획 없이 파일부터 수정

조사와 구현이 뒤섞임

작업 순서가 계속 바뀜

현재 어디까지 왔는지 알 수 없음

완료 조건 없이 끝없이 작업

사용자가 중간 진행상황을 파악하기 어려움

계획과 실제 행동이 달라짐

중간에 다른 문제로 빠짐
```

이를 방지하기 위해 모든 비단순 작업에는 최소한의 `ACTIVE WORK PLAN`을 유지한다.

핵심 흐름:

```text
ROADMAP POSITION

↓

CURRENT GOAL

↓

SUCCESS CRITERIA

↓

CURRENT STATE

↓

EXECUTION STEPS

↓

WHY EACH STEP EXISTS

↓

DEPENDENCIES

↓

EXPECTED CHANGE

↓

VERIFICATION

↓

EXIT CONDITION
```

---

# 1. 최상위 원칙

> 비단순 작업은 “코드부터 수정”하지 않는다.

먼저:

```text
무엇을 해야 하는가?

왜 해야 하는가?

무엇부터 확인해야 하는가?

어떤 순서가 가장 안전한가?

어디까지 바꿀 것인가?

무엇이 끝나면 완료인가?
```

를 정의한다.

---

# 2. Active Plan의 역할

Roadmap:

```text
프로젝트 전체에서 어디로 가는가?
```

Active Plan:

```text
현재 목적지까지 어떻게 갈 것인가?
```

를 담당한다.

---

# 3. Roadmap과 Active Plan 관계

```text
PROJECT ROADMAP
      ↓
CURRENT MILESTONE
      ↓
CURRENT FEATURE
      ↓
ACTIVE WORK PLAN
      ↓
EXECUTION
```

Active Plan은 반드시 현재 Milestone 또는 사용자 직접 요청과 연결되어야 한다.

---

# 4. Active Plan 최소 구성

기본적으로 다음을 포함한다.

```text
Goal

Why

Current State

Success Criteria

Steps

Expected Scope

Do Not Change

Verification

Exit Condition

Next
```

---

# 5. Goal

이번 작업에서 정확히 달성하려는 결과.

나쁜 예:

```text
Dashboard 수정
```

좋은 예:

```text
야간 근무자가 없는 경우
TodayShiftCard에 "공석"을 표시한다.
```

---

# 6. Goal은 하나의 중심 목표를 가진다

한 Active Plan에 서로 독립적인 목표를 너무 많이 넣지 않는다.

나쁜 예:

```text
공석 표시 수정

Dashboard 디자인 개선

API 정리

테스트 구조 개선

Dependency 업데이트
```

필요하면 별도 Task 또는 Milestone으로 분리한다.

---

# 7. Why

각 작업에는 왜 필요한지 설명할 수 있어야 한다.

예:

```text
Goal:
야간 공석 표시

Why:
현재 "-" 표시는
근무자가 없는 것인지 데이터 오류인지 구분하기 어렵다.
```

---

# 8. Why가 중요하다

`무엇을 한다`만 알면 Agent가 구현 디테일에 빠질 수 있다.

`왜 한다`를 알면 더 작은 해결책을 찾을 수 있다.

---

# 9. 예

사용자:

```text
텍스트 잘리는 것 수정해줘.
```

잘못된 Plan:

```text
width 증가
```

좋은 Plan:

```text
Goal:
텍스트 잘림 제거

Why:
현재 중요한 상태명이 일부 보이지 않음

Step 1:
실제 잘림 원인 확인

Step 2:
가장 작은 수정 적용
```

이렇게 하면 원인이 `overflow:hidden`인데 width를 무작정 키우는 일을 막을 수 있다.

---

# 10. Current State

수정 전 상태를 짧게 기록한다.

예:

```text
CURRENT STATE

- TodayShiftCard 존재
- 야간 근무자 없음 → "-"
- API는 worker nullable 값 제공
- Error state 별도 존재
```

---

# 11. Current State는 FACT 중심

확인되지 않은 내용을 사실처럼 쓰지 않는다.

Assumption & Uncertainty Policy를 적용한다.

---

# 12. Success Criteria

작업 완료를 판단할 기준.

예:

```text
SUCCESS

[ ] 야간 근무자 있음 → 이름

[ ] 야간 근무자 없음 → "공석"

[ ] API 오류 → 기존 Error 상태

[ ] 주간 근무자 표시 유지

[ ] API / DB 변경 없음
```

---

# 13. Plan Step

계획은 단순 행동 목록이 아니라 **의미 있는 단계**로 구성한다.

---

# 14. 나쁜 Plan

```text
1. 파일 열기
2. 검색
3. 수정
4. 테스트
```

이것만으로는 왜 하는지 알 수 없다.

---

# 15. 좋은 Plan

```text
1. TodayShiftCard의 실제 데이터 흐름 확인
   이유:
   Backend 수정이 필요한지 판단

2. Empty와 Error 상태가 현재 어떻게 구분되는지 확인
   이유:
   장애를 공석으로 잘못 표시하지 않기 위해

3. UI에 최소 조건 추가
   이유:
   API Contract를 바꾸지 않고 요구 충족

4. 정상 / 공석 / 오류 테스트
   이유:
   세 상태의 Regression 방지

5. Final Diff 확인
   이유:
   다른 Dashboard 영역이 수정되지 않았는지 검증
```

---

# 16. 모든 Step에는 Reason이 필수인가?

아주 단순한 단계까지 모두 설명할 필요는 없다.

하지만 다음은 Reason을 붙이는 것이 좋다.

```text
Architecture decision

새 파일 추가

API / DB 변경

조사 단계

고위험 수정

계획상 중요한 분기점
```

---

# 17. Step Classification

필요하면 단계 유형을 구분한다.

```text
DISCOVER

DECIDE

IMPLEMENT

VERIFY

DOCUMENT

HANDOFF
```

---

# 18. DISCOVER

아직 모르는 사실을 확인.

예:

```text
DISCOVER:
API가 이미 필요한 데이터를 제공하는가?
```

---

# 19. DECIDE

조사 결과를 바탕으로 방법 선택.

예:

```text
DECIDE:
Frontend-only vs API change
```

---

# 20. IMPLEMENT

확정된 방법을 실제 변경.

---

# 21. VERIFY

Success Criteria 검증.

---

# 22. DOCUMENT

필요한 Map / ADR / Spec 업데이트.

---

# 23. HANDOFF

다른 Agent/Session이 이어갈 상태 정리.

---

# 24. Plan은 단계 순서를 보여야 한다

예:

```text
DISCOVER
↓
DECIDE
↓
IMPLEMENT
↓
VERIFY
```

조사하기 전에 구현을 시작하지 않는다.

---

# 25. Decision Gate

아직 중요한 정보가 없는 경우:

```text
Step 1:
정보 확인

↓

Decision Gate

↓

Step 2A 또는 2B
```

형태로 만든다.

---

# 26. Branch Plan

예:

```text
1. API 데이터 확인

IF 필요한 데이터 있음:
→ Frontend-only

IF 없음:
→ API extension 검토
```

모르는 상태에서 하나를 사실처럼 고정하지 않는다.

---

# 27. Conditional Plan

좋은 계획은 불확실성을 인정할 수 있다.

```text
현재 예상:
Frontend-only 가능성 높음

확정 조건:
API payload 확인 후 결정
```

---

# 28. Plan ≠ Prediction

계획은 미래를 완벽하게 맞히는 것이 아니다.

새로운 사실이 나오면 수정할 수 있다.

단 이유 없이 변하지 않는다.

---

# 29. Expected Scope

작업 시작 전 예상 변경 범위를 기록한다.

예:

```text
EXPECTED SCOPE

Primary:
TodayShiftCard.tsx

Tests:
TodayShiftCard.test.tsx

Possible:
useTodayShift.ts

Expected:
2~3 files

API:
NO

DB:
NO
```

---

# 30. 예상 범위가 필요한 이유

실제 변경이:

```text
2 files expected
→ 11 files changed
```

라면 Drift 또는 숨은 Dependency 가능성을 빠르게 알 수 있다.

---

# 31. Expected Diff

가능하면:

```text
Files:
1~3

Layers:
Frontend only

Change Type:
Condition + tests

Refactor:
NO
```

정도로 정의한다.

---

# 32. 정확한 LOC 예측은 필수가 아니다

근거 없는:

```text
정확히 27줄 수정
```

같은 Fake Precision을 만들지 않는다.

---

# 33. Do Not Change

사용자 또는 Change Contract의 Protected 영역을 Active Plan에도 반영한다.

예:

```text
DO NOT CHANGE

Sidebar

API response

Database schema

Other dashboard cards
```

---

# 34. Must Preserve

기존 Behavior 중 유지해야 할 것.

예:

```text
MUST PRESERVE

주간 근무자 표시

기존 Error state

현재 click interaction
```

---

# 35. Active Plan과 Change Contract 차이

Active Plan:

```text
무엇을 어떤 순서로 할 것인가?
```

Change Contract:

```text
어디까지 변경이 허용되는가?
```

둘은 연결되지만 역할이 다르다.

---

# 36. Dependencies

현재 작업의 선행 조건을 기록한다.

예:

```text
DEPENDS ON

M2.1 Pattern Engine — DONE

SPEC-021 — LOCKED
```

---

# 37. External Dependency

예:

```text
Requires:
API specification confirmation
```

이 완료되지 않으면 다음 단계가 BLOCKED일 수 있다.

---

# 38. Task Dependency

복잡한 작업에서는:

```text
T1 → T2 → T4

T1 → T3 → T4
```

처럼 Task DAG Policy로 넘긴다.

---

# 39. Active Plan에서는 주요 Dependency만

작은 작업까지 DAG를 만들 필요 없다.

---

# 40. Entry Condition

계획을 시작하기 전에 필요한 조건을 정의할 수 있다.

예:

```text
ENTRY

Spec:
LOCKED

Required access:
available

Feature location:
identified
```

---

# 41. Exit Condition

이 작업을 멈출 기준.

예:

```text
EXIT

All required success criteria PASS

Relevant tests PASS

Final diff clean

No unresolved blocking issue
```

---

# 42. Exit Condition이 중요한 이유

AI Agent가 끝없이 개선하는 것을 막는다.

---

# 43. "더 개선할 수 있음"은 완료 실패가 아니다

Success Criteria가 충족됐다면:

```text
추가 개선 가능
```

은 Parking Lot 또는 Follow-up이다.

현재 Task는 종료할 수 있다.

---

# 44. Definition of Done

Active Plan의 Exit Condition은 Verification Gate와 연결한다.

---

# 45. Plan Status

각 Step에 상태를 둔다.

```text
TODO

ACTIVE

DONE

BLOCKED

SKIPPED

REPLACED
```

---

# 46. TODO

아직 시작하지 않음.

---

# 47. ACTIVE

현재 수행 중.

가능하면 하나의 Agent가 동시에 너무 많은 Step을 ACTIVE로 두지 않는다.

---

# 48. DONE

해당 Step의 목적이 달성됨.

---

# 49. BLOCKED

외부 조건으로 진행 불가.

Reason 필수.

---

# 50. SKIPPED

조사 결과 필요 없어진 단계.

예:

```text
API 수정 검토
→ 기존 API로 해결 가능
→ SKIPPED
```

---

# 51. REPLACED

Replanning으로 다른 단계에 대체됨.

---

# 52. Step Evidence

중요 단계 완료에는 짧은 Evidence를 붙일 수 있다.

예:

```text
Step 1 — DONE

Evidence:
GET /api/shifts/today already returns nullable nightWorker
```

---

# 53. Evidence는 전체 Tool Log가 아니다

짧은 결론과 Reference만 유지한다.

---

# 54. Plan Progress

예:

```text
1 ✓ 데이터 흐름 확인

2 ✓ 상태 분기 확인

3 → UI 수정

4 ○ Test

5 ○ Diff Review
```

처럼 표시할 수 있다.

---

# 55. 사용자에게 중간 상태를 보여주는 방법

긴 작업에서는 다음처럼 압축한다.

```text
현재 목표:
야간 공석 표시

진행:
✓ 데이터 흐름 확인
✓ API 변경 불필요 확인
→ UI 수정 중
○ 테스트
○ 최종 검증

현재까지 계획 변경:
없음
```

---

# 56. Progress Update는 의미 있는 정보가 있어야 한다

나쁜 Update:

```text
계속 진행 중입니다.
```

좋은 Update:

```text
API에 이미 필요한 정보가 있어서
Backend 수정 없이 UI만 바꾸는 방향으로 확정했습니다.

현재는 공석/오류 상태를 분리하는 단계입니다.
```

---

# 57. Update Frequency

모든 작은 Step마다 사용자에게 보고하지 않는다.

긴 작업, 중요한 결정, 계획 변경, Blocker 발생 시 의미 있는 Update를 제공한다.

---

# 58. Current Step

Active Plan에는 항상 현재 Step이 명확해야 한다.

예:

```text
CURRENT STEP:
3 — Add UI empty-state branch
```

---

# 59. Next Step

항상 다음 행동도 명확히 한다.

```text
NEXT:
Run affected tests
```

---

# 60. "다음 작업"을 추상적으로 쓰지 않는다

나쁜 예:

```text
계속 구현
```

좋은 예:

```text
TodayShiftCard의 null worker 분기 추가
```

---

# 61. Active Plan State

추천:

```text
ACTIVE PLAN

Status:
ACTIVE

Current Step:
3

Next Step:
4

Blocked:
None
```

---

# 62. Plan Owner

Multi-Agent Harness에서는 Orchestrator가 Canonical Active Plan을 소유한다.

---

# 63. Subagent는 Global Plan을 수정하지 않는다

Subagent는:

```text
Finding

Result

Blocker

Suggested Plan Change
```

를 Parent에게 반환한다.

---

# 64. Plan Mutation 권한

Orchestrator는 근거가 있으면 Active Plan을 수정할 수 있다.

하지만 User-owned Spec과 충돌하면 안 된다.

---

# 65. Plan Change

Material Plan Change에는 이유를 기록한다.

예:

```text
PLAN CHANGE

Original:
Frontend-only

New:
Frontend + API

Reason:
API does not expose required state

Impact:
+2 files
Risk:
LOW → MEDIUM
```

---

# 66. 작은 Plan Adjustment

예:

```text
Test file 위치 변경
```

같은 사소한 사항은 Formal Replan까지 필요 없을 수 있다.

---

# 67. Material Plan Deviation

다음이면 정식 Replanning 대상.

```text
새 Layer 추가

API 변경

DB 변경

Dependency 추가

Risk 상승

Expected files 크게 초과

새 Feature 필요

Architecture 변경
```

---

# 68. Plan Deviation과 Drift 차이

정당한 Plan Deviation:

```text
Success Criteria 충족을 위해 필요
```

Drift:

```text
하면 좋을 것 같아서 추가
```

---

# 69. Replanning Policy 연결

Material Deviation은 23번 Replanning Policy를 활성화한다.

---

# 70. Drift Sentinel 연결

현재 Step이 Active Goal에 필요한지 지속 확인한다.

---

# 71. Drift Check 질문

```text
이 작업이 현재 Success Criteria 중
어느 항목을 만족시키는가?
```

답할 수 없다면 Drift 후보.

---

# 72. Supporting Work

현재 Success Criteria를 직접 만들지는 않지만 필수일 수 있다.

예:

```text
Type Error 해결
```

현재 구현을 막고 있다면 Supporting Task다.

---

# 73. Supporting Task를 무한 확장하지 않는다

Type Error를 고치다 전체 Type System 리팩터링으로 가지 않는다.

---

# 74. Parking Lot

관련은 있지만 현재 필요하지 않은 발견은 별도 저장한다.

예:

```text
PL-014

ShiftService duplication

Reason:
Maintenance concern

Current Task:
Not required
```

---

# 75. Parking Lot은 Active Plan에 넣지 않는다

---

# 76. Plan Drift Example

원래:

```text
Goal:
버튼 loading state 수정
```

작업 중:

```text
공용 Form Architecture 개선
```

직접 필요 없음:

```text
PARKING LOT
```

---

# 77. Root Cause Investigation Plan

Bug Fix에서는 계획이 바로 구현으로 가면 안 될 수 있다.

좋은 흐름:

```text
REPRODUCE

↓

TRACE

↓

ROOT CAUSE

↓

FIX

↓

REGRESSION TEST
```

---

# 78. Bug Plan Template

```text
1. 현재 Bug 재현
   이유:
   실제 Failure 확인

2. 실행 흐름 추적
   이유:
   발생 위치와 Root Cause 구분

3. Root Cause 확정
   이유:
   증상 Patch 방지

4. 최소 Fix
   이유:
   Regression 범위 최소화

5. Regression Test
   이유:
   재발 방지
```

---

# 79. Feature Plan Template

```text
1. Requirement / Spec 확인

2. Existing implementation pattern 확인

3. Data/API dependency 확인

4. Minimal design 결정

5. 구현

6. Relevant tests

7. Impact regression

8. Final diff
```

---

# 200. Active Plan Example — 전체

```text

Task:
Dashboard Night Shift Empty State

Roadmap:
Phase 2 — Operations Dashboard
Milestone M2.3 — Shift Status Visibility

야간 근무자가 없을 때 "공석" 표시

Why:
현재 "-" 표시는 사용자에게 상태 의미가 불명확

Success Criteria:
- 근무자 있음 → 이름
- 근무자 없음 → 공석
- API 오류 → Error
- 주간 표시 유지
- API/DB 변경 없음

Current State:
- TodayShiftCard 확인
- worker nullable
- Error state 존재

Expected Scope:
- TodayShiftCard.tsx
- TodayShiftCard.test.tsx
- possible useTodayShift.ts read-only

Do Not Change:
- API schema
- DB
- Sidebar
- other cards

Plan:

1. Data flow 확인
   Status: DONE
   Reason:
   Backend 변경 필요 여부 판단
   Evidence:
   API already returns nullable worker

2. Empty/Error 분기 확인
   Status: DONE
   Reason:
   장애를 공석으로 숨기지 않기 위해

3. UI condition 수정
   Status: ACTIVE
   Reason:
   가장 작은 Frontend-only 변경

4. Test 추가/실행
   Status: TODO
   Covers:
   normal / vacant / error

5. Final Diff
   Status: TODO
   Verify:
   no unrelated changes

Current:
Step 3

Next:
Step 4

Exit:
Success Criteria + tests + clean diff

Plan Status:
ACTIVE
```

# 213. 압축 Core 지침

```text
ACTIVE WORK PLAN / EXECUTION PLAN CORE

1. Before non-trivial implementation, define the current goal, why it matters, success criteria, expected scope, verification method, and exit condition.
2. Connect the task to the current roadmap milestone when the task belongs to a larger project.
3. Break work into meaningful execution steps rather than generic actions such as "read, edit, test."
4. Important steps should explain why they exist, especially discovery, decision, architecture, API/DB, and high-risk steps.
5. Separate discovery, decision, implementation, and verification so the agent does not code before resolving necessary facts.
6. Use conditional branches when important facts are not yet known instead of pretending the implementation path is already certain.
7. Maintain an explicit current step and concrete next step.
8. Define expected files, layers, and change types before editing when practical.
9. Preserve do-not-change and must-preserve constraints inside the active plan.
10. If actual activity no longer maps to a planned step or success criterion, classify it as supporting work, drift, or a reason to replan.
11. Unrelated discoveries belong in the Parking Lot rather than being silently added to the current task.
12. Material changes to scope, architecture, API, DB, dependencies, risk, or file count require plan re-evaluation.
13. Plans may change when verified evidence changes, but material plan changes must have an explicit reason.
14. Use evidence-based exit conditions rather than indefinite improvement goals.
15. Stop the task when the locked success criteria and required verification are satisfied; additional improvements become separate follow-up work.
16. In long-running work, periodically re-anchor on goal, current step, remaining steps, and exit condition.
17. The orchestrator owns the canonical active plan; subagents execute bounded steps and return results or suggested changes.
18. Keep the plan compact and current; it is an execution state, not a transcript of every action.
```

# 214. Final Principle

좋은 계획은:

```text
"앞으로 어떤 파일을 수정할 것이다."
```

만 말하는 문서가 아니다.

좋은 계획은:

```text
왜 이 작업이 필요한지

↓

무엇을 먼저 알아야 하는지

↓

그 사실에 따라 어떤 결정을 할지

↓

어디까지 수정할지

↓

어떻게 검증할지

↓

언제 멈출지
```

를 명확히 하는 문서다.

따라서 AI는 언제든 다음 질문에 답할 수 있어야 한다.

```text
WHAT IS THE GOAL?

WHY ARE WE DOING THIS?

WHAT STEP ARE WE ON?

WHY IS THIS STEP REQUIRED?

WHAT IS NEXT?

WHAT WOULD MAKE US CHANGE THE PLAN?

WHAT PROVES WE ARE DONE?
```

최종 목표는:

> **사용자와 Agent 모두 현재 작업이 어디로 가고 있는지 잃지 않도록 하고, 계획에 없는 행동이 시작되는 순간 즉시 감지할 수 있는 실행 기준선을 만드는 것**

이다.
