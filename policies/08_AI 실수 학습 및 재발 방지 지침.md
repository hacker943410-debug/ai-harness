# Error Learning & Anti-Regression Loop v1

## AI 실수 학습·재발 방지·규칙 승격 지침

Version: 1.0

---

# 0. 목적

이 Policy는 AI Agent가 작업 중 발생한 실수, 검증 실패, 사용자 정정, 잘못된 가정, 회귀 문제를 단순히 수정하고 잊어버리지 않도록 한다.

목표는 다음과 같다.

```text
FAILURE

↓

DETECT

↓

CLASSIFY

↓

ROOT CAUSE

↓

FIX

↓

VERIFY

↓

LESSON

↓

RECALL ON SIMILAR TASK

↓

REPEATED?

↓

RULE

↓

AUTOMATABLE?

↓

TEST / VALIDATOR / LINTER / GUARDRAIL
```

궁극적인 목표:

> 프로젝트가 오래 운영될수록 동일 유형의 실수를 다시 하기 어려워지는 구조를 만든다.

---

# 1. 중요한 정의

이 문서에서 `Learning`은 모델 자체의 파라미터를 재학습한다는 의미가 아니다.

기본적으로 다음을 의미한다.

```text
Project-level Experience Memory

+

Regression Tests

+

Rules

+

Automated Validators

+

Harness Routing Improvements
```

즉:

> 모델이 기억하는 것이 아니라 프로젝트와 Harness가 기억한다.

---

# 2. 왜 프로젝트가 기억해야 하는가

모델은:

```text
Session 변경

Model 변경

Provider 변경

Context 압축

Agent 교체
```

등으로 이전 실수에 대한 세부 기억을 잃을 수 있다.

따라서 재발 방지는 모델 개인 기억에 의존해서는 안 된다.

다음에 저장한다.

```text
.ai/lessons/

.ai/rules/

tests/

validators/

CI/

Code Map

Convention Map
```

---

# 3. 핵심 원칙

> 같은 실수를 두 번 설명으로만 해결하지 않는다.

첫 번째 실수는 Lesson이 될 수 있다.

반복되면 Rule로 승격한다.

계속 반복되고 기계적으로 검사 가능하면 Validator/Test로 강제한다.

# 6. 모든 실패를 Lesson으로 만들지 않는다

작은 일회성 실수까지 모두 저장하면 Lesson Store가 쓰레기통이 된다.

예:

```text
변수명 오타 한 번

일시적 Network Timeout

단순 명령어 Typo
```

같은 것은 일반적으로 영구 Lesson으로 만들 필요가 없다.

---

# 7. Lesson 가치 판정

다음 질문을 한다.

```text
1. 다시 발생할 가능성이 있는가?

2. 다른 Feature에서도 발생할 수 있는가?

3. 발생하면 비용이나 위험이 큰가?

4. 원인이 일반화 가능한가?

5. 미래 Agent가 이 Lesson을 알면 행동이 달라지는가?
```

여러 항목이 YES라면 Lesson 후보가 된다.

---

# 8. Lesson 생성 조건

다음 중 하나 이상이면 Lesson 생성 가치가 높다.

```text
사용자가 직접 잘못을 지적함

Regression 발생

동일 유형 Test 두 번 이상 실패

Shared Code 영향 누락

Security / Permission 오류

API Contract 파손

DB 영향 누락

잘못된 모호성 해석

AI가 존재하지 않는 API를 추측

관련 없는 Refactoring 발생

Verification 없이 완료 주장

Token 낭비가 반복
```

---

# 9. Failure와 Symptom을 구분한다

예:

```text
Symptom:
화면에 "공석" 표시
```

문제가 아닐 수도 있다.

진짜 Failure:

```text
API 호출 실패인데도 "공석"으로 표시
```

Root Cause:

```text
Empty State와 Error State를 동일하게 처리함
```

Lesson은 Symptom이 아니라 Root Cause 수준에서 만든다.

---

# 10. Root Cause 우선

다음처럼 기록하지 않는다.

```text
LESSON:
TodayShiftCard를 조심한다.
```

너무 구체적이고 재사용 가치가 낮다.

권장:

```text
LESSON:
Nullable business data와 request failure를
동일한 empty state로 처리하지 않는다.
```

---

# 12. REQUIREMENT_ERROR

사용자 의도를 잘못 이해한 경우.

예:

```text
"고급스럽게"
→ AI가 임의로 검정/금색 사용
```

예방:

```text
Ambiguity / Grill Policy
```

---

# 13. ASSUMPTION_ERROR

검증되지 않은 가정을 사실처럼 사용.

예:

```text
외부 Consumer가 없을 것이라고 가정
```

예방:

```text
find_references
+
Assumption Policy
```

---

# 14. DISCOVERY_ERROR

잘못된 구현 위치를 선택.

예:

```text
파일명만 보고 Feature 구현 파일이라고 판단
```

예방:

```text
Feature Map
+
Code Graph
```

---

# 15. IMPLEMENTATION_ERROR

코드 자체의 논리 오류.

예:

```text
null branch 잘못 처리
```

예방:

```text
Regression Test
```

---

# 16. SCOPE_ERROR

불필요한 변경.

예:

```text
단순 UI 수정 중 Shared API Client 리팩터링
```

예방:

```text
Change Contract
+
Diff Budget
```

---

# 17. CONVENTION_ERROR

프로젝트 표준과 다른 구현.

예:

```text
apiClient가 있는데 직접 axios 사용
```

예방:

```text
Convention Map
```

---

# 18. DEPENDENCY_ERROR

Library/API 사용법을 잘못 추측.

예:

```text
현재 설치 버전에 없는 함수 사용
```

예방:

```text
Installed Version
+
Official API Verification
```

---

# 19. VERIFICATION_ERROR

검증 없이 성공으로 판단.

예:

```text
Test 작성했지만 실행하지 않고 PASS라고 보고
```

예방:

```text
Verification Gate
```

---

# 20. ORCHESTRATION_ERROR

잘못된 Subagent 배치.

예:

```text
단순 탐색을 Frontier 모델이 직접 수행
```

또는:

```text
어려운 Architecture 판단을 Efficient 모델에 맡김
```

예방:

```text
Routing Policy 수정
```

---

# 21. TOKEN_EFFICIENCY_ERROR

작업은 성공했지만 비효율적이었다.

예:

```text
Subagent 4명에게 Parent Context 전체 40K씩 전달
```

예방:

```text
Task Packet
+
Context Isolation
```

# 22. Severity 분류

Lesson에는 심각도를 부여할 수 있다.

```text
S1 — LOW

S2 — MEDIUM

S3 — HIGH

S4 — CRITICAL
```

---

# 23. S1 LOW

예:

```text
불필요한 작은 Formatting

사소한 Naming 오류
```

일반적으로 영구 Rule까지 승격하지 않는다.

---

# 24. S2 MEDIUM

예:

```text
Feature 동작 오류

불필요한 파일 수정

일반 Regression
```

Lesson + Regression Test 후보.

---

# 25. S3 HIGH

예:

```text
API Contract break

Shared code regression

DB Migration 문제

사용자 요구와 다른 결과
```

Lesson + Rule + Test를 적극 고려한다.

---

# 26. S4 CRITICAL

예:

```text
Authentication bypass

Permission escalation

Production data loss

Secret leakage

Financial calculation corruption
```

설명형 Lesson만으로 끝내지 않는다.

가능하면:

```text
Guardrail

Validator

Test

Approval Gate
```

까지 승격한다.

# 29. Lesson 예시

```text
LESSON ID:
LESSON-001

Title:
Empty State와 Error State를 분리한다.

Category:
IMPLEMENTATION_ERROR

Severity:
S2

Trigger:
- nullable data
- empty state
- fallback UI
- API failure

Failure:
API 호출 실패를 데이터 없음으로 처리하여
화면에 "공석" 표시.

Impact:
실제 장애가 정상적인 공석 상태처럼 숨겨짐.

Root Cause:
business data null 여부만 확인하고
request status를 확인하지 않음.

Correct Behavior:
- 요청 성공 + 데이터 없음 → 공석
- 요청 실패 → 오류 상태

Prevention Rule:
Empty State와 Error State를 별도 상태로 처리한다.

Regression Test:
TodayShiftCard.error-state.test.tsx

Status:
ACTIVE

Occurrences:
1
```

# 30. Lesson은 짧게 유지한다

Lesson 자체가 새로운 Context 낭비가 되어서는 안 된다.

긴 사고 과정이나 전체 대화를 저장하지 않는다.

보존:

```text
무슨 실수

왜 발생

다음에는 어떻게 방지

어떻게 검증
```

만 유지한다.

```text
Feature ID
```

# 33. 왜 Trigger가 필요한가

매 작업마다 모든 Lesson을 Context에 넣으면 실패다.

따라서:

```text
CURRENT TASK

↓

FEATURE / SYMBOL / RISK / KEYWORDS

↓

LESSON MATCH

↓

TOP RELEVANT LESSONS ONLY
```

방식을 사용한다.

# 34. Lesson Recall

작업 전 또는 관련 위험 발견 시:

```text
lesson.find_relevant(
  feature,
  task_type,
  affected_symbols,
  risk,
  keywords
)
```

같은 인터페이스를 사용할 수 있다.

---

# 35. Recall은 선택적으로

예:

사용자 요청:

```text
Empty State 추가
```

Relevant:

```text
LESSON-001 empty-vs-error
```

Irrelevant:

```text
LESSON-032 Docker image naming
```

는 읽지 않는다.

# 37. High-Severity Lesson 우선

관련성이 비슷하다면 S4/S3 Lesson을 우선 Recall한다.

---

# 38. Lesson Context Budget

한 작업에서 필요한 Lesson만 소수 로드한다.

예:

```text
Top 3~5 relevant lessons
```

정도를 기본으로 할 수 있다.

고정 수가 아니라 정보 가치 기준으로 결정한다.

---

# 39. Duplicate Lesson 금지

같은 Root Cause에 대해 Lesson을 여러 개 만들지 않는다.

예:

```text
LESSON-001
공용 Hook consumer 확인 안 함

LESSON-017
Shared Hook 영향 확인 안 함
```

같은 내용이면 병합한다.

---

# 40. Lesson Deduplication

신규 Lesson 생성 전:

```text
Search existing lessons

↓

Same root cause?

YES
→ occurrence +1

NO
→ new lesson
```

# 41. Occurrence Count

반복 횟수를 기록한다.

```text

```

```text
Occurrences:

```

# 43. Promotion Criteria

다음 중 하나 이상이면 Rule 승격을 고려한다.

```text
동일 유형 2회 이상 발생

S3 이상

여러 Feature에서 발생

사용자 재지적

Review에서 반복 발견

비용이 큰 재작업 발생
```

---

# 44. 횟수는 절대 기준이 아니다

Critical 문제는 첫 번째 발생부터 Guardrail을 만들 수 있다.

예:

```text
Production 데이터 삭제
```

는:

```text
Occurrences = 1
```

이어도 자동 보호 장치가 필요할 수 있다.

# 47. Lesson과 Rule 차이

Lesson:

> 과거에 무엇을 잘못했고 무엇을 배웠는가?

Rule:

> 앞으로 무엇을 반드시 해야 하는가?

---

# 48. Rule에서 Automation으로 승격

질문:

```text
이 규칙을 사람이 읽지 않아도
기계적으로 검사할 수 있는가?
```

YES면 자동화를 우선한다.

# 49. Prevention Hierarchy

재발 방지 강도:

```text
1. MEMORY / LESSON

2. PROMPT RULE

3. CHECKLIST / GATE

4. TEST

5. STATIC VALIDATOR

6. CI GUARDRAIL

7. ARCHITECTURAL CONSTRAINT
```

가능하면 아래 단계로 내려갈수록 더 강력하다.

---

# 50. 가장 좋은 재발 방지

AI에게:

```text
"다음에는 조심하세요."
```

라고 하는 것은 가장 약한 방지책이다.

가능하다면:

```text
Test가 실패하게 만든다.
```

가 더 좋다.

---

# 51. Regression Test 우선

Bug가 테스트로 재현 가능하면 Regression Test를 추가한다.

```text
Bug

↓

Failing Test

↓

Fix

↓

Passing Test
```

---

# 52. Test 이름도 Intent를 표현

예:

```text
should_show_error_when_request_fails
```

가:

```text
test_case_12
```

보다 좋다.

---

# 53. Validator 승격

예:

실수:

```text

```

기계적으로 검사 가능하다면:

```text
codemap impact validator
```

같은 도구로 승격할 수 있다.

---

# 54. Linter 승격

예:

금지 패턴:

```text
direct axios usage
```

프로젝트 표준:

```text
apiClient
```

이면 custom lint rule을 고려할 수 있다.

---

# 55. CI Guardrail

반복적으로 발생하고 Merge 전 잡을 수 있다면 CI에 넣는다.

예:

```text
API schema diff

Migration check

Code Map stale check

Forbidden dependency
```

---

# 56. Architecture Guardrail

가장 강한 형태.

예:

```text
Permission 검사를 모든 Controller가 직접 하지 않고
공용 Guard가 강제로 수행
```

처럼 실수 자체가 구조적으로 어려워지게 만든다.

---

# 57. 사용자 지적도 Failure Signal

사용자가:

```text
"아니, 그게 아니라..."
```

라고 수정하면 단순 Conversation Correction으로만 처리하지 않는다.

다음 질문을 내부적으로 한다.

```text
왜 처음부터 잘못 이해했는가?

모호성 때문인가?

기존 Context를 놓쳤는가?

AI가 임의 추측했는가?

다음에도 발생 가능한가?
```

---

# 58. 사용자 피드백 분류

```text
CORRECTION

NEW_REQUIREMENT

SCOPE_CHANGE

BUG_REPORT
```

을 구분한다.

새 요구사항을 과거 실수로 잘못 기록하지 않는다.

---

# 59. Corrective Feedback

예:

사용자:

```text
"나는 전체 Sidebar를 바꾸라고 한 게 아니라
카드만 바꾸라고 했어."
```

이는:

```text
SCOPE_ERROR
```

Lesson 후보가 된다.

---

# 60. New Requirement는 Lesson 아님

사용자:

```text
"그리고 Sidebar도 바꿔줘."
```

는 새 요구사항이다.

실수로 기록하지 않는다.

---

# 61. Root Cause Template

```text
ROOT CAUSE

Observed failure:
...

Immediate cause:
...

Underlying cause:
...

Why existing guard failed:
...

Prevention:
...
```

# 62. Five-Why를 무조건 사용하지 않는다

간단한 문제에 과도한 분석을 하지 않는다.

Root Cause가 명확하면 바로 기록한다.

---

# 63. Guard Failure 분석

이미 Rule이 있었는데도 실수가 발생했다면 더 중요하다.

질문:

```text
Rule이 로드되지 않았나?

Rule이 애매했나?

Agent가 무시했나?

검증이 없었나?

Router Trigger가 잘못됐나?
```

---

# 64. Policy Failure도 학습 대상

즉 Harness 자체가 실패할 수 있다.

예:

```text
Migration 변경인데
Router가 Migration Policy를 로드하지 않음.
```

이는:

```text
HARNESS_RULE_FAILURE
```

로 기록할 수 있다.

---

# 65. Router 개선

위 사례의 수정은 코드가 아니라:

```text
Trigger registry 개선
```

일 수 있다.

---

# 66. Subagent 실패 학습

Subagent도 Lesson을 직접 생성하지 않는 것을 기본으로 한다.

Subagent는:

```text
FAILURE_CANDIDATE
```

를 Parent에게 반환한다.

Orchestrator가 Lesson 저장 여부를 결정한다.

---

# 67. Orchestrator가 Canonical Lesson 소유

여러 Agent가 같은 실패를 각자 Lesson으로 만들지 않도록 한다.

# 68. Subagent Failure Result

```json
  "failureType": "ASSUMPTION_ERROR",
  "observed": "API consumer를 하나만 확인함",
  "suspectedRootCause": "reference search skipped",
  "lessonCandidate": true
}
```

```text
↓

↓

↓

↓

↓
```

순서로 연결한다.

# 70. Change Control 연동

실수 수정 과정에서도 Scope를 무제한 확장하지 않는다.

```text
↓

Change Control

↓

Minimal corrective diff
```

# 71. Checkpoint 연동

예:

```text
New Lesson:
LESSON-014 shared-hook-impact
```

만 기록한다.

---

# 72. Handoff 연동

다음 Agent에게 특히 관련 있는 Lesson ID만 전달한다.

예:

```text
Relevant Lessons:
- LESSON-014
```

# 73. Ambiguity Policy 연동

Requirement Error가 발생하면:

```text
Ambiguity trigger missing?
```

를 분석한다.

필요하면 Grill Trigger를 보강한다.

# 74. Codebase OS 연동


즉 오류가 AI 때문인지 Map 때문인지 구분한다.

# 75. Map Error도 Self-Healing

예:

```text

```

Root Cause:


```text

+

Staleness validator 강화
```

# 76. Multi-Agent Harness 연동

Routing Error:

```text
Task complexity underestimated
```

라면:

```text
Task Classifier
Capability threshold
Escalation condition
```

을 개선한다.

---

# 77. Token 효율도 학습

예:

```text
3명의 Scout가 같은 파일을 각각 읽음
```

Root Cause:

```text
Task partition overlap
```

Lesson:

```text
Parallel Scout는 탐색 범위를 명시적으로 분할
```

Automation:

```text
Task ownership / search scope allocator
```

---

# 78. Learning에도 ROI가 있다

모든 실패를 분석하는 비용이 가치 있는 것은 아니다.

다음과 같이 판단한다.

```text
Expected recurrence cost

×

Recurrence probability

>

Learning / Guardrail cost
```

일 때 적극적인 재발 방지 투자 가치가 높다.

---

# 79. High ROI Example

```text
Auth permission 실수

재발 가능성 중간

영향 매우 큼

→ 강한 Guardrail
```

---

# 80. Low ROI Example

```text
일회성 fixture 이름 Typo

재발해도 영향 작음

→ 저장하지 않음
```

---

# 81. Lesson Status

각 Lesson은 다음 상태를 가진다.

```text
ACTIVE

PROMOTED

RESOLVED_BY_AUTOMATION

OBSOLETE

ARCHIVED
```

---

# 82. ACTIVE

향후 Agent가 참고해야 함.

---

# 83. PROMOTED

Rule이나 Policy로 승격됨.

Lesson 자체를 Recall할 필요가 줄어들 수 있다.

---

# 84. RESOLVED_BY_AUTOMATION

Validator/Test가 자동으로 방지하므로 Prompt Context에서 제거 가능.

이 상태가 이상적이다.

---

# 85. OBSOLETE

Architecture 변경으로 더 이상 적용되지 않음.

---

# 86. Archive

오래된 Lesson을 Working Search 결과에서 제외한다.

---

# 87. Lesson Staleness

Lesson도 코드처럼 오래될 수 있다.

예:

```text
과거 axios 관련 Lesson
```

인데 프로젝트가 fetch 기반으로 완전히 변경됐다면 stale하다.

---

# 88. Lesson Validation

주기적으로 확인:

```text
Referenced feature still exists?

Referenced symbol still exists?

Rule still relevant?

Automation now covers it?
```

---

# 89. Lesson Cleanup

중복되거나 obsolete한 Lesson은 병합/Archive한다.

Lesson Store를 무한 증가시키지 않는다.

---

# 90. Learning Metrics

Harness 성숙도를 측정할 수 있다.

```text
Repeated Failure Rate

Lesson Recall Hit Rate

Regression Recurrence

Rule Promotion Count

Automated Prevention Rate

User Correction Rate
```

---

# 91. 가장 중요한 지표

```text
Same-Class Failure Recurrence Rate
```

즉:

> 같은 유형의 실수가 다시 얼마나 발생하는가?

---

# 92. 좋은 시스템

시간이 지날수록:

```text
Repeated Failure ↓

Automated Detection ↑

Manual Lesson Recall ↓
```

가 되어야 한다.

---

# 93. 잘못된 Learning 지표

Lesson 파일 개수가 많다고 좋은 시스템이 아니다.

오히려:

```text
Lesson 500개

Validator 0개
```

보다:

```text
Lesson 30개

Test/Validator 20개
```

가 더 성숙할 수 있다.

---

# 94. Learning Promotion Principle

장기적으로:

```text
Prompt Memory

↓

Executable Guardrail
```

로 이동하는 것이 목표다.

---

# 95. Failure Reproduction

가능하면 실패를 재현한다.

특히 Bug:

```text
Before Fix:
FAIL

After Fix:
PASS
```

증거를 남긴다.

---

# 96. Non-Reproducible Failure

재현할 수 없다면:

```text
UNVERIFIED ROOT CAUSE
```

로 기록한다.

추측을 확정된 Lesson으로 만들지 않는다.

---

# 97. Lesson Confidence

가능하면:

```text
VERIFIED

LIKELY

UNVERIFIED
```

를 사용할 수 있다.

---

# 98. VERIFIED Lesson

Root Cause가 테스트/코드/실행 결과로 확인됨.

---

# 99. LIKELY Lesson

강한 근거는 있지만 완전히 증명되지 않음.

강제 Rule 승격에는 주의한다.

---

# 100. False Learning 방지

잘못된 Root Cause를 Lesson으로 저장하면 미래 Agent를 더 잘못된 방향으로 유도한다.

따라서:

```text
Lesson quality > Lesson quantity
```

다.

---

# 101. Contradictory Lessons

두 Lesson이 충돌하면 둘 다 유지하며 평균내지 않는다.

```text
LESSON A:
Shared Hook 변경 금지

LESSON B:
Local duplicate보다 Shared Hook 수정 선호
```

이런 충돌은 Context에 따라 Rule을 재설계해야 한다.

---

# 102. Generalization Level

Lesson은 너무 구체적이지도, 너무 일반적이지도 않아야 한다.

너무 구체적:

```text
TodayShiftCard 87번째 줄 조심
```

너무 일반적:

```text
버그를 만들지 않는다.
```

좋은 수준:

```text
Nullable business state와 transport failure를 분리한다.
```

---

# 103. User-specific Preference와 Error Lesson 분리

사용자가 선호하는 스타일:

```text
카드는 compact하게
```

는 Preference다.

잘못된 구현:

```text
사용자가 "compact"라고 했는데
Layout 전체를 재설계
```

는 Error Lesson이다.

둘을 섞지 않는다.

---

# 104. Communication Error

기술적으로 작업은 맞았지만 설명이 이해하기 어려웠다면 이것도 개선 대상이다.

예:

```text
사용자가 "무슨 뜻이야?"라고 반복적으로 물음
```

Root Cause:

```text
전문 용어를 설명 없이 사용
```

Lesson:

```text
일반 사용자 설명에서는 전문용어에 쉬운 풀이와 예시 제공
```

---

# 105. Design Error

사용자가 디자인 결과를 여러 번 수정한다면:

```text
Requirement ambiguity?

Reference mismatch?

Subjective term miscalibration?

Visual measurement missing?
```

를 분석한다.

---

# 106. Image/UI Lesson 예

```text
LESSON:
"똑같이" 요청에서 감각적 재생성보다
기존 시안의 좌표/크기/간격/색상 측정을 우선한다.
```

이런 Lesson은 UI 구현에도 재사용 가능하다.

---

# 107. Learning Loop와 Grill 결합

사용자 정정이 모호성 때문이었다면:

```text
Failure
↓
Root Cause = ambiguity not resolved
↓
Add/adjust Grill trigger
```

로 끝나야 한다.

단순히:

```text
다음에는 더 주의
```

로 끝내지 않는다.

---

# 108. Learning Loop와 Plain Language 결합

설명 오류가 반복되면:

```text
Technical response
↓
User confusion
↓
Lesson
↓
Plain Language Rule
```

로 승격한다.

---

# 109. Model-specific Lesson 주의

가능하면:

```text
GPT-X는 이걸 못한다.
```

처럼 특정 모델명에 묶지 않는다.

대신:

```text
Low-capability coding worker에서
cross-layer dependency 추적 실패율 높음
```

처럼 Capability 기반으로 일반화한다.

---

# 110. Model-specific Telemetry는 별도 유지 가능

실제 성능 자료는 Model Registry/Benchmark에 기록한다.

Policy Lesson과 분리한다.

---

# 111. Routing Feedback

특정 Task Class가 자주 Escalation된다면:

```text
Efficient → Balanced
```

기본 Threshold를 올릴 수 있다.

즉 실수 학습이 Routing 개선으로 이어질 수 있다.

---

# 112. Promotion Decision

Lesson 승격 전:

```text
Is this better solved by:

Prompt?

Policy?

Test?

Validator?

Architecture?
```

를 판단한다.

가장 낮은 비용으로 가장 강한 방지책을 선택한다.

---

# 113. Prompt Rule 남발 금지

모든 실수를 `AGENTS.md`에 추가하면 다시 Context가 비대해진다.

따라서 Core Prompt에 바로 넣지 않는다.

---

# 114. Core Rule 승격 조건

다음 정도로 범용적이어야 한다.

```text
거의 모든 작업에서 중요

반복적으로 발생

큰 위험

짧게 표현 가능
```

---

# 115. Local Rule 우선

특정 DB 영역에서만 발생한다면:

```text
/prisma/AGENTS.md
```

또는:

```text
migration-policy
```

에 넣는다.

Root Core를 오염시키지 않는다.

---

# 116. Feature-specific Lesson

특정 Feature에서만 중요한 경우:

```text
docs/features/shift-management.md
```

또는 Feature Lesson Tag로 제한한다.

---

# 117. Lesson Promotion Matrix

```text
Single / Low
→ no persistent lesson

Single / Medium
→ lesson

Repeated / Medium
→ rule + test

Single / High
→ lesson + test

Repeated / High
→ validator / gate

Critical
→ immediate hard guardrail where feasible
```

# 118. 사용자 지적 직후 행동

사용자가 잘못을 지적하면:

```text
1. 현재 결과 수정

2. 왜 발생했는지 분류

3. 동일 유형 재발 가능성 평가

4. 가치가 있으면 Lesson 생성/갱신

5. 관련 Test/Guardrail 추가

6. 다시 검증
```

순서를 따른다.

단 사용자에게 내부 Learning 기록을 장황하게 보고할 필요는 없다.

# 119. Verification 실패 직후 행동

```text

↓

Do not immediately patch blindly.

↓

Classify failure.

↓

Identify root cause.

↓

Update Change Contract if scope changed.

↓

Make minimal fix.

↓

Re-run failed verification.

↓

Evaluate lesson.
```

# 120. Lesson 생성 자체도 검증한다

질문:

```text
이 Lesson이 실제 Root Cause를 설명하는가?

너무 일반적이지 않은가?

다음 Agent의 행동을 실제 바꿀 수 있는가?

기존 Lesson과 중복되지 않는가?
```

---

# 121. Anti-Pattern — Blame the Model

금지:

```text
모델이 실수했다.
```

로 끝내는 것.

더 유용한 질문:

```text
왜 Harness가 이 실수를 사전에 잡지 못했는가?
```

---

# 122. Anti-Pattern — Blame the User

모호한 요구였더라도:

```text
사용자가 애매하게 말했다.
```

로 끝내지 않는다.

Grill Policy가 제대로 동작했는지 본다.

---

# 123. Anti-Pattern — Lesson Explosion

한 작업 실패에서 10개의 Lesson을 만들지 않는다.

가능하면 핵심 Root Cause로 통합한다.

---

# 124. Anti-Pattern — Rule Without Trigger

```text
"항상 주의한다."
```

처럼 언제 적용해야 하는지 모르는 Rule은 약하다.

반드시 Trigger를 갖게 한다.

---

# 125. Anti-Pattern — Memory Only

심각한 Regression인데:

```text
LESSON.md에 적어두기
```

만 하고 테스트를 추가하지 않는 것을 피한다.

---

# 126. Anti-Pattern — Test Only

반대로 Test는 특정 버그를 막지만 원인이 넓은 문제라면 Rule도 필요할 수 있다.

예:

```text
한 Component 테스트
```

만으로 모든 Shared Hook consumer 누락을 막을 수 없는 경우.

---

# 127. Anti-Pattern — Wrong Generalization

한 번의 특정 문제를 지나치게 일반화하지 않는다.

예:

```text
axios 버그 발생
→ 외부 Library 사용 금지
```

같은 과잉 반응을 피한다.

---

# 128. Anti-Pattern — Permanent Old Rules

Architecture가 바뀌었는데 오래된 Lesson을 계속 Recall하지 않는다.

---

# 129. Learning Review

주기적으로 Lesson Store를 검토할 수 있다.

확인:

```text
Duplicate

Obsolete

Promoted

Automated

Still recurring
```

# 130. Harness Evaluation 연동

```text
User Corrections: 2
```

# 131. 이상적인 변화

```text
Relevant Lesson Recall ↑

Token Rework ↓
```

가 되어야 한다.

# 136. Definition of Learned Failure

# 137. Definition of Anti-Regression Success


보다:

```text
Harness가 수정 전에 경고했다

또는

Test/Validator가 Merge 전에 차단했다
```

가 더 높은 성공 수준이다.

# 138. Instruction Router Trigger

```text

REPEATED_REWORK

SCOPE_ERROR

SECURITY_FAILURE

HARNESS_FAILURE

MODEL_ROUTING_FAILURE

TOKEN_EFFICIENCY_FAILURE
```

평상시 모든 작업에서 전체 Policy를 유지하지 않는다.

# 139. 작업 성공 시에는 불필요하게 Learning Loop를 실행하지 않는다

특별한 문제 없이 정상 완료된 작업마다 Lesson을 만들 필요는 없다.

# 140. 압축 Core 지침

전체 문서를 매번 로드하지 못하는 경우 다음만 유지한다.

```text
ERROR LEARNING / ANTI-REGRESSION CORE

1. Do not merely fix a meaningful failure and forget it.
2. Classify the failure and identify the root cause before creating a lesson.
3. Store lessons only when the failure is reusable, likely to recur, costly, risky, or broadly applicable.
4. Generalize lessons at the root-cause level, not at a single file or line-number level.
5. Keep lessons short: trigger, failure, root cause, prevention, verification.
6. Before relevant future tasks, recall only the small set of matching lessons.
7. Deduplicate lessons; repeated occurrences should increase the existing lesson count.
8. Promote repeated or high-risk lessons into enforceable rules.
9. Prefer regression tests, validators, CI checks, or architectural guardrails over permanent prompt text whenever the failure can be checked automatically.
10. Critical failures may require hard guardrails after the first occurrence.
11. Treat user corrections, verification failures, routing failures, scope errors, and token-efficiency failures as possible learning signals.
12. Distinguish new requirements from actual past mistakes.
13. If an existing rule failed to prevent the error, fix the rule, trigger, router, or validator instead of merely adding another reminder.
14. Remove or archive obsolete lessons so the lesson store does not pollute context.
15. The goal is not to accumulate lessons; the goal is to reduce repeated failure.
```

# 141. Final Principle

> 사람에게 “다음부터 조심해”라고 말하는 것보다 체크리스트가 강하다.

> 체크리스트보다 테스트가 강하다.

> 테스트보다 구조적으로 실수할 수 없게 만드는 것이 더 강하다.

따라서 이 Harness는 실패할 때마다 가능하면 다음 방향으로 진화한다.

```text
HUMAN / AI MEMORY

↓

LESSON

↓

RULE

↓

TEST

↓

VALIDATOR

↓

GUARDRAIL

↓

ARCHITECTURAL PREVENTION
```

최종 목표는:

> AI가 같은 실수를 기억해서 피하는 시스템

이 아니라,

> **같은 실수를 하려고 해도 시스템이 먼저 발견하거나 차단하는 시스템**

이다.
