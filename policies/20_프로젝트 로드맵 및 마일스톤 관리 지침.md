# Master Roadmap & Milestone Policy v1

## 프로젝트 전체 로드맵·단계·마일스톤·현재 위치 관리 지침

Version: 1.0

---

# 0. 목적

이 Policy는 장기간 진행되는 개발 프로젝트에서 AI Agent가 다음 문제를 겪지 않도록 한다.

```text
전체 프로젝트 목표를 잊음

지금 어느 단계인지 모름

현재 작업이 전체 프로젝트에서 왜 필요한지 모름

앞으로 무엇을 해야 하는지 모름

작은 Task에 몰입하다 전체 방향을 잃음

완료된 작업을 다시 조사

선행 작업 없이 후속 기능부터 구현

중요 Milestone 누락

프로젝트가 끝없이 확장됨
```

이를 방지하기 위해 프로젝트를 다음 계층으로 관리한다.

```text
PROJECT GOAL

↓

PHASE

↓

MILESTONE

↓

WORKSTREAM / FEATURE

↓

TASK
```

핵심 목표:

> AI는 어떤 Task를 수행하더라도 항상 “이 작업이 전체 프로젝트의 어디에 위치하는가?”에 답할 수 있어야 한다.

---

# 1. 최상위 원칙

모든 중요한 작업은 프로젝트의 상위 목표와 연결되어야 한다.

다음과 같은 상태를 허용하지 않는다.

```text
Task는 존재하지만
왜 필요한지 모름
```

대신:

```text
Task
↓
Feature
↓
Milestone
↓
Phase
↓
Project Goal
```

추적 가능해야 한다.

---

# 2. Roadmap의 역할

Roadmap은 단순한 TODO 목록이 아니다.

Roadmap이 답해야 할 질문:

```text
우리는 무엇을 만들고 있는가?

왜 만들고 있는가?

큰 단계는 무엇인가?

각 단계가 끝났다고 어떻게 판단하는가?

현재 어느 단계인가?

다음 단계는 무엇인가?
```

---

# 3. Roadmap과 Task List 차이

Task List:

```text
파일 수정

API 추가

테스트 추가
```

Roadmap:

```text
Phase 1:
기초 데이터 구조 완성

Phase 2:
자동 스케줄 생성

Phase 3:
대체근무 처리

Phase 4:
운영 검증
```

Task List는 실행 단위다.

Roadmap은 방향과 순서를 관리한다.

---

# 4. 프로젝트 계층

기본 계층:

```text
PROJECT

├─ PHASE
│  ├─ MILESTONE
│  │  ├─ WORKSTREAM / FEATURE
│  │  │  └─ TASK
```

모든 프로젝트에서 이 모든 계층이 반드시 필요한 것은 아니다.

작은 프로젝트에서는:

```text
PROJECT

↓

MILESTONE

↓

TASK
```

정도로 단순화할 수 있다.

---

# 5. PROJECT

Project는 최상위 목적이다.

예:

```text
Project:
교대근무 관리 시스템
```

Project Goal:

```text
근무조, 근무 패턴, 휴가, 대체근무를
자동 계산하고 관리할 수 있는 시스템 구축
```

---

# 6. Project Goal은 기능 목록이 아니다

나쁜 예:

```text
Goal:
로그인
달력
휴가
대체근무
설정
```

좋은 예:

```text
Goal:
교대근무 운영자가 수작업 없이
근무 일정과 휴가/대체근무를 관리할 수 있게 한다.
```

기능은 Goal을 달성하기 위한 수단이다.

---

# 7. Project Success Criteria

프로젝트 전체 완료 조건을 정의한다.

예:

```text
[ ] 근무조 생성 가능

[ ] 패턴 기반 일정 자동 생성

[ ] 휴가 승인 일정 반영

[ ] 대체근무 반영

[ ] 수당 정책 적용

[ ] 월간 Calendar 조회 가능

[ ] 주요 업무 테스트 통과
```

---

# 8. PHASE

Phase는 프로젝트의 큰 개발 단계다.

예:

```text
PHASE 1 — FOUNDATION

PHASE 2 — SCHEDULING

PHASE 3 — LEAVE / REPLACEMENT

PHASE 4 — OPERATIONS

PHASE 5 — HARDENING
```

---

# 9. Phase는 결과 중심으로 정의한다

나쁜 Phase:

```text
코딩

테스트

수정
```

좋은 Phase:

```text
FOUNDATION
핵심 Domain 구조를 만든다.

SCHEDULING
근무 패턴에서 실제 일정을 생성한다.

OPERATIONS
실제 운영에서 사용할 수 있도록 관리 기능을 완성한다.
```

---

# 10. PHASE Exit Condition

각 Phase에는 종료 조건이 있어야 한다.

예:

```text
PHASE 1 FOUNDATION

Exit:

- Employee 모델 확정
- Shift Group 모델 확정
- Pattern 모델 확정
- 기본 CRUD 검증
```

Exit Condition이 없으면 Phase가 끝없이 늘어날 수 있다.

---

# 11. MILESTONE

Milestone은 사용자 또는 시스템 관점에서 의미 있는 완료 지점이다.

예:

```text
M1.1 근무조 모델 완성

M1.2 근무 패턴 엔진 완성

M2.1 월간 일정 생성

M3.1 휴가 반영

M3.2 대체근무 반영
```

---

# 12. Milestone은 파일 단위가 아니다

나쁜 예:

```text
M1:
ShiftService.ts 작성
```

좋은 예:

```text
M1:
등록된 근무 패턴을 기반으로
날짜별 근무 상태를 계산할 수 있다.
```

---

# 13. Outcome-based Milestone

Milestone은 가능하면 다음 질문에 답해야 한다.

> 이 단계가 끝났을 때 사용 가능해지는 것은 무엇인가?

---

# 14. Milestone Success Criteria

예:

```text
M2.1 Pattern Engine

Success:

Given:
Pattern = 주주주휴휴휴야야야휴휴휴

When:
Start date = 2026-09-01

Then:
각 날짜별 주/야/휴무 상태가 정확히 계산됨

그리고:
각 조의 시작 Offset 반영
```

---

# 15. Workstream

큰 프로젝트에서는 서로 다른 작업 흐름을 나눌 수 있다.

예:

```text
Frontend

Backend

Database

Infrastructure

Design

Documentation
```

또는 Domain 기준:

```text
Scheduling

Leave

Replacement

Permission
```

---

# 16. Workstream은 무조건 만들지 않는다

Workstream은 병렬 개발이나 책임 분리가 필요할 때 사용한다.

작은 프로젝트에서 복잡도만 늘리지 않는다.

---

# 17. FEATURE

Feature는 사용자가 인지 가능한 기능 단위다.

예:

```text
shift.pattern

shift.calendar

leave.request

leave.approval

replacement.shift
```

가능하면 기존 Feature Map의 Stable Feature ID를 사용한다.

---

# 18. TASK

Task는 실제 실행 단위다.

예:

```text
Pattern Engine에서 Offset 계산 구현

관련 Unit Test 추가

Calendar API 연결
```

Task는 한 Milestone에 연결되어야 한다.

---

# 19. Orphan Task 금지

다음처럼 상위 목적이 없는 Task:

```text
Refactor ShiftUtils

Update lodash

Rename service
```

는 바로 실행하지 않는다.

질문:

```text
어떤 Milestone을 위해 필요한가?
```

답이 없다면:

```text
PARKING LOT
```

후보로 보낸다.

---

# 20. Roadmap 상태

Project/Phase/Milestone에는 기본적으로 다음 상태를 사용한다.

```text
TODO

READY

ACTIVE

BLOCKED

DONE

DEFERRED

CANCELLED
```

---

# 21. TODO

아직 시작 조건이 충족되지 않았거나 시작하지 않은 상태.

---

# 22. READY

선행 조건이 충족되어 시작할 수 있는 상태.

---

# 23. ACTIVE

현재 실제 작업 중.

가능하면 동시에 너무 많은 ACTIVE Milestone을 두지 않는다.

---

# 24. BLOCKED

외부 조건 또는 선행 작업 때문에 진행 불가.

Blocker를 반드시 기록한다.

---

# 25. DONE

Milestone Success Criteria와 필수 Verification이 충족된 상태.

단순 구현 완료가 아니다.

---

# 26. DEFERRED

현재 Release 또는 Scope에서 미룸.

---

# 27. CANCELLED

더 이상 필요하지 않음.

---

# 28. 상태 이동

기본:

```text
TODO
↓
READY
↓
ACTIVE
↓
DONE
```

실패:

```text
ACTIVE
↓
BLOCKED
```

필요하면:

```text
TODO / ACTIVE
↓
DEFERRED
```

---

# 29. DONE 조건

다음만으로 DONE 처리하지 않는다.

```text
코드를 작성함

PR 생성

Agent가 구현 완료라고 판단
```

필요:

```text
Milestone Success Criteria 충족

+

Required Verification 완료
```

---

# 30. Current Position

AI는 Working State에 현재 위치를 유지한다.

예:

```text
PROJECT:
Shift Management System

PHASE:
P2 Scheduling

MILESTONE:
M2.2 Calendar Generation

FEATURE:
shift.schedule.calendar

TASK:
Generate month view from pattern result
```

---

# 31. Current Position은 중요 정보

Context 압축 시 삭제하지 않는다.

Checkpoint에 항상 포함할 가치가 높다.

---

# 32. 프로젝트 작업 전 질문

AI는 프로젝트 작업을 시작할 때 최소 다음을 파악한다.

```text
1. Project Goal은 무엇인가?

2. 현재 Phase는 무엇인가?

3. 현재 Milestone은 무엇인가?

4. 이 Task는 어떤 Milestone을 위해 필요한가?

5. 완료되면 다음 Milestone은 무엇인가?
```

---

# 33. 현재 위치를 모를 경우

Roadmap이 존재한다면 읽는다.

```text
.ai/project/roadmap.md
```

또는 해당 Project State를 확인한다.

---

# 34. Roadmap이 없는 기존 프로젝트

전체 Repository를 무조건 다 읽어서 Roadmap을 만들지 않는다.

다음 순서를 권장한다.

```text
User Goal

↓

Current Product Structure

↓

Existing Features

↓

Major Missing Capabilities

↓

High-level Roadmap Draft

↓

현재 관련 영역부터 검증
```

---

# 35. Roadmap Bootstrap

새 프로젝트 시작 시:

```text
USER GOAL

↓

MAJOR CAPABILITIES

↓

DEPENDENCIES

↓

PHASES

↓

MILESTONES

↓

SUCCESS CONDITIONS
```

으로 생성한다.

---

# 36. 사용자 자연어를 그대로 Roadmap으로 복사하지 않는다

예:

사용자:

```text
로그인도 하고
달력도 하고
나중에 통계도 넣고...
```

AI는 이를 구조화한다.

---

# 37. Roadmap은 구현 세부사항을 과도하게 포함하지 않는다

나쁜 예:

```text
M2.1
useMemo 추가
```

좋은 예:

```text
M2.1
월간 근무표 자동 생성
```

---

# 38. Roadmap은 안정적이어야 한다

함수명, 파일명 같은 세부사항은 자주 바뀐다.

Roadmap은 사용자 결과와 Capability 중심으로 유지한다.

---

# 39. Roadmap 변경

Roadmap도 변경될 수 있다.

다음 상황에서 갱신할 수 있다.

```text
새로운 사용자 요구

기술적 제약 발견

Milestone 분해 필요

Requirement 삭제

Architecture 결정으로 순서 변경
```

---

# 40. Roadmap Drift와 Replanning 구분

Roadmap 변경 자체는 문제가 아니다.

하지만:

```text
"하다 보니 이 기능도 넣자"
```

만으로 변경하지 않는다.

근거가 필요하다.

---

# 41. Roadmap 변경 이유

Material 변경 시:

```text
ROADMAP CHANGE

Original:
...

New:
...

Reason:
...

Affected Milestones:
...

Priority Impact:
...
```

를 기록할 수 있다.

---

# 42. Roadmap Version

큰 프로젝트에서는 Version을 둘 수 있다.

```text
ROADMAP v1

ROADMAP v2
```

---

# 43. Minor 변경에는 Version을 남발하지 않는다

단순 Status 갱신은 Version 증가 대상이 아니다.

---

# 44. Milestone ID

안정적인 ID를 사용한다.

예:

```text
P1-M1

P1-M2

P2-M1
```

또는:

```text
M1.1

M1.2

M2.1
```

한 프로젝트에서 일관된 방식만 사용한다.

---

# 45. Milestone ID는 이름 변경에도 유지 가능

예:

```text
M2.2 Calendar Generator
```

↓

```text
M2.2 Monthly Schedule Builder
```

이름은 바뀌어도 ID는 유지할 수 있다.

---

# 46. Dependency

Milestone 간 선행 관계를 표시한다.

예:

```text
M2.1 Pattern Engine

↓

M2.2 Calendar Generation
```

Calendar가 Pattern Engine 결과에 의존한다면 M2.1 완료 전 M2.2를 깊게 구현하지 않는다.

---

# 47. Dependency 표기

예:

```text
M2.2

Depends On:
M2.1
```

---

# 48. 병렬 Milestone

독립적이면 병렬 진행 가능하다.

예:

```text
M2.3 Holiday Data

M2.4 Calendar UI Prototype
```

서로 직접 의존하지 않는다면 병렬 가능.

---

# 49. 단순 Roadmap에서는 DAG 전체를 만들지 않는다

복잡한 의존성은 별도의 Task DAG Policy에서 관리한다.

Roadmap은 주요 선행관계만 표현한다.

---

# 50. Milestone Size

너무 큰 Milestone:

```text
전체 근무 시스템 완성
```

은 관리가 어렵다.

너무 작은 Milestone:

```text
버튼 하나 추가
```

는 Roadmap을 Task List로 만든다.

---

# 51. 좋은 Milestone 크기

하나의 명확한 사용자/시스템 Capability가 완성되는 수준.

---

# 52. Milestone 분할 신호

다음이면 분할을 고려한다.

```text
성공 조건이 너무 많음

여러 Domain 포함

독립적으로 배포 가능

한 Milestone 안에 여러 큰 위험 존재

Active Plan이 지나치게 길어짐
```

---

# 53. Milestone 병합 신호

다음이면 합칠 수 있다.

```text
각각 독립적 가치 없음

항상 같이 구현

Verification도 동일

지나치게 잘게 분할
```

---

# 54. MVP Roadmap

프로젝트에 반드시 필요한 것과 나중에 가능한 것을 구분한다.

예:

```text
MVP

P1 Foundation
P2 Scheduling
P3 Leave

LATER

Statistics
Advanced analytics
AI recommendation
```

---

# 55. Scope Horizon

Roadmap을 다음처럼 구분할 수 있다.

```text
NOW

NEXT

LATER
```

특히 장기 프로젝트에서 유용하다.

---

# 56. NOW

현재 Release / 현재 Phase.

높은 상세도.

---

# 57. NEXT

다음 Phase.

중간 상세도.

---

# 58. LATER

장기 방향.

낮은 상세도.

세부 구현까지 미리 결정하지 않는다.

---

# 59. Progressive Planning

멀리 있는 Milestone일수록 세부 계획을 적게 둔다.

```text
현재 Milestone
→ 매우 구체적

다음 Milestone
→ 중간

6개월 뒤
→ Goal 수준
```

---

# 60. 왜 Progressive Planning이 필요한가

미래의 상세계획은 현재 정보가 부족해 쉽게 틀린다.

따라서 Roadmap은 미래를 지나치게 고정하지 않는다.

---

# 61. Roadmap ≠ Promise

Roadmap은 현재 정보 기반 계획이다.

새로운 사실에 따라 수정 가능하다.

---

# 62. Project North Star

장기 프로젝트에는 한 줄짜리 North Star를 둘 수 있다.

예:

```text
운영자가 Excel 수작업 없이
근무 일정과 대체근무를 운영할 수 있게 한다.
```

---

# 63. North Star 활용

새 기능 제안 시 질문:

```text
이 기능이 North Star에 직접 기여하는가?
```

NO면 현재 Roadmap 밖일 수 있다.

---

# 64. Roadmap Scope Guard

Roadmap에 없는 새로운 Feature를 발견했다고 즉시 구현하지 않는다.

```text
NEW IDEA

↓

Required for active milestone?

YES
→ evaluate

NO
→ Parking Lot
```

---

# 65. Parking Lot 연동

Roadmap 외 아이디어:

```text
PL-001
Advanced Statistics

PL-002
AI Schedule Recommendation
```

같이 별도 저장한다.

---

# 66. Parking Lot은 Roadmap이 아니다

아직 승인/우선순위가 결정되지 않은 아이디어다.

---

# 67. Parking Lot → Roadmap 승격

다음 경우 고려:

# 85. Roadmap Reordering

새 Dependency가 발견되면 순서를 변경할 수 있다.

예:


# 87. User Request vs Current Roadmap

사용자가 현재 Roadmap 순서와 다른 작업을 요청할 수 있다.

현재 사용자의 명시적 요청이 우선할 수 있다.

# 88. Out-of-order Work

예:

현재:


```text
먼저 관리자 권한 화면 만들어줘.
```

이면:

```text
User-directed priority change
```

로 Roadmap/Active State를 갱신한다.

# 89. Roadmap이 사용자의 직접 요청을 막지 않는다

# 107. Roadmap 생성 시 사용자 언어

Plain Language Policy를 적용한다.

좋음:

```text
근무 데이터 저장 구조 완성
```

# 108. Roadmap Granularity Check

Roadmap을 보고:

```text
너무 큰가?

너무 작은가?

파일 목록처럼 되어 있지 않은가?
```

확인한다.

# 109. Roadmap Completeness

초기 Roadmap이 모든 미래 요구를 포함할 필요는 없다.

# 110. Unknown Future Work

```text
LATER / TBD
```

로 둘 수 있다.

근거 없는 Feature를 미리 채우지 않는다.

# 111. Technical Debt

기술 부채는 별도 Track 또는 Parking Lot에 둘 수 있다.

현재 Milestone에 필수적인 경우에만 Active Scope로 올린다.

---

# 112. Technical Debt Roadmap

중요성이 커지면:

```text
Hardening Phase
```

에 정식 Milestone으로 넣을 수 있다.

---

# 113. Discovery Milestone

불확실성이 큰 영역에서는 구현보다 조사 자체가 Milestone일 수 있다.

예:

```text
M0.2
외부 API 가능성 검증
```

Success:

```text
지원 여부 확인
비용 확인
기술 위험 확인
```

---

# 114. Spike

단기간 기술 검증 작업을 Spike로 표현할 수 있다.

```text
SPIKE-001
WebSocket feasibility
```

결과는 구현이 아니라 Decision Evidence다.

---

# 115. Spike가 영구 Feature로 변하지 않게 한다

성공/실패 후 종료한다.

---

# 116. Release와 Roadmap

예:


# 117. Release Gate

Release에 필요한 Milestone이 모두 VERIFIED되어야 한다.

---

# 118. Milestone Acceptance

각 Milestone 완료 시 다음 질문을 한다.

```text
이 Milestone의 사용자/시스템 결과가 실제로 존재하는가?

Success Criteria가 통과했는가?

다음 Milestone이 시작 가능한가?
```

# 119. Milestone 완료 후

```text
↓

```

# 120. 자동 Advance 주의

다음 Milestone을 계획 상태로 이동할 수 있지만 사용자가 다른 우선순위를 지정했다면 따르지 않는다.

---

# 121. Phase Completion

모든 Required Milestone 완료:

```text
Phase Exit Criteria
```

를 다시 확인한다.

---

# 122. Milestone이 모두 DONE이어도 Phase Exit 조건 실패 가능

예:

각 기능은 있지만 통합 테스트가 없음.

Phase는 아직 DONE이 아닐 수 있다.

---

# 123. Roadmap Health Check

장기 프로젝트에서는 가끔 다음을 검사한다.

```text
현재 Goal과 여전히 맞는가?

취소된 Milestone이 남아있는가?

Priority가 오래되었나?

Blocker가 방치됐나?

Parking Lot이 무분별하게 Roadmap으로 들어왔나?
```

---

# 124. Health Check는 매 Task마다 하지 않는다

Milestone/Phase 전환 또는 큰 Requirement 변경 시 수행한다.

---

# 125. Roadmap Staleness

Roadmap의 Current Position과 실제 구현 상태가 다르면 갱신한다.

---

# 126. Source of Truth

Roadmap이 DONE이라고 해도 실제 코드/검증 결과가 다르면 실제 상태를 우선한다.

---

# 127. Roadmap Self-Healing

예:

```text

M2.1 DONE

Reality:
Critical tests failing
```

이면:

```text

→ ACTIVE 또는 BLOCKED
```

로 되돌릴 수 있다.

---

# 128. No Fake Progress

사용자에게 진행률을 높게 보이기 위해 DONE을 남발하지 않는다.

---

# 129. Percentage Progress 주의


가 더 명확할 수 있다.

# 215. 압축 Core 지침

```text
MASTER ROADMAP / MILESTONE CORE

1. Every non-trivial project task should be traceable upward to a feature, milestone, phase, and project goal where those layers exist.
2. Maintain a stable project goal and use phases and milestones to describe meaningful outcomes, not files or implementation steps.
3. Always know the current project position: current phase, current milestone, current task, and immediate next milestone.
4. Define success or exit criteria for meaningful milestones; implementation alone does not make a milestone DONE.
5. Use explicit states such as TODO, READY, ACTIVE, BLOCKED, DONE, DEFERRED, and CANCELLED.
6. Do not mark a milestone DONE until its required verification is complete.
7. Record important dependencies between milestones and avoid deep implementation of blocked downstream work unless intentionally prototyping.
8. Keep future roadmap detail proportional to certainty: current work detailed, next work moderately detailed, distant work high-level.
9. Do not add every discovered idea to the active roadmap; unrelated improvements belong in a Parking Lot until justified and prioritized.
10. At the start of important work, answer: Where are we? Why does this task exist? Which milestone does it advance? What comes next?
11. If a task does not directly or necessarily support the active milestone, treat it as possible execution drift.
12. Roadmap changes are allowed when user priorities or verified constraints change, but material changes must have a reason.
13. The roadmap is a navigation and planning source, not a replacement for source code, tests, or runtime truth.
14. Preserve current project position in checkpoints and handoffs so new agents do not restart broad discovery.
15. Keep the always-loaded roadmap context small: project goal, current milestone, current task, immediate next step, and critical dependencies.
```

# 216. Final Principle

개발 Agent가 길을 잃는 가장 큰 이유 중 하나는 현재 Task만 보고 있기 때문이다.

따라서 항상:

```text
WHY ARE WE BUILDING THIS?

↓

WHERE ARE WE?

↓

WHAT ARE WE BUILDING NOW?

↓

WHAT MUST BE TRUE TO FINISH IT?

↓

WHAT IS NEXT?
```

에 답할 수 있어야 한다.

좋은 Roadmap은 미래를 완벽하게 예측하는 문서가 아니다.

> **현재 작업이 전체 프로젝트에서 어떤 의미를 가지는지 잃지 않게 하는 지도다.**

그리고 AI는 지도에 없는 길을 발견했다고 바로 그 길로 들어가지 않는다.

```text
발견
↓
필수인가?
├─ YES → 계획에 반영
└─ NO → Parking Lot
```

으로 처리한다.

최종 목표는:

> **어떤 Agent나 Session이 작업을 이어받아도 프로젝트 전체 목적, 현재 위치, 완료된 단계, 다음 단계부터 빠르게 이해할 수 있는 상태를 유지하는 것**

이다.
