# Execution Drift & Scope Sentinel Policy v1

## 작업 이탈·범위 확장·사이드퀘스트 탐지 및 차단 지침

Version: 1.0

---

# 0. 목적

이 Policy는 AI Agent가 작업 도중 원래 목표와 무관하거나 필요 이상으로 넓은 작업에 빠지는 현상을 방지한다.

대표적인 문제:

```text
작은 Bug Fix가 대규모 Refactor로 변함

한 Component 수정이 전체 Design System 변경으로 확장

현재 Feature 수정 중 unrelated bug까지 같이 수정

새로운 Library 도입

Architecture 전체 교체

요청하지 않은 기능 추가

"코드를 보다 보니" 시작된 Side Quest

작업 중 발견한 개선점을 바로 구현

Plan 없이 Scope가 점점 확대
```

핵심 흐름:

```text
LOCKED GOAL
+
ACTIVE PLAN
+
CHANGE CONTRACT
+
CURRENT MILESTONE

↓

ACTUAL ACTIVITY

↓

ALIGNMENT CHECK

↓

DIRECT?
SUPPORTING?
REPLAN REQUIRED?
UNRELATED?

↓

CONTINUE
or
CONTROLLED EXPANSION
or
PARKING LOT
or
STOP
```

최종 목표:

> AI가 새로운 문제를 발견하지 못하게 하는 것이 아니라, 발견한 문제와 현재 해결해야 할 문제를 구분하게 만든다.

---

# 1. 최상위 원칙

모든 중요한 행동은 다음 질문을 통과해야 한다.

```text
이 작업이 현재 Goal을 달성하는 데 직접 필요한가?
```

YES:

```text
계속 진행
```

NO:

다음 질문.

```text
현재 Goal을 완료하기 위해 반드시 필요한 지원 작업인가?
```

YES:

```text
SUPPORTING TASK
```

NO:

다음 질문.

```text
새로운 사실 때문에 현재 Plan 자체를 변경해야 하는가?
```

YES:

```text
REPLAN
```

NO:

```text
PARKING LOT / STOP
```

---

# 2. Drift의 정의

`Execution Drift`란 실제 행동이 원래 작업의:

```text
Goal

Success Criteria

Scope

Active Plan

Current Milestone
```

에서 근거 없이 벗어나는 상태다.

---

# 3. Drift와 Plan Change는 다르다

Drift:

```text
하면 좋을 것 같아서

코드가 마음에 안 들어서

최신 방식이 더 좋아 보여서

관련 파일이라 같이 정리하려고
```

정당한 Plan Change:

```text
현재 Success Criteria를 기존 Plan으로 달성할 수 없음

새로운 Dependency가 실제로 발견됨

Security issue 발견

필수 API 데이터가 없음

기존 설계 가정이 틀림
```

---

# 4. Sentinel 기준선

Drift Sentinel은 다음 정보를 기준으로 판단한다.

```text
1. Latest Locked Spec

2. User Intent Contract

3. Active Work Plan

4. Change Contract

5. Current Roadmap Milestone

6. Do Not Change

7. Must Preserve
```

---

# 5. 기준선이 없는 경우

비단순 Task인데:

```text
Goal 없음

Plan 없음

Scope 없음
```

이면 Drift 판단 자체가 어렵다.

따라서 먼저 최소 Active Plan을 만든다.

---

# 6. Alignment Classification

실제 작업을 다음 네 종류로 분류한다.

```text
DIRECT

SUPPORTING

REPLAN_REQUIRED

UNRELATED
```

---

# 7. DIRECT

현재 Success Criteria를 직접 구현하는 작업.

예:

Goal:

```text
야간 근무자 없음 → 공석 표시
```

DIRECT:

```text
TodayShiftCard 조건 분기 수정

관련 Test 작성
```

---

# 8. SUPPORTING

Success Criteria를 직접 만들지는 않지만 현재 작업 완료에 반드시 필요한 작업.

예:

```text
현재 Target 파일의 Type Error 수정

필수 Build 설정 오류 해결

현재 Feature Test 실행에 필요한 fixture 수정
```

---

# 9. REPLAN_REQUIRED

현재 Plan으로 목표 달성이 불가능하거나 위험하다는 사실이 확인된 경우.

예:

```text
Frontend-only 계획

↓

API에 필요한 데이터 없음

↓

Backend extension 필요
```

이는 Drift가 아니라 Replanning 대상이다.

---

# 10. UNRELATED

현재 Goal 달성에 필요하지 않은 작업.

예:

```text
공석 표시 작업 중

Login 화면 CSS 개선
```

또는:

```text
ShiftService 중복 제거
```

가 현재 요구와 무관하다면 UNRELATED다.

---

# 11. Default Action

```text
DIRECT
→ CONTINUE

SUPPORTING
→ CONTROLLED INCLUDE

REPLAN_REQUIRED
→ PAUSE + REPLAN

UNRELATED
→ PARKING LOT / STOP
```

---

# 12. Side Quest

작업 중 발견한 새로운 문제를 `Side Quest`라고 부를 수 있다.

예:

```text
현재:
Calendar bug fix

발견:
Old API helper 구조가 지저분함
```

---

# 13. Side Quest 판단

```text
SIDE QUEST FOUND

↓

Blocking current goal?

YES
→ Supporting Task

NO
↓

Required for success criteria?

YES
→ Scope evaluation

NO
↓

Parking Lot
```

---

# 14. Side Quest를 바로 해결하지 않는다

AI에게 흔한 패턴:

```text
"어차피 파일을 열었으니 같이 고치자."
```

금지한다.

---

# 15. "While I'm Here" 금지

다음 생각은 Drift Trigger다.

```text
while I'm here

since we're touching this file

might as well

good opportunity to refactor

clean this up too
```

---

# 16. 파일을 이미 열었다는 것은 수정 근거가 아니다

다음은 변경 이유가 아니다.

```text
파일을 이미 읽음

근처 코드 발견

쉽게 고칠 수 있음

보기 싫음
```

---

# 17. Every Change Needs a Reason

모든 변경 파일은 다음 중 하나에 연결되어야 한다.

```text
USER_REQUIREMENT

SUCCESS_CRITERION

ROOT_CAUSE

REQUIRED_SUPPORTING_CHANGE

VERIFICATION_REQUIREMENT

SECURITY_REQUIREMENT

APPROVED_REPLAN
```

---

# 18. Orphan Change

어떤 근거에도 연결되지 않는 Diff:

```text
ORPHAN CHANGE
```

로 분류한다.

기본적으로 제거 대상이다.

---

# 19. Drift Detection — File Count

예상:

```text
Expected:
2~3 files
```

실제:

```text
9 files
```

이면 Drift Sentinel을 실행한다.

---

# 20. 파일 수 초과가 자동 실패는 아니다

실제 Dependency가 더 많을 수 있다.

중요한 것은:

```text
왜 늘어났는가?
```

이다.

---

# 21. Scope Expansion Gate

Actual Scope가 Expected Scope를 의미 있게 초과하면:

```text
STOP EDITING

↓

REVIEW WHY

↓

RECLASSIFY
```

한다.

---

# 22. Scope Expansion 질문

```text
1. 추가 파일이 Goal 달성에 필수인가?

2. 직접 Dependency인가?

3. 기존 Plan에서 놓친 실제 영향인가?

4. 단순 Cleanup인가?

5. 별도 Task로 분리 가능한가?
```

---

# 23. Legitimate Expansion

예:

```text
예상:
Component + test

실제:
Shared Hook 수정도 필수
```

Root Cause가 Shared Hook에 있다면 정당할 수 있다.

이 경우 Active Plan/Change Contract를 갱신한다.

---

# 24. Illegitimate Expansion

예:

```text
Shared Hook이 조금 복잡해 보여서
전체를 Refactor
```

현재 Goal에 필요 없다면 Drift.

---

# 25. Layer Drift

Expected:

```text
Frontend only
```

Actual:

```text
Frontend
Backend
Database
```

강한 Sentinel Trigger다.

---

# 26. Boundary Crossing

다음 Boundary를 넘으면 자동 재평가한다.

```text
UI → API

API → DB

Local → Shared

Internal → External Contract

Application → Infrastructure

Normal → Security

Single Feature → Cross Feature
```

---

# 27. Boundary Crossing은 금지가 아니다

정말 필요할 수 있다.

하지만:

```text
silent crossing
```

을 금지한다.

---

# 28. New Dependency Trigger

작업 중:

```text
npm install ...
```

이 필요해졌다면 Drift/Scope 재평가.

기존 Goal에 정말 필요한지 확인한다.

---

# 29. Dependency Convenience

다음 이유만으로 Package를 추가하지 않는다.

```text
구현이 쉬워짐

코드가 짧아짐

요즘 많이 사용함
```

기존 도구로 충분하면 현재 Task에서는 추가하지 않는 것이 기본이다.

---

# 30. Refactor Trigger

Task 중:

```text
"이 구조를 먼저 정리해야겠다."
```

라는 판단이 생기면 확인한다.

---

# 31. Required Refactor

현재 Bug/Feature를 안전하게 구현하는 데 구조 변경이 필수라면 허용 가능.

예:

```text
현재 코드가 한 함수에 500줄이기 때문에
Target logic을 안전하게 분리할 방법이 없음
```

그러나 실제로 필수인지 증거가 있어야 한다.

---

# 32. Optional Refactor

단지:

```text
더 깔끔

더 현대적

더 아름다운 구조
```

이면 현재 Scope 밖으로 보내는 것이 기본이다.

---

# 33. Refactor Budget

현재 Task에 필요한 최소 Refactor만 허용한다.

---

# 34. Design Drift

사용자:

```text
Card만 수정
```

Actual:

```text
Sidebar
Header
Navigation
Palette
```

까지 변경하면 Drift.

---

# 35. Visual Scope Sentinel

Reference/Design 작업에서는:

```text
ALLOWED REGION

PROTECTED REGION
```

을 명확히 한다.

---

# 36. Protected Region 변경

명시적 근거 없이 Protected 영역이 변경되면 FAIL 후보.

---

# 37. Behavior Drift

사용자가 UI 표현만 요청했는데 Behavior까지 변경되는 경우.

예:

```text
Label 변경

↓

API 요청 주기까지 변경
```

Drift 가능성이 높다.

---

# 38. Business Logic Drift

기술 구현 과정에서 비즈니스 정책을 임의 변경하지 않는다.

---

# 39. Test Drift

테스트를 통과시키려고 기대값을 새 구현에 맞게 임의 수정하지 않는다.

---

# 40. Example

Expected:

```text
Error → Error UI
```

새 코드가:

```text
Error → Empty UI
```

테스트가 실패.

다음은 금지:

```text
Test expectation을 Empty UI로 변경
```

요구가 바뀐 게 아니라면 구현을 수정한다.

---

# 41. Verification Drift

현재 Task를 검증하는 과정에서 전체 프로젝트 문제 해결로 확대하지 않는다.

---

# 42. Build Failure 발견

Build 중 기존 Failure가 발견되면:

```text
Introduced by current change?

YES
→ fix

NO
↓
Blocks required verification?

YES
→ supporting task or BLOCKED

NO
→ baseline failure 기록
```

---

# 43. Existing Failure는 자동 Scope가 아니다

기존 문제를 발견했다고 모두 수정하지 않는다.

---

# 44. Baseline Failure

예:

```text
현재 Task와 무관한 기존 test 2개 실패
```

기록:

```text
BASELINE FAILURE
```

현재 변경이 만든 문제로 착각하지 않는다.

---

# 45. Baseline Repair

현재 Task 완료에 필수적이지 않으면 Parking Lot 후보.

---

# 46. Discovery Drift

코드 탐색도 옆길로 샐 수 있다.

예:

```text
Target Feature 검색

↓

Repository 전체 Architecture 분석
```

필요하지 않으면 중단한다.

---

# 47. Investigation Objective

탐색 시작 전 질문을 명확히 한다.

예:

```text
Find:
TodayShiftCard primary implementation,
data source,
affected tests.
```

---

# 48. Investigation Stop Rule

필요한 Evidence를 찾으면 탐색을 멈춘다.

---

# 49. "혹시 더 있을지" 무한 검색 금지

Impact Analysis가 충분한 Confidence를 제공했다면 끝낸다.

---

# 50. Research Drift

외부 문서 조사에서도:

```text
현재 Dependency API 확인
```

을 하다가:

```text
관련 Framework 전체 최신 동향 조사
```

로 가지 않는다.

---

# 51. Scope Sentinel Checkpoints

다음 시점에 Drift Check 가치가 높다.

```text
Target 파일 수 증가

새 Layer 진입

새 Package 필요

Shared Code 변경

API/DB 변경 필요

Architecture 변경 제안

현재 Step 완료

Verification 전

Final Diff 전
```

---

# 52. 매 줄마다 Drift Check하지 않는다

과도한 검사로 작업 속도를 떨어뜨리지 않는다.

의미 있는 경계에서만 수행한다.

# 55. Goal Trace

예:

```text

Error branch test

SC-003
```

---

# 56. Goal Trace가 없으면

무조건 잘못은 아니지만 Drift 가능성을 검사한다.

---

# 57. Scope Expansion Record

정당한 확장:

```text
SCOPE EXPANSION

2 files / frontend

4 files / frontend + shared hook

Root cause located in shared hook

Required:
YES

Risk:
MEDIUM → HIGH
```

# 58. Scope Expansion 후

다음 업데이트:


# 59. Scope Expansion 승인

낮은 위험이고 사용자 결과가 같다면 AI가 내부적으로 승인 가능할 수 있다.

하지만 큰 사용자-visible/DB/API/비용/보안 변화는 User Authority Policy를 따른다.

# 60. Parking Lot의 역할

Parking Lot은:

> 지금 하지 않을 일을 안전하게 기억하는 곳

이다.

---

# 61. Parking Lot이 없으면 생기는 문제

AI:

```text
이 문제를 지금 안 고치면 잊을 것 같다.
```

↓

현재 Task에 포함

↓

Scope Drift

````

Parking Lot이 이를 줄인다.

---

# 62. Parking Lot 파일

권장:

```text
.ai/project/parking-lot.md
````

---

# 63. Parking Lot Entry

```text
PL-014

Title:
ShiftService duplication cleanup

Found During:
M2.2 Calendar Generation

Reason:
Repeated business logic

Current Task Required:
NO

Potential Value:
MEDIUM

Risk:
MEDIUM

Suggested Later:
Hardening phase
```

---

# 64. Parking Lot은 간단해야 한다

전체 해결방안을 설계하지 않는다.

발견 내용을 보존할 만큼만 작성한다.

---

# 65. Parking Lot Priority

필요하면:

```text
LOW

MEDIUM

HIGH
```

정도만 둘 수 있다.

---

# 66. Parking Lot은 자동 Roadmap 승격 금지

사용자/Project Priority Review가 필요하다.

---

# 67. Parking Lot 중복 제거

같은 문제를 반복 발견하면 기존 Entry에 Occurrence를 추가할 수 있다.

---

# 68. Parking Lot → Lesson 차이

Parking Lot:

```text
나중에 할 수 있는 작업
```

Lesson:

```text
과거 실패에서 배운 규칙
```

다르다.

---

# 69. Parking Lot → ADR 차이

Parking Lot:

```text
미해결 아이디어
```

ADR:

```text
이미 내려진 중요한 결정
```

---

# 70. Parking Lot → Roadmap

검토 후 실제로 해야 할 일로 확정되면 Roadmap Milestone/Task로 승격.

---

# 71. Follow-up Suggestion

현재 Task 완료 후 사용자에게 필요하면:

```text
이번 범위에는 포함하지 않았지만,
ShiftService에 중복 로직이 있어 별도 리팩터링 후보로 기록했습니다.
```

처럼 짧게 알릴 수 있다.

---

# 72. Parking Lot을 사용자에게 모두 보여줄 필요 없음

가치가 높은 것만 제안한다.

---

# 73. Drift Severity

Drift를 다음처럼 분류할 수 있다.

```text
D1 — MINOR

D2 — MODERATE

D3 — MAJOR

D4 — CRITICAL
```

---

# 74. D1

예:

```text
작은 formatting noise

불필요 comment 변경
```

Final Diff에서 제거.

---

# 75. D2

예:

```text
관련 있지만 필요 없는 helper cleanup

추가 test refactor
```

Parking Lot/되돌림.

---

# 76. D3

예:

```text
새 Layer 진입

Shared architecture refactor

추가 Dependency
```

Replan 필요.

---

# 77. D4

예:

```text
DB 변경 금지인데 Schema 변경

Permission 확대

Production destructive change

사용자 금지 영역 변경
```

즉시 중단 및 Intent/Change Contract 재검토.

---

# 78. Drift Trigger Score

고정 계산식은 필요 없지만 다음 신호가 많을수록 Drift 가능성이 높다.

```text
Expected file count 초과

새 Layer

새 Dependency

새 Feature

새 public API

새 DB field

새 shared abstraction

새 user-visible behavior

Do Not Change 영역 수정
```

# 215. 압축 Core 지침

```text
EXECUTION DRIFT / SCOPE SENTINEL CORE

1. Continuously anchor meaningful work to the latest locked goal, success criteria, active plan, change contract, and current milestone.
2. Classify unexpected work as DIRECT, SUPPORTING, REPLAN_REQUIRED, or UNRELATED.
3. Continue DIRECT work, narrowly include required SUPPORTING work, formally replan when verified evidence invalidates the current plan, and park or stop UNRELATED work.
4. Never use "while I'm here", cleanup convenience, aesthetics, novelty, or future hypothetical usefulness as sufficient justification for scope expansion.
5. Every changed file or meaningful change must trace to a user requirement, success criterion, root cause, required supporting change, verification requirement, security requirement, or approved replan.
6. Treat entry into a new layer, shared code, API, DB, dependency, security boundary, or infrastructure as a scope sentinel trigger.
7. Compare expected scope with actual scope whenever file count, layers, or concepts expand materially.
8. Do not silently cross a boundary; if crossing is required, update the active plan, change contract, risk, policies, and verification scope.
9. Keep unrelated discoveries in a Parking Lot rather than solving them immediately.
10. A useful idea is not automatically part of the current task.
11. Existing unrelated bugs are not automatically current scope; distinguish introduced failures, blocking baseline failures, and non-blocking baseline failures.
12. Do not refactor shared architecture, rename unrelated symbols, clean dead code, update dependencies, or reformat unrelated areas unless directly justified.
13. Do not modify tests merely to make unintended behavior pass.
14. Stop investigation when enough evidence exists for the current decision; do not broaden exploration without a decision need.
15. At final diff review, require a concrete reason for every changed file and remove orphan changes and debug noise.
16. Once success criteria and required verification pass, stop; optional improvement becomes follow-up work.
17. Critical unrelated safety/security findings may become explicit interrupt tasks, but must not be silently mixed into the current task.
18. Treat repeated scope drift as a Harness learning signal and promote suitable prevention into rules, gates, or validators.
```

# 216. Final Principle

좋은 Agent는 문제를 많이 발견하는 Agent만이 아니다.

좋은 Agent는:

```text
발견한 문제
```

와:

```text
지금 해결해야 하는 문제
```

를 구분할 수 있어야 한다.

따라서 기본 행동은:

```text
DISCOVER SOMETHING

↓

IS IT REQUIRED NOW?

├─ YES
│   ↓
│ DIRECT / SUPPORTING / REPLAN
│
└─ NO
    ↓
  PARK IT
    ↓
RETURN TO CURRENT GOAL
```

이다.

최종적으로 AI는 언제든 다음에 답할 수 있어야 한다.

```text
지금 하는 일이 원래 목표에 왜 필요한가?

현재 Scope 안에 있는가?

계획에 없었다면 왜 추가됐는가?

지금 하지 않아도 되는가?

별도 작업으로 분리할 수 있는가?
```

답하지 못한다면 그 작업은 진행하기 전에 멈춰야 한다.

이 Policy의 최종 목표는:

> **AI가 딴길을 전혀 발견하지 않는 시스템이 아니라, 딴길을 발견해도 현재 목적지를 잃지 않는 시스템을 만드는 것**

이다.
