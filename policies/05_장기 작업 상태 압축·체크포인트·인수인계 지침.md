# Context Checkpoint & Handoff Policy v1

## 장기 작업 컨텍스트 압축·상태 보존·에이전트 인수인계 지침

Version: 1.0

---

# 0. 목적

이 Policy는 장시간 또는 다단계 AI 작업에서 Context가 계속 누적되어 다음 문제가 발생하는 것을 방지한다.

```text
Context 비대화

중복 정보 누적

과거 가설과 현재 사실 혼재

Tool Output 반복

Subagent 결과 누적

목표 Drift

중요 의사결정 망각

새 Agent가 Repository를 다시 탐색

Token 사용량 증가
```

핵심 목표:

> 현재 작업을 계속 수행하는 데 필요한 최소 상태만 보존하고, 이미 해결된 탐색 과정과 불필요한 원문 Context는 버린다.

---

# 1. Checkpoint와 Handoff를 구분한다

두 개념은 비슷하지만 목적이 다르다.

## CHECKPOINT

같은 작업을 계속하기 위한 압축 상태.

```text
현재 Agent
↓
Context 압축
↓
현재 Agent 또는 동일 작업 계속
```

목적:

```text
Token 절약

Context 정리

목표 유지

중간 복구
```

---

## HANDOFF

다른 Agent 또는 다음 Session이 작업을 이어받기 위한 전달 상태.

```text
Agent A
↓
HANDOFF
↓
Agent B
```

목적:

```text
재탐색 방지

의사결정 전달

미완료 작업 전달

위험 요소 전달

검증 상태 전달
```

---

# 2. 핵심 원칙

> Context는 작업 기록 저장소가 아니다.

> 모든 Tool Output을 계속 유지하지 않는다.

> 이미 확인된 사실은 Raw Evidence가 아니라 압축된 Confirmed Fact로 유지한다.

> 가설과 검증된 사실을 구분한다.

> 완료된 조사 과정은 결과만 남긴다.

> 다음 작업 단계의 결정을 바꾸지 않는 정보는 제거할 수 있다.

---

# 3. Context 구조

Working Context는 가능하면 다음 네 계층으로 구분한다.

```text
USER INTENT

↓

WORKING STATE

↓

ACTIVE EVIDENCE

↓

TEMPORARY CONTEXT
```

---

# 4. USER INTENT

절대 잃어버리면 안 되는 정보다.

포함:

```text
사용자 원래 요청

Success Criteria

사용자가 명시한 제약

금지사항

우선순위
```

Checkpoint 과정에서도 유지한다.

---

# 5. WORKING STATE

현재 작업의 핵심 상태다.

포함:

```text
Current Feature

Current Phase

Current Goal

Risk

Target Files

Decisions

Changed Files

Tests

Open Issues

Next Actions
```

이 영역이 Checkpoint의 중심이다.

---

# 6. ACTIVE EVIDENCE

아직 현재 판단에 직접 필요한 근거.

예:

```text
현재 수정 중인 함수

관련 API Contract

현재 실패 중인 Test

Migration diff

현재 비교 중인 두 Architecture 후보
```

작업 단계가 지나가면 압축 또는 제거할 수 있다.

---

# 7. TEMPORARY CONTEXT

가장 먼저 제거할 수 있는 정보.

예:

```text
중복 Search 결과

실패한 grep 결과

이미 폐기된 가설

Raw Build Log

전체 Test Log

반복된 Tool Output

Subagent 원문 응답
```

결과만 남기고 제거한다.

---

# 8. Checkpoint 활성화 조건

다음 중 하나 이상이면 Checkpoint 생성을 고려한다.

```text
작업 단계가 크게 변경됨

Feature 탐색 완료

Root Cause 발견

구현 계획 확정

대규모 코드 수정 완료

DB Migration 완료

Subagent 결과가 여러 개 누적

Tool Output이 많이 누적

Context가 복잡해짐

이전 정보 검색 비용이 증가

다른 Agent에게 넘길 가능성이 있음

다음 Session까지 이어질 가능성이 있음
```

---

# 9. Token Threshold를 하드코딩하지 않는다

Checkpoint를 특정 Token 숫자에만 의존하지 않는다.

모델 Context Window는 계속 변할 수 있기 때문이다.

대신 다음 신호를 사용한다.

```text
Context Pressure

Information Duplication

Task Phase Transition

Agent Transition

Long Tool History

Reasoning Drift
```

---

# 10. Context Pressure 감지

다음 상태는 Checkpoint 신호다.

```text
같은 사실을 다시 찾음

이미 확인한 파일을 다시 읽음

과거 결정 이유를 다시 추론함

현재 Goal보다 과거 Tool Output이 많음

Agent가 현재 작업 위치를 잃음

Subagent 결과를 다시 요약해야 함
```

---

# 11. Checkpoint 생성 시점

좋은 Checkpoint 시점:

```text
Discovery 완료
→ Checkpoint

Implementation 시작

Implementation 완료
→ Checkpoint

Verification 시작

Verification 완료
→ Final/Handoff
```

매 작은 작업마다 Checkpoint를 만들 필요는 없다.

# 13. 실제 예시

```text
CHECKPOINT

Task:
대시보드 야간 근무 공석 표시

Feature:
dashboard.todayShift

Current Phase:
IMPLEMENTATION COMPLETE

Goal:
야간 근무자가 없으면 "공석" 표시

Success Criteria:
- 야간 근무자 없음 → 공석
- 근무자 있음 → 기존 이름 표시
- 주간 근무 영향 없음

Confirmed Facts:
- UI는 TodayShiftCard가 담당
- API는 GET /api/shifts/today
- API 변경 불필요
- DB 변경 불필요

Decisions:
- UI 레이어에서 empty state 처리
- Backend는 변경하지 않음

Target Files:
- TodayShiftCard.tsx
- TodayShiftCard.test.tsx

Changed Files:
- TodayShiftCard.tsx

Tests:
- 관련 Unit Test 추가 예정

Verification:
- Implementation 완료
- Test 미실행

Open Issues:
- Empty state test 필요

Risk:
LOW

Do Not Change:
- API
- DB
- 주간 근무 표시

Next Step:
관련 Unit Test 작성 및 실행

Active Policies:
- Change Control
- Verification 예정
```

이 정보만으로 다음 작업을 계속할 수 있어야 한다.

---

# 14. Confirmed Facts

Checkpoint에는 사실과 추측을 분리한다.

좋은 예:

```text
CONFIRMED:
TodayShiftCard가 /api/shifts/today 데이터를 사용한다.
```

나쁜 예:

```text
아마 ShiftService가 문제일 것이다.
```

---

# 15. Assumption 별도 관리

확인되지 않은 내용은 다음처럼 표시한다.

```text
ASSUMPTION

INFERRED

UNVERIFIED

UNKNOWN
```

예:

```text
UNVERIFIED:
외부 Consumer가 해당 API를 사용하지 않는 것으로 추정됨.
```

검증되지 않은 내용을 Confirmed Fact에 넣지 않는다.

---

# 16. Decision 기록

중요한 결정은 결과뿐 아니라 이유를 짧게 남긴다.

예:

```text
Decision:
API는 변경하지 않는다.

Reason:
기존 Response에 필요한 정보가 이미 포함되어 있고
UI에서 Empty State 처리가 가능함.
```

다음 Agent가 같은 논쟁을 반복하지 않게 한다.

---

# 17. Decision 기록이 필요한 경우

모든 사소한 코딩 선택을 기록하지 않는다.

기록 가치가 높은 것:

```text
Architecture 선택

API Contract 유지/변경

DB Schema 결정

Library 선택

Security 전략

Shared Code 변경 여부

중요한 Trade-off
```

---

# 18. Rejected Alternatives

중요한 대안이 이미 검토되어 폐기되었다면 짧게 기록한다.

예:

```text
Rejected:
DB에 "vacant" 상태 저장

Reason:
공석은 데이터 부재에서 계산 가능한 UI 상태라
Schema 변경이 불필요함.
```

이를 통해 다른 Agent가 같은 대안을 다시 조사하지 않는다.

---

# 19. Raw Tool Output 압축

다음처럼 저장하지 않는다.

```text
npm test 전체 로그 400줄
```

대신:

```text
Test:
TodayShiftCard.test.tsx

Result:
PASS

6 tests passed
```

실패 시:

```text
Result:
FAIL

Relevant failure:
expected "공석", received "-"
```

만 유지한다.

---

# 20. Build Log 압축

Raw:

```text
수백 줄 Build Output
```

대신:

```text
Build:
PASS
```

또는:

```text
Build:
FAIL

Blocking error:
src/... line ...
Type X is not assignable to Y
```

만 유지한다.

---

# 21. Search 결과 압축

Raw:

```text
검색 결과 파일 50개
```

대신:

```text
Relevant Results:

Primary:
TodayShiftCard.tsx

Consumer:
Dashboard.tsx

Test:
TodayShiftCard.test.tsx
```

만 남긴다.

---

# 22. Subagent Result 압축

Subagent 원문 전체를 Parent Context에 유지하지 않는다.

다음 형태로 압축한다.

```text
SCOUT RESULT

Status:
VERIFIED

Findings:
- TodayShiftCard = Primary UI
- useTodayShift = Data hook
- API change unnecessary

Evidence:
- TodayShiftCard.tsx#TodayShiftCard
- useTodayShift.ts#useTodayShift

Uncertainty:
None
```

---

# 23. Multiple Subagent 병합

세 Agent가 조사했다면 결과를 따로 장기 유지하지 않는다.

```text
Scout A raw
Scout B raw
Scout C raw
```

↓

```text
AGGREGATED FINDINGS
```

로 합친다.

---

# 24. 충돌은 제거하지 않는다

Subagent 결과가 충돌할 경우 압축 과정에서 숨기지 않는다.

예:

```text
CONFLICT

Agent A:
API 변경 필요

Agent B:
API 변경 불필요

Status:
UNRESOLVED
```

Source of Truth 확인 후 해결한다.

---

# 25. Resolved Conflict

해결 후:

```text
RESOLVED

Decision:
API 변경 불필요

Evidence:
Response에 nightWorker nullable field 존재
```

만 유지할 수 있다.

---

# 26. Context Compaction 대상

우선 제거:

```text
중복 정보

오래된 가설

폐기된 구현 계획

이미 처리된 TODO

Raw Tool Output

완료된 Subagent 대화

중복 Documentation 설명
```

---

# 27. 절대 제거하면 안 되는 정보

다음은 작업 완료까지 유지한다.

```text
사용자 원래 요구

Success Criteria

중요 제약

보안 제약

현재 Feature

중요 Architecture Decision

변경 파일

미검증 항목

현재 Failure

Next Step
```

---

# 28. Goal Drift 방지

Checkpoint를 생성할 때 반드시 원래 Goal과 현재 작업을 비교한다.

질문:

```text
현재 작업이 여전히 사용자 원래 요청을 향하고 있는가?
```

NO라면 Scope Drift를 의심한다.

---

# 29. Success Criteria 재확인

Checkpoint마다 가능하면 다음을 확인한다.

```text
완료됨

부분 완료

미완료
```

예:

```text
Success Criteria:

[x] 야간 없음 → 공석

[x] 야간 있음 → 이름

[ ] 관련 Test 통과

[x] API 변경 없음
```

# 35. Checkpoint와 Repository 문서 구분

Checkpoint는 임시 상태다.

다음과 혼동하지 않는다.

```text
ARCHITECTURE.md

Feature Documentation

ADR

Code Map
```

영구적 지식은 해당 문서로 승격한다.

---

# 36. Knowledge Promotion

작업 중 발견한 정보 중 장기 가치가 있는 것은 Checkpoint에만 두지 않는다.

예:

```text
"모든 Shift API는 apiClient를 사용해야 한다."
```

같은 규칙이 장기 Convention이면:

```text
Convention Map
```

으로 이동시킨다.

---

# 37. Architecture Decision 승격

중요한 Architecture 결정은:

```text
Checkpoint
```

에서 끝내지 않고 필요하면:

```text
ADR
```

로 승격한다.

---

# 38. Feature Map 승격

새 Feature 관계를 발견하면:

```text
Checkpoint만 기록
```

하지 않고:

```text
Feature Map Update
```

를 수행한다.

# 39. Handoff 활성화 조건

다음 상황에서 Handoff를 생성한다.

```text
다른 Agent가 이어받음

다른 모델로 전환

Session 종료

사용자가 나중에 계속할 예정

현재 Agent가 Context 한계에 접근

작업이 다른 전문 Agent로 넘어감
```

---

# 40. Handoff 목적

새 Agent가 다음을 하지 않도록 한다.

```text
Repository 전체 재탐색

이미 결정된 Architecture 재논의

같은 Bug Root Cause 재조사

같은 테스트 재발견

사용자 요구 다시 해석
```

# 42. Handoff 예시

```text
HANDOFF

Task:
근무 패턴 엔진 수정

Original Request:
A/B/C/D 조 패턴 계산 정확도 개선

Feature:
shift.schedule.pattern

Current Phase:
VERIFYING

Completed:
- 기존 Pattern parser 분석
- offset 계산 로직 수정
- 주간 패턴 테스트 통과

Changed Files:
- src/shift/pattern-engine.ts
- tests/shift/pattern-engine.test.ts

Important Decisions:
- 기존 DB Schema 유지
- 패턴 문자열 저장 형식 유지
- 계산 엔진만 변경

Rejected Alternatives:
- Shift 테이블에 일별 결과 저장
  Reason: 중복 데이터 발생

Verification:
- Unit Test: PASS
- Build: PASS
- 대체근무 Test: PENDING

Open Issues:
- 대체근무 케이스 2개 미검증

Known Risks:
- replacement allowance 계산에 영향 가능

Do Not Change:
- pattern DB format
- API response schema

Relevant Symbols:
- pattern-engine.ts#calculateShift
- replacement.ts#calculateReplacement

Active Policies:
- Codebase OS
- Change Control
- Verification

Recommended Next Action:
대체근무 Test를 실행하고 Impact 확인
```

---

# 43. Handoff는 결과만 전달한다

다른 Agent에게 다음을 넘기지 않는 것을 기본으로 한다.

```text
전체 Conversation

전체 Tool History

전체 Search Result

폐기된 가설의 세부 과정
```

필요하면 Evidence Pointer로 원문에 접근하게 한다.

---

# 44. Evidence Pointer

Handoff에 다음을 사용할 수 있다.

```text
file + symbol

test + test name

feature ID

API path

ADR ID

commit/hash

checkpoint ID
```

---

# 45. Handoff Trust Model

새 Agent는 Handoff 내용을 참고하되 실제 코드보다 우선하지 않는다.

Source of Truth:

```text
Actual Code

>

Verified Test/Runtime

>

Handoff
```

Handoff와 코드가 충돌하면 코드를 확인한다.

---

# 46. Handoff Freshness

Handoff에는 가능하면 다음 Metadata를 둔다.

```text
Generated At

Git Commit

Working Tree State
```

예:

```text
Base Commit:
abc123

Uncommitted Changes:
YES
```

---

# 47. Stale Handoff

현재 Repository가 Handoff 이후 크게 변경되었다면 모든 내용을 그대로 신뢰하지 않는다.

먼저:

```text
git diff

Code Map freshness

Relevant Files
```

를 확인한다.

---

# 48. Model Transition

고성능 Agent → 저비용 Agent로 넘길 때 특히 Decision을 명확히 전달한다.

예:

```text
Architecture is already decided.

Do not redesign.

Your task is mechanical implementation only.
```

이렇게 해야 저비용 Agent가 다시 설계 논의를 시작하지 않는다.

---

# 49. 저비용 Agent → 상위 Agent Handoff

반대로 Scout/Worker에서 Orchestrator로 전달할 때:

```text

Evidence

Uncertainty

Conflict
```

를 명확히 한다.

상위 Agent에게 Raw Exploration을 넘기지 않는다.


# 52. Checkpoint Versioning

동일 Task의 여러 Checkpoint가 있을 수 있다.

```text

```

항상 최신 상태를 기준으로 한다.

# 53. 이전 Checkpoint 보존

필요하면 저장할 수 있지만 Working Context에는 최신 Checkpoint만 유지한다.

과거 Checkpoint는 Historical Record로 취급한다.

---

# 54. Delta Checkpoint

매번 전체 내용을 다시 쓰지 않고 변경점만 기록할 수도 있다.

예:

```text
CP4 DELTA

Changed:
- Test passed
- Risk MEDIUM → LOW

Resolved:
- API compatibility concern

Next:

```

단 새 Agent에게 넘길 Handoff는 self-contained해야 한다.

# 55. Self-contained Handoff

Handoff는 이전 모든 Checkpoint를 읽지 않아도 이해 가능해야 한다.

즉:

```text
Handoff = standalone summary
```

여야 한다.

---

# 56. Token 효율 원칙

Checkpoint의 목적은 최대한 짧게 쓰는 것이 아니다.

목적은:

> 다음 결정을 내리는 데 필요한 최소 충분 정보

를 유지하는 것이다.

너무 짧아 다시 탐색해야 하면 오히려 Token 낭비다.

---

# 57. Compression 품질 기준

좋은 Checkpoint:

```text
짧음
+
정확함
+
현재 상태 명확
+
다음 행동 명확
```

나쁜 Checkpoint:

```text
짧지만
무슨 작업인지 알 수 없음
```

또는:

```text
모든 대화 내용을 그대로 복사
```

---

# 58. Information Value

Checkpoint에 항목을 넣기 전에 질문한다.

```text
이 정보가 다음 Agent의 판단을 바꿀 가능성이 있는가?
```

NO:

```text
제거
```

YES:

```text
유지
```

---

# 59. Finished Information

완료된 탐색은 다음처럼 바꾼다.

Before:

```text
파일 A 확인
파일 B 확인
파일 C 확인
파일 D 확인...
```

After:

```text
Confirmed implementation path:
A → C → D
```

---

# 60. Failure History

실패한 모든 시도를 기록하지 않는다.

그러나 다시 반복할 가능성이 높은 중요한 실패는 유지한다.

예:

```text
Do not retry:
API-side fix

Reason:
Backend already returns required nullable state.
```

---

# 61. Repetition Prevention

Checkpoint의 중요한 역할 중 하나는:

```text
같은 실패를 다시 하지 않게 하는 것
```

이다.

---

# 62. Open Questions

아직 해결되지 않은 질문을 명시한다.

예:

```text
OPEN:

Does replacement calculation share PatternEngine?
```

이렇게 하면 새 Agent가 무엇을 조사해야 할지 안다.

---

# 63. Unknown과 Blocker 구분

UNKNOWN:

```text
아직 조사하지 않음
```

BLOCKER:

```text
이 정보 없이는 다음 단계 진행 불가
```

구분한다.

---

# 64. Next Step은 구체적이어야 한다

나쁜 예:

```text
계속 진행
```

좋은 예:

```text
replacement-calculation.spec.ts를 실행하고
PatternEngine 변경으로 인한 회귀 여부 확인
```

---

# 65. Do Not Change

Handoff에는 가능하면 중요한 Protected Area를 기록한다.

예:

```text
Do Not Change:
API Response Schema
DB Pattern Format
Auth middleware
```

다음 Agent의 Scope Drift를 막는다.

---

# 66. Policy State 전달

다음 Agent가 어떤 지침을 적용해야 하는지 알려준다.

예:

```text

Verification

No longer needed:
Migration

Trigger if discovered:
Security
```

# 69. Multi-Agent Harness 연동

# 96. Too Many Checkpoints


# 97. Too Few Checkpoints

```text
대규모 수정
```

# 104. Completed Item Cleanup

# 105. Failed Hypothesis Cleanup


```text

```

를 Current State Source로 지정한다.

# 110. Concurrent Agents

각 Agent 결과는 Parent Orchestrator가 병합한다.

Subagent가 공용 `active-task.md`를 임의로 덮어쓰지 않는 것을 기본으로 한다.


# 113. Context Branch

```text

├─ Branch A
├─ Branch B
└─ Branch C
```

# 114. Branch Cleanup

병합 완료 후 Branch의 Raw Context는 장기 유지할 필요가 없다.

# 115. Handoff Verification

다른 Agent가 Handoff를 받으면 가장 먼저 모든 내용을 재검증하지 않는다.

다음만 Quick Check한다.

```text
Git State

Relevant Files 존재

Critical Decision still valid

Current Failure still reproducible if applicable
```

그 후 이어간다.

```text
무엇이 바뀌었나?

다음에 정확히 무엇을 해야 하나?
```

# 120. 실패 조건

다음은 Policy 실패다.

```text
전체 Tool Output 계속 누적

새 Agent가 처음부터 다시 탐색

과거 가설을 사실로 전달

미검증 상태 누락
```

# 123. Token Efficiency 핵심

Token 절약은 단순히 짧게 답하는 것이 아니다.

진짜 Token 절약은:

```text
이미 해결한 문제를 다시 풀지 않는 것

+

이미 읽은 Repository를 다시 읽지 않는 것

+

모든 Agent에게 전체 Context를 복제하지 않는 것

+

결과만 구조화해 전달하는 것
```

이다.

# 124. 압축 Core 지침

전체 문서를 매번 로드하기 어렵다면 아래만 유지한다.

```text
CONTEXT CHECKPOINT / HANDOFF CORE

1. Treat context as a working set, not a permanent transcript.
2. Preserve user intent, success criteria, critical constraints, decisions, changed files, verification state, open issues, and next actions.
3. Compress resolved exploration, raw tool output, duplicate findings, discarded hypotheses, and completed subagent conversations.
4. Separate VERIFIED facts from assumptions and unknowns.
5. Create a checkpoint at meaningful phase transitions, major decisions, context pressure, or agent transitions.
6. A checkpoint must describe current state; a handoff must be self-contained enough for another agent to continue without broad rediscovery.
7. Preserve evidence pointers instead of copying large source or tool outputs.
8. Record important decisions and rejected alternatives only when they prevent repeated work.
9. Keep the next action explicit and concrete.
10. Never compress away user constraints, security boundaries, protected areas, or unverified risks.
11. On handoff, include repository/git state and distinguish committed from uncommitted changes when relevant.
12. The orchestrator owns the canonical task state; subagents return bounded structured results.
13. After compaction, retain the minimum sufficient context required for the next decision.
```

# 125. Final Principle

> 장기 작업에서 가장 비싼 Token은 새로운 정보를 읽는 Token이 아니라, 이미 알았던 것을 다시 알아내는 Token이다.

따라서:

```text
EXPLORE ONCE

↓

VERIFY

↓

COMPRESS

↓

PRESERVE STATE

↓

CONTINUE
```

를 기본 동작으로 한다.

그리고 Agent가 바뀌면:

```text
DO NOT START OVER

↓

READ HANDOFF

↓

VERIFY FRESHNESS

↓

CONTINUE FROM NEXT STEP
```

를 따른다.
