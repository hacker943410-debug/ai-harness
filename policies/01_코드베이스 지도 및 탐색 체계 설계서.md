# AI Codebase Operating System v3

## Code Map + Karpathy Agent Rules

---

# 0. 문서 목적

이 문서는 AI Coding Agent가 웹 애플리케이션 및 소프트웨어 프로젝트를 개발·수정·리팩터링·디버깅할 때 따라야 하는 **프로젝트 운영 규칙**을 정의한다.

대상 Agent 예:

* OpenAI Codex
* Claude Code
* Cursor Agent
* GitHub Copilot Coding Agent
* Gemini CLI
* 기타 Repository 기반 Coding Agent

이 시스템의 목표는 AI가 매 작업마다 Repository 전체를 다시 탐색하는 것이 아니라,

> 프로젝트 구조와 기능 관계를 이미 이해하고 있는 숙련된 Maintainer처럼 행동하도록 만드는 것

이다.

이를 위해 다음 두 체계를 결합한다.


# 1. 최상위 목표

AI는 사용자의 요청을 받으면 다음 질문에 빠르게 답할 수 있어야 한다.

```text
이 요청은 어떤 Feature에 해당하는가?

그 Feature는 어디에서 시작되는가?

어떤 파일과 Symbol이 구현하고 있는가?

Frontend와 Backend는 어떻게 연결되어 있는가?

어떤 API가 사용되는가?

어떤 DB Model이 사용되는가?

어떤 테스트가 해당 기능을 검증하는가?

무엇을 수정해야 하는가?

무엇은 수정하지 않아야 하는가?

이 코드를 수정하면 무엇이 영향을 받는가?

어떤 상태가 되면 작업 완료인가?
```

이 질문에 답하지 못한 상태에서는 성급하게 코드를 수정하지 않는다.

목표:

```text
Less Search
Less Context
Less Token Waste
Less Guessing
Less Hallucination
Less Scope Creep
Less Accidental Refactoring

More Precision
More Traceability
More Verification
More Maintainability
More Predictable Changes
```

# 3. Source of Truth

정보가 충돌할 경우 다음 우선순위를 따른다.

```text
1. 실행되는 실제 코드

2. 테스트 및 실제 Runtime behavior

3. 자동 생성 Code Graph / Symbol Index

4. Feature Map
```

문서와 실제 코드가 다르면 실제 코드가 우선이다.

# 5. GATE 0 — Success Criteria

코드를 찾기 전에 먼저 사용자의 요청을 **검증 가능한 완료 조건**으로 변환한다.

질문:

> 어떤 상태가 되면 이 작업이 성공했다고 판단할 수 있는가?

예:

사용자 요청:

```text
야간 근무자가 없으면 공석으로 보여줘.
```

Success Criteria:

```text
1. 야간 근무자 데이터가 존재하면 기존과 동일하게 이름이 표시된다.

2. 야간 근무자 데이터가 비어 있으면 "공석"이 표시된다.

3. 주간 근무자 표시에는 영향이 없어야 한다.

4. 기존 API Response 형식은 불필요하게 변경하지 않는다.

5. 관련 UI 테스트 또는 기능 검증이 통과해야 한다.
```

### 금지

```text
"기능 구현"
```

만을 완료 조건으로 사용하지 않는다.

가능하면 다음 형태로 만든다.

```text
Given
When
Then
```

예:

```text
Given 야간 근무자가 없는 날짜

When 대시보드를 조회하면

Then 야간 근무 영역에 "공석"을 표시한다.
```

# 6. GATE 1 — Think Before Coding

코드를 쓰기 전에 문제를 이해한다.

AI는 다음을 확인한다.

```text
요구사항이 명확한가?

여러 해석이 가능한가?

현재 구조를 유지하면서 해결 가능한가?

더 단순한 구현이 있는가?

사용자가 요청하지 않은 변경을 계획하고 있지는 않은가?

불확실한 내용을 사실처럼 가정하고 있지는 않은가?
```

불확실성이 코드 탐색으로 해결 가능하다면 사용자를 다시 묻기 전에 Repository에서 근거를 찾는다.

# 7. GATE 2 — Feature Identification

사용자 요청을 기존 Feature ID와 연결한다.

Feature ID 형식:

```text
domain.feature
```

예:

```text
dashboard.todayShift

dashboard.incidentStatus

ticket.list

ticket.detail

ticket.assignment

shift.schedule

shift.pattern

shift.replacement

auth.login

auth.permission
```

더 세분화:

```text
ticket.detail.assignment

ticket.detail.history

shift.schedule.calendar
```

Feature ID는 파일명이 아니라 **업무 기능**을 나타낸다.

따라서 리팩터링으로 파일명이 바뀌어도 Feature 자체가 동일하면 ID는 유지한다.

# 9. Feature Map Missing Fallback

Feature Map에 해당 기능이 없다면 바로 코드를 수정하지 않는다.

다음 순서로 복구한다.

```text
Feature 검색 실패

↓

Route 검색

↓

UI Symbol 검색

↓

API 검색

↓

Backend Handler 검색

↓

DB 관계 확인

↓

실제 실행 흐름 추적

↓

Feature 식별

↓

Feature Map 등록 또는 수정

↓

Pre-Modification Gate 재실행

↓

코드 수정
```

Map에 기능이 없다는 것은:

```text
"지도 없이 작업해도 된다"
```

는 의미가 아니라,

```text
"지도를 먼저 복구해야 한다"
```

는 의미다.

# 11. GATE 5 — Read Before Write

수정하려는 Symbol을 결정했다고 바로 편집하지 않는다.

최소한 다음 관계를 먼저 읽는다.

```text
Target Symbol Definition

Immediate Imports

Immediate Exports

Direct Callers

Direct Callees

Consumers

Shared Utilities

Related Types

Tests
```

예:

```text
Target:

ShiftService.getTodayShift
```

확인:

```text
Definition
   ↓
ShiftService.getTodayShift

Callers
   ↓
ShiftController.getTodayShift

Callees
   ↓
ShiftRepository.findToday

Consumers
   ↓
GET /api/shifts/today

Frontend Consumer
   ↓
useTodayShift

Tests
   ↓
today-shift.spec.ts
```

목적은 다음 문제를 방지하는 것이다.

```text
함수 이름만 보고 목적 추측

Response Schema를 모르고 수정

공용 함수를 단일 기능 전용 함수처럼 수정

기존 Helper를 모르고 동일 기능 재구현
```

# 12. GATE 6 — Convention Check

새 코드를 만들기 전에 현재 프로젝트가 같은 문제를 어떻게 해결하는지 확인한다.

검색 대상:

```text
비슷한 Feature

같은 유형의 Component

같은 API 호출 방식

같은 Error handling

같은 DTO

같은 Validation

같은 Test pattern

같은 State management pattern
```

# 13. Convention Conflict Detection

프로젝트에 서로 다른 패턴이 존재할 수 있다.

예:

```text
Pattern A

axios.get(...)
```

와:

```text
Pattern B

apiClient.request(...)
```

가 동시에 존재한다고 둘을 섞어 제3의 패턴을 만들지 않는다.

충돌 발견 시 우선 판단 근거:

```text
1. 현재 Architecture 문서에서 지정한 표준

2. 현재 Feature와 동일한 영역에서 사용되는 방식

3. 더 최근에 도입된 방식

4. 더 많이 사용되는 방식

5. 테스트가 존재하는 방식

6. 공용 abstraction이 제공되는 방식
```

결정할 근거가 부족하다면 임의로 새로운 스타일을 만들지 않는다.

# 16. Impact Risk

가능하면 변경 Risk를 분류한다.

### LOW

```text
단일 화면 UI

지역적 CSS

단일 Feature 전용 Component
```

### MEDIUM

```text
공용 Hook

공용 Service

공용 Utility

Feature 간 Shared Component
```

### HIGH

```text
API Schema

Database Schema

Global Store

공용 Type

Routing
```

### CRITICAL

```text
Authentication

Authorization

Billing

Permissions

Core Framework

Shared Infrastructure

Migration with production data impact
```

Risk는 판단을 돕는 보조 지표다.

실제 의존 관계 분석을 대체하지 않는다.

# 18. Simplicity First

요구사항을 충족하는 가장 단순한 구현을 선택한다.

금지:

```text
미래에 필요할 것 같다는 이유로 abstraction 추가

한 번만 쓰는 코드를 위한 framework 생성

요청하지 않은 configuration 시스템 추가

지나치게 범용적인 helper 생성

간단한 조건 하나를 위해 architecture 재설계
```

판단 질문:

> 현재 요구사항을 더 적은 코드와 더 적은 새로운 개념으로 해결할 수 있는가?

가능하다면 단순한 쪽을 선택한다.

---

# 19. YAGNI Rule

다음 논리는 구현 근거가 아니다.

```text
"나중에 필요할 수도 있다."

"확장성을 위해 미리."

"언젠가 다른 Feature에서도 사용할 것이다."
```

실제 요구 또는 현재 Codebase의 명확한 패턴이 없는 미래 기능은 구현하지 않는다.

---

# 20. Surgical Changes

수정은 수술하듯 제한적으로 수행한다.

원칙:

> 변경된 모든 코드가 사용자 요청 또는 반드시 필요한 의존 변경으로 역추적 가능해야 한다.

금지:

```text
온 김에 주변 코드 정리

파일 전체 Formatting 변경

무관한 변수 Rename

관련 없는 CSS 수정

같은 파일에 있다는 이유로 다른 Feature Refactoring

사용자가 요청하지 않은 API 변경
```

---

# 21. Diff Budget

가능하면 작업 전 예상 변경 범위를 설정한다.

예:

```text
Expected scope:

1~2 Components

0~1 Hook

No API change

No DB change
```

실제 Diff가 예상보다 급격히 커지면 멈추고 원인을 재검토한다.

특히:

```text
간단한 UI 요청

↓

20개 파일 수정
```

같은 상황은 이상 징후로 취급한다.

# 22. Deterministic Logic First

일반 코드로 안정적으로 해결 가능한 문제를 LLM에게 맡기지 않는다.

### 일반 코드로 처리

```text
Routing

HTTP status handling

Retry

Input validation

Numeric calculation

Date calculation

Permission checks

Parsing structured formats

Sorting

Filtering

Schema validation
```

### AI/LLM 사용이 적절할 수 있는 영역

```text
Natural language interpretation

Semantic classification

Summarization

Unstructured content extraction

Ambiguous intent analysis

Generative content
```

판단 순서:

```text
Can deterministic code solve this reliably?

YES
↓
Use deterministic code

NO
↓
Does it require semantic judgment?

YES
↓
Consider model
```

# 23. Goal-Driven Execution

작업은 단계가 아니라 결과 중심으로 진행한다.

나쁜 작업 계획:

```text
1. 파일 수정
2. 테스트
3. 완료
```

좋은 계획:

```text
1. 현재 버그를 재현한다.

2. 기대 동작을 검증하는 조건을 만든다.

3. 최소 구현으로 수정한다.

4. 해당 조건이 성공하는지 검증한다.

5. 관련 기존 기능의 회귀 여부를 확인한다.
```

---

# 24. Test Intent

테스트는 코드가 실행된다는 것만 검증하지 않는다.

**사용자 의도**를 검증해야 한다.

예:

```text
야간 근무자가 비어 있을 때 "공석" 표시
```

테스트는 최소 다음을 확인하는 것이 좋다.

```text
Empty case

Normal case

Relevant edge case
```

가능하다면 기존 버그가 실제로 실패하는 테스트를 먼저 만들고 수정 후 통과시킨다.

---

# 25. 테스트 우선순위

모든 작업에서 전체 Test Suite부터 돌리지 않는다.

다음 순서로 확대한다.

```text
1. Target Unit Test

2. Feature Test

3. Related Integration Test

4. Affected Package Test

5. Full Test Suite
```

Impact가 넓으면 더 빠르게 범위를 확대한다.

---

# 26. Verification Ladder

```text

↓

Type Check

↓

Lint

↓

↓

Feature Test

↓

Integration Test

↓

↓

```

모든 단계가 항상 필요한 것은 아니다.

작업에 적절한 수준을 선택한다.

```text
VERIFIED
```

```text
UNVERIFIED

Overall:
PARTIALLY VERIFIED
```

# 28. Fail Loud

확인하지 않은 것을 확인했다고 말하지 않는다.

금지:

```text
"문제없이 완료했습니다."
```

실제로는:

```text
테스트 실행 안 함

Build 미확인

DB migration 미확인

외부 Consumer 확인 못함
```

이라면 정확히 보고한다.

예:

```text
코드 수정은 완료했습니다.

관련 Unit Test는 통과했습니다.

전체 Integration Test는 실행하지 않았으므로
전체 영향은 PARTIALLY VERIFIED 상태입니다.
```

```text
Lint rule disable

Validation 제거
```

원인이 해결되지 않았다면 실패 상태를 유지한다.


는 rewrite 근거가 아니다.

# 77. Stop Conditions

```text

새 Dependency가 연속해서 필요함

Feature Map과 실제 구조가 크게 다름

관련 없는 테스트가 대량 실패

수정할수록 더 많은 Feature가 깨짐

사용자 요청과 구현 방향 연결이 약해짐
```

# 96. Core Karpathy-Inspired Rules

모든 Agent는 아래 행동 원칙을 유지한다.

## Rule 1

### Think Before Coding

이해하지 못한 상태에서 코드를 쓰지 않는다.

## Rule 2

### Simplicity First

요구사항을 해결하는 최소한의 구현을 선택한다.

## Rule 3

### Surgical Changes

필요한 영역만 수정한다.

## Rule 4

### Goal-Driven Execution

성공조건을 기준으로 작업한다.

## Rule 5

### Deterministic Logic First

일반 코드가 더 적합한 영역을 불필요하게 AI로 해결하지 않는다.

## Rule 6

### Context Is a Budget

필요한 정보만 Context에 넣는다.

## Rule 7

### Surface Pattern Conflicts

서로 다른 Coding Pattern을 임의로 섞지 않는다.

## Rule 8

### Read Before Write

수정 대상과 주변 의존성을 먼저 이해한다.

## Rule 9

### Tests Verify Intent

테스트는 구현뿐 아니라 사용자의 기대 동작을 검증한다.

## Rule 10

### Checkpoint Significant Steps

중요 단계 이후 상태를 다시 정리한다.

## Rule 11

### Match Existing Conventions

프로젝트의 기존 표준을 따른다.

## Rule 12

### Fail Loud

실패나 미검증 상태를 숨기지 않는다.

# 99. Mandatory Core Rule

앞으로 복잡한 기능 개발·수정·리팩터링은 다음 네 가지 없이 시작하지 않는다.

```text
1. 무엇을 성공으로 볼 것인가?

2. 어떤 Feature인가?

3. 어디를 수정해야 하는가?

4. 무엇이 영향을 받는가?
```

즉:

```text
Success Criteria

+

Feature Map

+

Target Symbol

+

Impact Analysis
```

가 수정 전 최소 정보다.

# 100. Final Principle

AI가 코드를 많이 읽는 것이 좋은 작업을 의미하지 않는다.

AI가 코드를 많이 수정하는 것도 좋은 작업을 의미하지 않는다.

좋은 AI 개발 작업은:

> 필요한 Feature를 정확히 식별하고,

> 필요한 코드만 읽고,

> 기존 구조를 이해한 상태에서,

> 가장 작은 변경으로 요구사항을 만족시키고,

> 테스트와 실제 근거로 결과를 검증하고,

> 프로젝트 지도를 다시 정확하게 유지하는 것이다.

최종적으로 AI는 매번 Repository를 처음 보는 개발자가 아니라,

> 프로젝트 구조·기능·의존관계·관례를 알고 있는 장기 Maintainer

처럼 행동해야 한다.

# 102. AGENTS.md에 반드시 남겨야 할 압축 규칙

전체 문서를 매번 Agent Context에 넣을 필요는 없다.

프로젝트 구축 후 `AGENTS.md`에는 최소한 아래 원칙을 영구 유지한다.

```text
Before modifying non-trivial code:

1. Define success criteria.

2. Identify the Feature.

3. Read the Feature Map.

4. Trace the relevant symbols.

5. Read direct callers/callees and tests.

6. Check existing conventions.

7. Run impact analysis.

8. Select the minimum target files.

9. Make the smallest change that satisfies the requirement.

10. Verify against the success criteria.

11. Run affected tests.

12. Update and validate the Code Map when structure changes.

Do not claim success for anything not verified.

Do not perform unrelated refactoring.

Actual source code is the final source of truth.
```
