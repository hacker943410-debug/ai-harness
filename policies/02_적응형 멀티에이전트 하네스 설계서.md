# Adaptive Multi-Agent Harness

## 모델 중립형 토큰 효율·서브에이전트 오케스트레이션 지침서

Version: 1.0

---

# 0. 문서 목적

이 문서는 AI Coding Agent 및 General AI Agent가 복잡한 작업을 수행할 때:

* 상위 모델이 모든 작업을 직접 수행하지 않고
* 적절한 작업을 서브에이전트에게 위임하며
* 가능한 가장 저비용 모델을 사용하고
* 필요한 경우에만 고성능 모델로 Escalation하며
* 새로운 모델이 추가되어도 지침서를 수정하지 않고
* Token / Context / Cost / Latency를 최소화하면서
* 최종 품질을 유지

하도록 만드는 **Adaptive Multi-Agent Harness 운영 규칙**을 정의한다.

이 시스템은 특정 모델 이름에 의존해서는 안 된다.

금지:

```text
GPT-X면 GPT-Y에게 맡긴다.

Claude-X면 Sonnet-X에게 맡긴다.

Gemini-X면 Flash-X에게 맡긴다.
```

권장:

```text
ORCHESTRATOR
↓
TASK CLASSIFICATION
↓
CAPABILITY REQUIREMENTS
↓
ROLE SELECTION
↓
MODEL ROUTER
↓
CHEAPEST SUFFICIENT MODEL
```

# 1. 핵심 목표

Harness의 최상위 목표는 다음이다.

> 가장 강한 모델을 가장 많이 사용하는 것이 아니라, 작업을 안정적으로 완료할 수 있는 최소 비용의 충분한 모델을 각 단계에 배치한다.

이를 다음 식으로 표현한다.

```text
Minimize:

Token Cost
+
Inference Cost
+
Context Duplication
+
Latency
+
Redundant Work

Subject to:

Required Quality
Required Reliability
Required Safety
Required Verification
```

---

# 2. 절대 원칙 — 모델 이름을 정책에 넣지 않는다

Harness의 영구 정책에는 특정 모델명을 기록하지 않는다.

금지:

```yaml
scout: gpt-5.x-mini
coder: sonnet-x
reviewer: opus-x
```

권장:

```yaml
scout:
  tier: efficient

implementer:
  tier: balanced

reviewer:
  tier: frontier
```

실제 모델과 역할의 연결은 반드시 별도의 **Model Registry**에서 관리한다.

# 4. Orchestrator 정의

현재 사용자가 선택했거나 Harness 실행을 시작한 Primary Agent를:

```text
ORCHESTRATOR
```

라고 부른다.

지침에는 특정 모델명을 쓰지 않는다.

예:

```text
현재 Primary Agent가 무엇이든
→ ORCHESTRATOR
```

ORCHESTRATOR의 역할:

```text
사용자 의도 이해

Success Criteria 정의

Task 분해

Task Dependency 분석

Delegation 여부 결정

Role 지정

중요 Architecture 판단

Subagent 결과 병합

충돌 해결

Escalation 판단

최종 품질 검증

최종 사용자 응답
```

ORCHESTRATOR는 반복적이고 저위험한 모든 세부 작업을 직접 수행하지 않는 것을 기본 원칙으로 한다.

단, Delegation overhead가 더 큰 경우 직접 처리한다.

# 5. Agent Role 체계

모델이 아니라 **역할**을 먼저 선택한다.

기본 역할은 다음과 같다.

## ORCHESTRATOR

목적:

```text
작업 분해
중요 의사결정
결과 통합
최종 검증
```

기본 성격:

```text
높은 Reasoning
높은 Reliability
높은 Context 이해
```

---

## SCOUT

목적:

```text
코드 검색
문서 탐색
Feature 탐색
Symbol 탐색
파일 위치 탐색
API 위치 탐색
자료 수집
```

성격:

```text
낮은 비용
빠른 속도
좋은 Tool Use
중간 Reasoning
```

---

## WORKER

목적:

```text
반복 작업
정형 데이터 변환
대량 비교
단순 분류
파일 목록 처리
기계적 코드 수정
```

성격:

```text
매우 낮은 비용
높은 처리량
```

---

## IMPLEMENTER

목적:

```text
실제 기능 구현
코드 작성
버그 수정
테스트 작성
```

성격:

```text
높은 Coding
충분한 Reasoning
중간 비용
```

---

## SPECIALIST

목적:

```text
Database
Security
Frontend
Backend
Infrastructure
Performance
특정 Framework
```

등 특정 전문영역 처리.

---

## REVIEWER

목적:

```text
코드 검토
Architecture 검토
Regression 가능성 분석
Requirements 충족 검증
```

성격:

```text
높은 Reasoning
높은 Coding 이해
독립된 시각
```

---

## VERIFIER

목적:

```text
Test 결과 확인
Build 결과 확인
정형 검증
Success Criteria 검사
```

가능하면 LLM보다 Deterministic Tool을 우선 사용한다.

# 6. Model Tier

실제 모델은 이름 대신 기본적으로 다음 Tier로 분류한다.

```text

BALANCED

```

필요하면 추가 가능하다.

---

## EFFICIENT

적합:

```text
검색
분류
반복 작업
단순 코드 이해
파일 탐색
간단한 코드 변경
요약
정형 데이터 변환
```

우선순위:

```text
낮은 비용
빠른 속도
높은 처리량
```

---

## BALANCED

적합:

```text
일반 기능 구현
버그 수정
코드 작성
중간 수준 설계
코드 리뷰
복잡한 파일 분석
```

---

## FRONTIER

적합:

```text
Architecture 결정
고난도 Reasoning
복잡한 Root Cause 분석
Security Critical 작업
대규모 Refactor 판단
서로 충돌하는 Subagent 결과 해결
최종 Critical Review
```

```json
    "tool_use": 8.5,

    "relativeOutputCost": 5
```

# 8. Cheapest Sufficient Model 원칙

Router의 가장 중요한 규칙이다.

금지:

> 항상 가장 싼 모델을 선택한다.

금지:

> 항상 가장 강한 모델을 선택한다.

정답:

> 요구 Capability Threshold를 충족하는 후보 중 예상 총비용이 가장 낮은 모델을 선택한다.

예:

```text
Task Requirements

reasoning >= 6
coding >= 7
tool_use >= 8
reliability >= 7
```

후보:

```text
Model A

Cost 1
Coding 5

→ 탈락


Model B

Cost 3
Coding 8
Tool 9

→ 적합


Model C

Cost 10
Coding 10
Tool 10

→ 적합
```

선택:

```text
Model B
```

# 26. Delegation Gate

모든 작업을 Subagent에게 위임하지 않는다.

위임 전 다음을 판단한다.

```text
Delegation Benefit

>

Delegation Overhead
```

Delegation Benefit:

```text
Context 절감

저비용 모델 사용

Parallelism

전문 모델 활용

독립적 검증
```

Delegation Overhead:

```text
Task 설명 Token

Context 전달

Subagent 결과 Token

결과 병합

추가 Validation
```

---

# 27. 위임하지 않는 경우

일반적으로 다음은 직접 처리한다.

```text
매우 단순한 작업

현재 Context만으로 즉시 처리 가능

1개 파일 / 1개 Symbol 수준

Subagent 설명 비용이 실제 작업보다 큼

추가 Agent가 품질 향상에 거의 기여하지 않음
```

---

# 29. Token Efficiency의 핵심 — Context Fork 금지

Subagent에게 Parent 전체 대화를 그대로 복제하지 않는다.

금지:

```text
Parent Context 50K

→ Worker 1 전체 50K
→ Worker 2 전체 50K
→ Worker 3 전체 50K
```

이 구조는 Multi-Agent임에도 Token을 더 많이 소비할 수 있다.

# 30. Task Packet

Subagent에는 필요한 정보만 압축해서 전달한다.

기본 구조:

```json
{
  "taskId": "task-001",

  "role": "SCOUT",

  "objective": "오늘 근무 기능의 실제 구현 위치를 식별한다.",

  "successCriteria": [
    "Primary UI Symbol 식별",
    "관련 API 식별",
    "관련 테스트 식별"
  ],

  "knownContext": {
    "feature": "dashboard.todayShift"
  },

  "contextRefs": [
    "feature-map:dashboard.todayShift"
  ],

  "constraints": [
    "코드 수정 금지",
    "관련 없는 파일 탐색 최소화"
  ],

  "outputSchema": "ScoutResult"
}
```

전체 Conversation History는 기본 전달하지 않는다.

# 31. Context Reference 방식

예:

```text

```

Subagent가 필요한 데이터만 Harness를 통해 가져오도록 한다.

# 32. Progressive Context Loading

```text

↓

↓

Relevant Symbol
```

# 33. Result Compression

Subagent는 읽은 모든 내용을 Parent에게 그대로 반환하지 않는다.

결과는 구조화하고 압축한다.

예:

```json
{
  "status": "VERIFIED",

  "findings": [
    {
      "file": "src/features/dashboard/TodayShiftCard.tsx",
      "symbol": "TodayShiftCard",
      "role": "primary_ui"
    }
  ],

  "api": [
    "GET /api/shifts/today"
  ],

  "tests": [
    "tests/dashboard/today-shift.spec.ts"
  ],

  "uncertainties": []
}
```

---

# 34. Evidence Pointer

가능하면 결과에 원문 전체가 아니라 Evidence Pointer를 붙인다.

```text
File + Symbol

Document + Section

API + Handler

Test + Test Name
```

Parent가 필요할 때만 원문을 다시 조회한다.

# 35. No Duplicate Investigation

이미 다른 Agent가 검증한 사실을 동일한 목적의 Agent가 다시 조사하지 않는다.

Harness는 Task Result Cache를 유지할 수 있다.

예:

```text
Feature Trace:
dashboard.todayShift

status = VERIFIED

fresh = true
```

이면 동일 작업 재실행을 피한다.

---

# 36. Result Cache

가능하면 다음 Cache를 둔다.

```text
Feature discovery cache

Symbol lookup cache

API trace cache

Test lookup cache

Documentation summary cache
```

무효화 기준:

```text
관련 File 변경

Git Commit 변경

Map 갱신

TTL 만료
```

---

# 37. Parallel Delegation

독립적인 작업만 병렬화한다.

좋은 예:

```text
SCOUT A
Frontend 분석

SCOUT B
Backend 분석

SCOUT C
Tests 분석
```

---

# 38. 병렬화 금지

다음처럼 Dependency가 있는 작업은 순차적으로 수행한다.

```text
A 결과가 있어야 B의 입력을 결정할 수 있음
```

흐름:

```text
A

↓

B

↓

C
```

독립성 없는 작업을 병렬로 실행하면 중복 조사와 Token 낭비가 발생한다.

---

# 39. Maximum Parallelism

무제한 Subagent 생성을 금지한다.

기본적으로 작업당 필요한 최소 Agent 수를 사용한다.

예:

```text
Simple:
0 subagents

Standard:
0~2

Complex:
1~4

Very Complex:
필요성 근거가 있을 때만 확대
```

고정 숫자가 아니라 비용/효율 정책에 따라 조정할 수 있다.

---

# 40. Delegation Depth

Agent가 Agent에게 계속 위임하는 무제한 Tree를 금지한다.

권장 기본:

```text
MAX_DELEGATION_DEPTH = 2
```

일반:

```text
ORCHESTRATOR

↓

SUBAGENT
```

고난도:

```text
ORCHESTRATOR

↓

LEAD SPECIALIST

↓

SPECIALIST
```

그 이상의 위임은 특별한 근거가 없는 한 금지한다.

---

# 41. No Delegation Explosion

다음 구조를 피한다.

```text
1 Parent

→ 8 Agents

→ 각 Agent가 8 Agents

→ 64 Agents
```

Agent 수 자체를 성능으로 착각하지 않는다.

---

# 42. Escalation

저비용 모델이 해결하지 못하면 점진적으로 상위 Capability 모델로 올린다.

```text
EFFICIENT

↓

BALANCED

↓

FRONTIER
```

Escalation Trigger:

```text
confidence 부족

결과 충돌

테스트 실패

Tool 결과 이해 실패

Complexity 예상 초과

Security risk 발견

Architecture 판단 필요
```

---

# 43. Escalation은 전체 작업이 아니라 해당 Task만

한 Subtask가 어려워졌다고 전체 작업을 Frontier 모델로 옮기지 않는다.

예:

```text
Repository Search
→ EFFICIENT

Architecture Question
→ FRONTIER

Mechanical Edits
→ 다시 EFFICIENT
```

작업 단계별로 Model Tier를 재평가한다.

---

# 44. De-escalation

고성능 모델이 중요 판단을 끝냈다면 이후 단순 실행 작업은 다시 저비용 모델로 내린다.

예:

```text
Architecture

FRONTIER

↓

구현 규칙 확정

↓

파일 12개 단순 수정

EFFICIENT

↓

일반 기능 구현

BALANCED

↓

Critical Review

FRONTIER
```

---

# 45. Confidence Policy

Subagent는 결과와 함께 Confidence 또는 Verification Status를 반환한다.

예:

```text
VERIFIED

HIGH_CONFIDENCE

MEDIUM_CONFIDENCE

LOW_CONFIDENCE

UNVERIFIED
```

LOW 또는 UNVERIFIED일 경우 Router가 재검증 또는 Escalation을 결정한다.

---

# 46. Verification 우선순위

가능한 검증은 LLM보다 Deterministic Tool을 우선한다.

예:

```text
TypeScript compiler

Test runner

Linter

Schema validator

Git diff

AST parser

Database migration checker
```

LLM에게:

```text
"컴파일될 것 같아?"
```

라고 묻는 대신 실제 Compile을 실행한다.

---

# 47. Deterministic First

다음은 기본적으로 Agent에게 위임하지 않는다.

```text
단순 계산

정형 validation

정확한 parsing

Test 실행

Build 실행

Lint 실행

Diff 계산

파일 존재 여부

Symbol index lookup
```

가능하면 코드 또는 Tool이 처리한다.

---

# 48. Reviewer Independence

중요한 작업에서는 IMPLEMENTER와 REVIEWER를 분리할 수 있다.

```text
IMPLEMENTER

↓

code

↓

REVIEWER
```

동일 Agent의 자기검증만으로 중요한 변경을 승인하지 않을 수 있다.

CRITICAL 작업에서는 독립 Review를 우선한다.

---

# 49. Reviewer에게 전체 Context를 전달하지 않는다

Reviewer에는:

```text
Success Criteria

Relevant Diff

Feature Map

Impact Summary

Tests

Relevant Contracts
```

만 전달한다.

전체 개발 대화를 넘겨 Bias와 Token 비용을 증가시키지 않는다.

---

# 50. Model Diversity는 선택 사항

Provider 혼합은 정책으로 결정한다.

예:

```yaml
provider_policy:
  delegation_scope: same_provider
```

또는:

```yaml
provider_policy:
  delegation_scope: any_approved_provider
```

지침을 수정하지 않고 설정만 변경한다.

---

# 51. Same Provider Mode

설정:

```text
same_provider
```

이면:

```text
Parent Provider
↓
동일 Provider 내 후보 모델 검색
```

예를 들어 ORCHESTRATOR가 Provider A라면 Worker도 기본적으로 Provider A에서 찾는다.

---

# 52. Cross Provider Mode

설정:

```text
any_approved_provider
```

이면:

```text
OpenAI
Anthropic
Google
기타 Approved Provider
```

전체 후보에서 Capability/Cost 기준으로 선택한다.

---

# 53. Provider Preference와 Model Name 분리

가능:

```yaml
provider_policy:
  preferred:
    - same_as_orchestrator

  fallback:
    - any_approved
```

특정 모델명을 넣지 않는다.

---

# 54. Cost Policy

비용 정책 예:

```yaml
cost_policy:

  objective: cheapest_sufficient

  critical_tasks:
    quality_over_cost: true

  low_risk_tasks:
    cost_priority: high

  review:
    independent_model_preferred: true
```

---

# 55. Token Budget

고정 숫자를 영구 정책으로 박지 않는 것을 권장한다.

대신 상대적 예산을 사용한다.

예:

```text
SMALL

MEDIUM

LARGE
```

또는:

```text
전체 작업 예산 대비 비율
```

---

# 56. Token Budget Allocation

예:

```text
Planning / Routing
10%

Search / Discovery
20%

Implementation
35%

Verification
25%

Reserve
10%
```

고정 수치가 아니라 기본 정책 예시다.

Harness가 실제 작업 성격에 따라 조정한다.

---

# 57. Verification Reserve

초기 분석에서 Token Budget을 전부 쓰지 않는다.

항상 검증과 예외 상황을 위한 Reserve를 남긴다.

```text
Do not spend 100% on exploration.
```

---

# 58. Search Budget

SCOUT가 무제한 탐색하지 못하게 한다.

종료 조건:

```text
Success Criteria 충족

Primary Symbols 확보

필요한 API/Tests 확보

추가 검색의 정보 가치가 낮음
```

---

# 59. Information Value Rule

새 파일을 읽기 전에 판단한다.

> 이 파일을 읽으면 현재 결정이 실질적으로 달라질 가능성이 있는가?

NO:

```text
읽지 않는다.
```

YES:

```text
읽는다.
```

---

# 60. Parent Context Protection

ORCHESTRATOR Context에는 Raw Worker output을 계속 누적하지 않는다.

대신:

```text
Working State
```

를 유지한다.

예:

```json
{
  "feature": "dashboard.todayShift",

  "successCriteria": [],

  "confirmedFacts": [],

  "targetFiles": [],

  "openIssues": [],

  "verification": {}
}
```

---

# 61. Context Compaction

Context 압력이 높아지면 다음을 압축한다.

```text
이미 해결된 조사

중복 Tool Output

오래된 후보

실패한 탐색 경로

Raw Logs
```

다음은 유지한다.

```text
사용자 요구

Success Criteria

Confirmed facts

중요 의사결정

Target Files

Unresolved Issues

Verification Evidence
```

---

# 62. Task Dependency Graph

복잡한 작업은 Task를 DAG 형태로 표현할 수 있다.

예:

```text
           Feature Discovery
             /          \
            /            \
      Frontend Trace   Backend Trace
            \            /
             \          /
             Impact Analysis
                    |
              Implementation
                    |
                 Tests
                    |
                 Review
```

이 Graph로 Parallelism과 순서를 결정한다.

---

# 63. Task Decomposition Rule

분해 기준:

좋은 Subtask:

```text

입력과 출력이 명확

Success Criteria가 명확

결과를 압축 가능
```

나쁜 Subtask:

```text
"프로젝트 전체를 알아서 분석해줘."

"다 확인해."

"잘 만들어줘."
```

# 65. Result Validation

Subagent 응답을 무조건 신뢰하지 않는다.

최소:

```text
Schema Validation

Evidence Validation

File/Symbol existence validation
```

을 할 수 있다.

Critical Result는 추가 Reviewer가 검증할 수 있다.

---

# 66. Conflict Resolution

두 Agent 결과가 충돌하는 경우 평균내지 않는다.

예:

```text
Agent A:
API 변경 필요

Agent B:
API 변경 불필요
```

정답:

```text
A와 B의 근거 확인

↓

Source of Truth 조회

↓

필요하면 상위 모델에 판단 위임
```

"중간쯤"으로 결정하지 않는다.

---

# 67. Retry Policy

동일 Prompt를 동일 모델에게 무한 반복하지 않는다.

실패 시:

```text
1차

Task Packet 보정

↓

2차

동일 Tier 다른 후보 또는 설정 변경

↓

3차

Escalate
```

---

# 68. Retry Budget

Retry도 비용이다.

Task마다 최대 Retry 또는 비용 한도를 둔다.

무한 재시도 금지.

---

# 69. Failure Classification

실패를 구분한다.

```text
MODEL_FAILURE

TOOL_FAILURE

CONTEXT_FAILURE

TASK_DECOMPOSITION_FAILURE

MISSING_INFORMATION

POLICY_BLOCK

EXTERNAL_SERVICE_FAILURE
```

무조건 더 강한 모델로 Escalate하지 않는다.

예:

```text
API 서버 다운

→ Frontier 모델로 바꿔도 해결되지 않음
```

---

# 70. Architecture Decision Rule

Architecture 선택은 반복 Worker에게 위임하지 않는다.

Architecture 결정이 필요한 경우:

```text
ORCHESTRATOR

또는

FRONTIER SPECIALIST
```

가 판단한다.

결정 이후 기계적 구현은 낮은 Tier로 내려보낼 수 있다.

# 79. Model Health

# 80. Performance Drift

모델 Provider 업데이트로 동작이 달라질 수 있다.

주기적으로 Calibration Benchmark를 실행한다.

큰 성능 변화가 발견되면 Capability Profile을 갱신한다.

---

# 81. Cost Drift

가격 변동 역시 Registry/Metadata 영역에서 반영한다.

정책 문서는 수정하지 않는다.

예:

```text
Model A 가격 하락

↓

↓

Router 우선순위 자동 변경
```

---

# 82. Model Replacement

기존 Efficient 모델보다:

```text
더 싸고

더 빠르고

동일 이상 품질
```

의 신규 모델이 추가되면 Router가 자연스럽게 신규 모델을 선호하게 한다.

지침서 수정은 필요 없다.

---

# 83. Alias 전략

Provider가 Stable alias 또는 최신 모델 alias를 제공하는 경우 사용 가능하지만:

```text
latest
```

가 자동 변경될 수 있다면 Benchmark/Canary 정책과 결합한다.

Critical Production Harness에서는 검증되지 않은 Hot Swap을 피할 수 있다.

---

# 84. Canary

신규 모델을 일정 비율의 저위험 Task에 먼저 사용한다.

예:

```text
CANDIDATE

↓

Low-risk 5%

↓

결과 정상

↓

25%

↓

정상

↓

ACTIVE
```

구체적 비율은 환경에 맞게 설정한다.

---

# 85. Fallback

선택된 모델 사용 불가 시:

```text
same role

same capability tier

next cheapest candidate
```

순으로 대체한다.

모델 ID를 하드코딩하지 않는다.

# 86. Routing Score

```text
+
Reliability
+
Speed
-

-

-
```

```text

```

SEARCH:

```text

```

# 87. Cost Estimate는 총비용 기준

단순 Token 단가만 비교하지 않는다.

# 101. Harness Mandatory Rules

모든 Agent 작업에 다음 원칙을 적용한다.

```text
1. 현재 모델명을 기준으로 작업자를 선택하지 않는다.

2. 먼저 Task의 복잡도와 요구 Capability를 판단한다.

3. Delegation Benefit이 Overhead보다 클 때만 위임한다.

4. 위임 시 전체 Context가 아니라 최소 Task Packet만 전달한다.

5. Capability Threshold를 충족하는 모델 중 예상 총비용이 가장 낮은 모델을 선택한다.

6. 어려운 Task만 Escalate한다.

7. 판단이 끝난 뒤 단순 작업은 De-escalate한다.

8. 독립 Task만 Parallelize한다.

9. Deterministic Tool로 가능한 검증은 LLM 대신 Tool을 사용한다.

10. Subagent 결과는 압축된 구조로 반환한다.

11. 검증되지 않은 결과는 VERIFIED로 취급하지 않는다.

12. 신규 모델은 자동 발견할 수 있지만 자동 신뢰하지 않는다.

13. 새 모델 추가 때문에 Harness Core Instruction을 수정하지 않는다.

14. 모델 변화는 Registry와 Benchmark Layer에서 흡수한다.

15. 품질 Threshold를 지키면서 총 Token/Cost를 최소화한다.
```

# 102. ORCHESTRATOR용 압축 지침

전체 Harness 문서를 매번 Prompt에 넣지 않아도 된다.

실제 상시 Agent 지침에는 다음을 유지한다.

```text
You are the ORCHESTRATOR.

Do not select subagents by hardcoded model names.

For each non-trivial task:

1. Define success criteria.
2. Classify task complexity and risk.
3. Decide whether delegation has positive expected value.
4. If delegating, select a ROLE, not a model.
5. Let the model router choose the cheapest approved model that satisfies the required capabilities.
6. Send only a minimal Task Packet, never the full parent context unless strictly necessary.
7. Parallelize only independent tasks.
8. Prefer deterministic tools for deterministic work.
9. Escalate only the difficult subtask when confidence or verification is insufficient.
10. De-escalate mechanical or low-risk work after high-level decisions are complete.
11. Require structured, compressed subagent results with evidence and uncertainties.
12. Verify important results before accepting them.
13. Do not allow unlimited retries, agent spawning, or delegation depth.
14. Preserve context and token budget for verification.
15. Never hardcode current model family names into long-lived routing policy.
```

---

# 103. Subagent용 압축 지침

```text
You are a SUBAGENT with a bounded task.

Work only on the supplied objective.

Do not broaden scope.

Do not delegate further unless explicitly permitted.

Use the provided context references first.

Load additional context only when necessary.

Do not return raw files or long reasoning unless required.

Return:

- status
- concise findings
- evidence pointers
- uncertainties
- verification state

If the task cannot be completed reliably, report that clearly instead of guessing.
```

# 107. Final Principle

이 Harness의 궁극적인 목적은:

> 어떤 모델이 최신인지 지침서가 아는 것

이 아니다.

Harness는 오직 다음을 알아야 한다.

```text
무슨 작업인가?

얼마나 어려운가?

얼마나 위험한가?

어떤 능력이 필요한가?

위임이 실제로 이득인가?

어떤 역할이 필요한가?

현재 승인된 모델 중 누가 이 조건을 가장 싸게 만족하는가?

결과는 검증되었는가?
```

모델 이름과 세대 변화는 **Model Registry Layer가 흡수한다.**

따라서 장기적으로 유지해야 하는 것은:

```text
Stable Policy

+

Dynamic Registry

+

Continuous Benchmark

+

Adaptive Routing
```

이다.

# 108. 최종 강제 원칙

> 모델명을 지침에 하드코딩하지 않는다.

> 역할을 먼저 선택하고 모델은 Router가 선택한다.

> 가장 싼 모델이 아니라 가장 싼 **충분한** 모델을 선택한다.

> 단순한 작업은 위임하지 않을 수 있다.

> 전체 Context를 Subagent에게 복제하지 않는다.

> 어려운 부분만 Escalate한다.

> 중요한 판단이 끝나면 다시 저비용 모델로 De-escalate한다.

> 새로운 모델은 자동 발견할 수 있지만 검증 없이 사용하지 않는다.

> 모델 교체는 Policy가 아니라 Registry에서 해결한다.

> 최종 Token 최적화는 단순 호출 단가가 아니라 **성공한 작업 하나당 총비용**을 기준으로 평가한다.
