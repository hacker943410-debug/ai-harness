# Migration to v6.0.0

SUPPORTED_FROM: 4.x / 5.x / 6.x recognized scalar/JSON project bindings. Migration is REQUIRED from v4/v5; a detected unknown version or conflicting legacy binding blocks. No v4 historical fixture is available, so v4 compatibility is a declared format path, not a tested historical deployment. No tracked policy or Skill is removed.

Read [UPDATE_PROTOCOL](harness/update/UPDATE_PROTOCOL.md). Preserve custom security/company/model/deployment rules; unresolved conflicts require a material decision. Use a staged source candidate rather than overwriting the shared live v5 root. Projects receive a version+content-hash pinned immutable snapshot. Compare OLD UPSTREAM / LOCAL / NEW UPSTREAM using managed hashes and instruction-block bases. Legacy arbitrary custom YAML is kept verbatim as a reference and exact rollback backup; reconcile semantic conflicts before activation. Native Skills and machine runtime Layer B are unchanged.

H1 reference patches can keep the current phase; H2 workflow changes apply after checkpoint, primarily next phase; H3 major updates freeze product changes. Active DB/deploy/data transformation/incident operations defer. A blocking Harness defect allows a minimal repair, not an unreviewed major update. Completed phases carry forward; missing security/review/baseline/rollback/data/production gates are backfilled before release. Resume requires validated source, audit, build/test baseline, critical regression and benchmark evidence plus restored goal/phase/next task.

Rollback restores only owned project bindings and managed instruction files, byte for byte. Product files are never rewritten. Later edits cause a drift conflict rather than destructive restoration. Transaction journals contain hashes, safe state and owned-file backups; credentials and command output are not serialized. Keep the rollback journal until observation is complete. Interrupted transactions route to recovery before new plans.

Known limits: tests/benchmark are deterministic fixtures on Windows with Node22 and PowerShell5.1; no real production app was deployed, no novice user study or paid model task replay was run. Token measurements count local context with a named tokenizer, not billed provider usage. Deployment/DB/auth changes still need domain-specific decisions, dry runs, backups and real operational evidence. Missing build/test commands are explicit and do not become PASS. Real UI completion requires browser rendering. Structural checks verify contracts/references and executed routes, not arbitrary semantic contradictions in all prose. No automatic remote code/product deployment is performed by the project transaction.
